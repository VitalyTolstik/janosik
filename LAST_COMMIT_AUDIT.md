## 1. 🔴 Critical — чужой `linkId` переписывает строку связи на другой доске

**[ПОДТВЕРЖДЕНО e2e-PoC]**

**Файлы:** [command-writers.ts:713-744](backend/src/commands/command-writers.ts#L713-L744),
[referenced-entity-ids.ts:16-28](backend/src/commands/referenced-entity-ids.ts#L16-L28),
[commands.service.ts:322-370](backend/src/commands/commands.service.ts#L322-L370)

`ADD_CARD_LINK` пишется `upsert`'ом по глобальному первичному ключу:

```ts
await tx.cardLink.upsert({
  where: { id: action.linkId },          // linkId приходит от клиента
  create: { … },
  update: { fromCardId, toCardId, type, position, deletedAt: null },
});
```

`linkId` при этом **не проверяется на принадлежность доске**:

* в `referencedEntityIds()` список `DIRECT_KEYS` не содержит `linkId` (есть `cardId`,
  `columnId`, `labelId`, `checklistId`, `itemId` — и всё);
* `assertIdsBelongToBoard()` умеет опрашивать таблицы `column`, `card`, `label`,
  `checklist`, `checklistItem` — таблицы `cardLink` там нет.

Это прямой регресс инварианта TASK-30.2. Докблок в `referenced-entity-ids.ts`
утверждает: *«Every id a command can name … is collected here»* — после TASK-46 это
утверждение перестало быть правдой, но ни доккомментарий, ни тест не обновились.

### Что удалось воспроизвести

PoC: один аккаунт, две свои доски A и B (кросс-аккаунтная атака требует лишь знания
UUID чужой строки — членство на доске-жертве не нужно).

1. На доске A создана связь `link-a`: `card1-a --blocks--> card2-a`.
2. С доски B отправлена команда `ADD_CARD_LINK { cardId: "card1-b", linkId: "link-a",
   targetCardId: "card2-b", linkType: "relates_to" }` → **HTTP 200**.
3. Строка в БД после атаки:

```json
{"id":"link-a","boardId":"<доска A>","fromCardId":"card1-b","toCardId":"card2-b","type":"relates_to","position":0,"deletedAt":null}
```

4. Агрегат доски A: `cards["card1-a"].links → undefined` — **связь жертвы молча исчезла.**
5. Агрегат доски B: `cards["card1-b"].links → undefined` — у атакующего она тоже не
   появилась (`boardId` строки остался чужим), то есть его оптимистичное состояние
   расходится с сервером навсегда.

Итог: аутентифицированный пользователь, зная UUID строки связи, **удаляет связь на
чужой доске** (и ломает свою собственную). Тихая потеря данных, без ошибки и без следа
в агрегате жертвы.

### Насколько это реально эксплуатируется

`linkId` генерируется на клиенте через
[`createId()`](ui/src/utils/id.ts) — и это **не UUID**:

```ts
return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
```

Префикс — обычная метка времени (перебирается по известному окну), суффикс —
восемь base36-символов от `Math.random()`, то есть около 40 бит **не-криптографической**
случайности; докблок функции сам это признаёт («Not cryptographically secure (fine for
localStorage data)»). Перебор такого идентификатора несопоставимо дешевле перебора UUIDv4.

Плюс более простой путь: **бывший участник доски** (или VIEWER, у которого истёк
`expiresAt`) сохранил все `linkId` доски у себя локально и в экспортном JSON. Ему
подбирать ничего не нужно.

Отдельная находка внутри находки: идентификаторы, на проверке владения которыми держится
вся граница между досками, генерируются клиентом слабым не-crypto генератором. См.
[ALL_AUDIT.md §2.2](ALL_AUDIT.md).

### Чего воспроизвести НЕ удалось (важная поправка)

Симметричный вектор через `REMOVE_CARD_LINK` — `updateMany({ where: { id: action.linkId,
deletedAt: null } })`, тоже без скоупа по доске — **сегодня не эксплуатируется**:
редьюсер на чужой `linkId` делает no-op, `changed === false`, и
[commands.service.ts:236](backend/src/commands/commands.service.ts#L236) не доходит до
`applyCommandWrites`. Запрос всё равно написан без границы доски — это пробитый слой
защиты в глубину, который перестанет спасать при первом же изменении гейта `changed`.

### Фикс

1. `DIRECT_KEYS += "linkId"` в `referenced-entity-ids.ts`.
2. В `assertIdsBelongToBoard` добавить `cardLink` (`{ id: { in: ids }, boardId: { not: boardId } }`).
3. Обоим writer'ам дать скоуп: `upsert` → `updateMany({ where: { id, boardId } })` +
   `create` при `count === 0`; `REMOVE` → `where: { id, boardId, deletedAt: null }`.
4. В [command-ids.e2e-spec.ts:148](backend/test/command-ids.e2e-spec.ts#L148)
   («rejects a foreign entity id in every create-shaped action») добавить кейс
   `ADD_CARD_LINK` — сейчас коммит дописал в этот спек только строчку `cardLink.deleteMany()`
   в wipe, а сам тест-кейс прошёл мимо.

### ✅ Исправлено

* `linkId` добавлен в `DIRECT_KEYS`, докблок теперь прямо предупреждает, чем
  грозит пропуск ключа, и называет этот случай.
* `assertIdsBelongToBoard` опрашивает таблицу `cardLink`.
* Оба writer'а переписаны со скоупом по доске: `upsert` заменён на
  `updateMany({ where: { id, boardId } })` + `create`, когда ничего не
  обновилось; `REMOVE` получил `boardId` в `where`. Граница держится теперь
  в двух местах, а не в одном.
* Тесты: кейс `ADD_CARD_LINK` добавлен в перечисление
  `command-ids.e2e-spec.ts`, плюс отдельный тест
  «leaves the other board's link row untouched (TASK-46)» — оба вектора
  отвечают **409**, строка жертвы остаётся байт-идентичной, агрегат доски A
  не меняется.

## 2. 🟠 High — висячие связи нельзя удалить, но они съедают лимит 50

**[ИЗ КОДА]**

**Файлы:** [links.ts:78-86](ui/src/utils/links.ts#L78-L86),
[CardLinks.tsx:91-134](ui/src/components/board/CardLinks.tsx#L91-L134),
[CardLinks.tsx:143](ui/src/components/board/CardLinks.tsx#L143),
[board-reducer.ts:1579-1580](shared/src/store/board-reducer.ts#L1579-L1580)

Дизайн-решение «висячую строку (цель удалена) не вычищаем» задокументировано и
последовательно реализовано в редьюсере, агрегате и миграции. Но UI и лимит смотрят на
неё по-разному:

* `cardLinkIndex()` **пропускает** висячие строки (`if (link.targetCardId in cards)`),
  поэтому в `facts.outgoing` их нет;
* группы диалога строятся ровно из `facts` → висячая строка **никогда не рендерится**;
* а `linkCount(id) = board.cards[id]?.links?.length` (и `guarded`-проверка в редьюсере)
  считают их **в счёт лимита** `LIMITS.linksPerCard = 50`.

Сценарий: пользователь линкует карточку с 50 другими, те 50 удаляют → карточка
показывает ноль связей, но на любую попытку добавить новую получает тост
«максимум 50 связей», и убрать невидимые строки из интерфейса нечем. Карточку не
починить без импорта/экспорта.

**Фикс (на выбор):** либо считать в лимит только живые строки, либо показывать
висячие отдельной группой с кнопкой удаления («связь на удалённую карточку»).

### ✅ Исправлено

Выбран второй вариант — он не трогает инвариант лимита (первый ломался бы на
undo удаления карточки: 50 живых + воскресшая = 51).

* `cardLinkIndex` больше не выбрасывает висячие строки из `outgoing`; вместо
  этого `degree` считает только живые отношения (`liveOutgoing + incoming`).
  Бейдж на лицевой стороне карточки и фильтр `hasLinks` от этого не поехали —
  они читают именно `degree`.
* В диалоге появилась хвостовая группа `dangling` («links to a deleted card»)
  с обычной кнопкой удаления; кнопка перехода на несуществующую карточку
  задизейблена. Дублирующий суффикс «(deleted)» убран — типизированные группы
  висячих строк больше не содержат, и метку несёт заголовок группы.
* Тесты: `links.test.ts` — «keeps a dangling row in outgoing so the dialog can
  remove it»; `CardLinks.test.tsx` — «renders a row towards a deleted card so
  its cap can be freed» (на доске, засеянной ровно в это состояние) и
  «does not count a deleted target on the card front badge».

## 3. 🟠 High — `suggestLinkTargets` квадратичен, тормозит на каждое нажатие клавиши

**[ПОДТВЕРЖДЕНО замерами]**

**Файлы:** [links.ts:159-176](ui/src/utils/links.ts#L159-L176) (`isPairLinked`),
[links.ts:183-207](ui/src/utils/links.ts#L183-L207) (`suggestLinkTargets`),
[CardLinks.tsx:83-86](ui/src/components/board/CardLinks.tsx#L83-L86)

`suggestLinkTargets` для **каждой** подошедшей по тексту карточки зовёт `isPairLinked`,
а та делает полный проход `Object.values(cards)` × все их `links`. На широком запросе
(«Task», «фикс», одна буква) это O(N²).

Вызов сидит в `useMemo` с зависимостью `[board.cards, cardId, query]`, то есть считается
**синхронно в фазе рендера на каждое нажатие клавиши** в поле подбора.

Замер (Node 22, чистые функции, без оверхеда React; скрипт — порт `links.ts` один-в-один):

| Карточек на доске | запрос «Task» (широкий) | запрос «number 12» (узкий) |
| --- | --- | --- |
| 200 | 2.9 ms | 0.17 ms |
| 1 000 | **65.0 ms** | 0.80 ms |
| 3 000 | **621.4 ms** | 23.5 ms |

Доска штатно вмещает `columnsPerBoard 12 × cardsPerColumn 200 = 2 400` живых карточек
плюс архив (архивные тоже сканируются внутри `isPairLinked`), так что правый столбец
таблицы — не гипотетика. 65 ms на нажатие — это уже заметный лаг ввода; 621 ms —
залипание.

**Фикс:** построить множество занятых пар один раз за прогон (тот же `cardLinkIndex`
уже знает `outgoing`/`incoming` — достаточно спросить у него `factsOf(cardId)` и собрать
`Set` соседей), вместо `isPairLinked` на каждого кандидата. Это снимает внутренний
проход и делает функцию линейной.

Для сравнения — `linkSignature` (тоже новый, зовётся на каждый рендер `DndBoard`)
замерен и **проблемой не является**: 0.047 / 0.103 / 0.275 ms на 200 / 1 000 / 3 000
карточек.

### ✅ Исправлено

`suggestLinkTargets` строит множество соседей одним проходом
(`linkedNeighbourIds` в `shared/src/store/card-links.ts`) и проверяет кандидата
за O(1). Функция стала линейной: два фиксированных прохода по доске вместо
одного прохода на кандидата.

Тест «stays linear in board size on a broad query» считает обращения к записи
карточек через `Proxy` и сравнивает рост при N=100 и N=200. Он проверен на
откат: со старой реализацией падает (**40 000** чтений против **~400**), с
новой проходит. Замер счётчиком, а не таймером — иначе тест был бы
флаки-зависим от машины.

## 4. 🟡 Medium — `position` у связей дублируется после удаления

**[ПОДТВЕРЖДЕНО e2e-PoC]**

**Файл:** [command-writers.ts:715-718](backend/src/commands/command-writers.ts#L715-L718)

Writer берёт `position` как индекс строки в массиве `after.cards[cardId].links`, а
`REMOVE_CARD_LINK` оставшиеся строки не перенумеровывает. Отсюда коллизии:

PoC: `ADD L1` (pos 0) → `ADD L2` (pos 1) → `REMOVE L1` → `ADD L3`. Строки в БД:

```json
[{"id":"L2","position":1},{"id":"L3","position":1}]
```

`loadBoardAggregate` сортирует связи по `orderBy: { position: "asc" }`, поэтому порядок
`L2`/`L3` в агрегате не определён, а у клиента редьюсер держит `[L2, L3]`. Расхождение
порядка client/server в `card.links` переживает refetch и ломает предпосылку
байт-эквивалентности агрегатов, на которой построены `walk`-тесты.

Дополнительно: `board-import.ts` нумерует `linkPosition` **сквозным счётчиком по всей
доске**, а writer — **поиндексно внутри карточки**. Одна колонка, две несовместимые
семантики.

**Фикс:** перенумеровывать живые строки карточки при каждой записи, либо сортировать в
агрегате по `(position, createdAt, id)` для детерминизма.

### ✅ Исправлено

Сделано и то, и другое:

* новый `writeLinkPositions(tx, boardId, card)` переписывает позиции всего
  (короткого — не больше `LIMITS.linksPerCard`) списка карточки при каждом
  add и remove, так что порядок в БД всегда равен порядку редьюсера;
* агрегат сортирует по `[{ position }, { id }]` — детерминизм даже при
  теоретической ничьей;
* `board-import.ts` нумерует связи **внутри карточки**, а не сквозным
  счётчиком: одна семантика колонки вместо двух. Заодно вставка идёт одним
  `createMany` вместо N круговых рейсов (находка 7.3).

Тест «renumbers positions so the aggregate reproduces the reducer»
воспроизводит сценарий PoC и требует `[{ln-2, 0}, {ln-3, 1}]`.

## 6. 🟡 Medium — доккомментарий про «честные» ответы не соответствует коду

**[ИЗ КОДА]** — [commands.service.ts:549-553](backend/src/commands/commands.service.ts#L549-L553)

```ts
// Guards that would make the command a silent no-op in the reducer
// are answered honestly: self-link, an already-linked pair or a
// `blocks` cycle are the client's bug; the row cap is a real limit.
…
if (!card || !target || card.id === target.id) return;   // ← 200 OK, тихий no-op
if (linkedPair) return;                                   // ← 200 OK, тихий no-op
```

Из трёх перечисленных «честно» отвечает только цикл (`reject()` кидает 409). Self-link и
дубль пары — обычный `return`, то есть ровно тот самый silent no-op, который комментарий
обещает не допускать.

> **Поправка к этому отчёту.** В первой редакции я дописал сюда, что клиент
> «применит оптимистичное изменение и увидит откат только на следующем
> refetch». Это неверно: клиент прогоняет **тот же** редьюсер перед отправкой,
> те же гварды срабатывают и у него, `after === before`, шаг в историю не
> пишется. Обе стороны no-op'ят одинаково, расхождения состояний нет.
> Находка остаётся — но она про неверный комментарий, а не про баг поведения,
> и это понижает её до косметической.

### ✅ Исправлено

Поведение не менялось — менялся комментарий, потому что неправдой был он.
Новый текст объясняет, **почему** три из четырёх гвардов отвечают 200: клиент
исполняет тот же редьюсер, обе стороны no-op'ят одинаково, и 409 превратил бы
безобидную гонку в тост с ошибкой. Лимит строк отличается принципиально —
пользователь обязан узнать, почему связь не появилась, поэтому он и остаётся

## Что в этом коммите сделано хорошо

Не для баланса, а потому что это реально влияет на оценку рисков:

* **Направленность связи и «одна строка на пару»** — модель выбрана правильно: строка
  живёт на источнике, пять вариантов Jira складываются в три типа (`LINK_TYPE_OPTIONS`
  с полем `holder`). Это честно снимает проблему двусторонней синхронизации.
* **Висячие связи как осознанный инвариант**, проведённый через редьюсер, `migrate`,
  `validate`, агрегат и import, с объяснением «why» в каждом месте. Находка №2 — это
  дыра в UI, а не в модели.
* **`cardLinkIndex` на `WeakMap` + `linkSignature`** для стабильности идентичности индекса —
  аккуратное решение задачи render-isolation, и замеры показывают, что цена сигнатуры
  действительно пренебрежима.
* **Undo/redo через upsert с оживлением soft-deleted строки** — правильное понимание
  того, что redo должен воскресить ту же строку, а не создать новую.
* **Тесты:** +190 строк в `board-reducer.test.ts`, +32 в `invert.test.ts`, +63 в
  `migrate.test.ts`, +128 в `links.test.ts`, e2e на walk и undo. Весь пакет зелёный
  (shared 353/353, ui 661/661, backend unit 57/57).

Слабое место покрытия — не количество тестов, а то, что **e2e на безопасность
(`command-ids.e2e-spec.ts`) перечисляет типы действий руками**. Новый тип действия
попадает туда только если автор вспомнит. Находка №1 прошла именно через эту щель.

Инструкции состоят из последовательных шагов с командами для копирования. Для
действий, меняющих данные или состояние сервера, указан способ отката.
Шаги с пометкой **Risky** могут уничтожить данные; сначала сделайте резервную
копию.

## Резервное копирование

Janosik не создаёт, не планирует и не проверяет серверные бэкапы. Экспорт доски
или аккаунта не включает файлы и не заменяет аварийную копию. Ниже используются
PostgreSQL из Compose и `/data/uploads`; для внешних сервисов адаптируйте
процедуру. Выполняйте команды в каталоге Compose на Linux. На время копирования
остановите **все** реплики приложения, workers и внешние записи: база и файлы
должны соответствовать одному моменту. Запишите версию образа и Compose.
До остановки завершите или зафиксируйте ожидающие задания. Эта процедура не
копирует очереди Redis: при несовпадении состояния очереди и базы задания могут
потеряться или выполниться повторно. Заранее определите восстановление очередей;
не подключайте восстановленную базу к работающему production Redis без проверки.

1. Остановите запись, сохраните базу и архив загрузок. Замените имена файлов
   уникальным идентификатором и храните пару вместе. Учётные данные берутся из
   работающего контейнера PostgreSQL.

   ```bash
   docker compose stop app
   docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > backup.sql
   docker run --rm --volumes-from "$(docker compose ps -aq app):ro" -v "$PWD:/out" \
     alpine tar czf /out/uploads.tar.gz -C /data/uploads .
   ```

   Проверяйте код завершения **каждой** команды; неполный файл при ошибке не
   является копией. Устраните ошибку до возобновления записи. Пример рассчитан
   на один контейнер app; при нескольких репликах отдельно определите и
   скопируйте общее хранилище загрузок.

2. Запустите приложение `docker compose start app` и проверьте
   `/api/v1/health/ready`. Сохраните пару вне хоста вместе с защищёнными
   копиями `.env` и Compose. Шифруйте их и ограничивайте доступ: база, файлы
   и конфигурация содержат чувствительные данные. Запишите время, версию, имена
   и результаты команд. Успешное архивирование ещё не проверка восстановления.

## Восстановление

**Опасно:** процедура заменяет целевую базу и все загрузки. Для PostgreSQL 16
из Compose используется суперпользователь, созданный образом. Для тренировки
не используйте production. Перед восстановлением production сделайте свежую
**пару** копий по инструкции выше и сохраните текущие образ, Compose и
конфигурацию для отката. Пересоздание базы удалит также объекты, отсутствующие
в дампе. Остановите все записи и другие подключения к базе.

1. Выберите `backup.sql` и `uploads.tar.gz` из одной пары. Проверьте архив
   командой `tar tzf uploads.tar.gz > /dev/null`. Используйте образ приложения
   и Compose той версии, что записана вместе с копией. Перед запуском workers
   проверьте очереди Redis и согласуйте ожидающие задания с планом восстановления.
2. Остановите все реплики и workers. Для одного контейнера:

   ```bash
   docker compose stop app
   ```

3. **Опасно:** пересоздайте настроенную базу и загрузите дамп. При ошибке база
   останется неполной: не запускайте приложение, устраните проблему или
   восстановите пару, сделанную перед операцией.

   ```bash
   docker compose exec -T postgres sh -c 'dropdb --if-exists --force -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
   docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backup.sql
   ```

4. **Опасно:** проверьте целевой том и архив, затем замените загрузки. Текущее
   содержимое будет удалено.

   ```bash
   docker run --rm --volumes-from "$(docker compose ps -aq app)" -v "$PWD:/out" alpine \
     sh -c 'find /data/uploads -mindepth 1 -delete && tar xzf /out/uploads.tar.gz -C /data/uploads'
   ```

   При ошибке распаковки не запускайте приложение; восстановите предыдущую пару.
5. Запустите соответствующую версию: `docker compose up -d app`. Проверьте
   readiness, журналы, вход, примеры досок и скачивание вложений. Для отмены
   неудачного восстановления повторите процедуру со свежей парой базы **и**
   загрузок и соответствующими образом и конфигурацией.

## Проверка восстановления

Используйте отдельный хост или изолированный проект Compose с собственными
базой, Redis, томом загрузок, портами и конфигурацией. Заблокируйте доступ к
production и исходящие письма, OAuth и другие интеграции: копия базы может
содержать рабочие секреты и задания. Не используйте production-тома и базу.
Подготовьте записанные версии образа и Compose и выполните восстановление
скопированной пары в изолированном стеке.

Запишите время копии, версию, ответственного, длительность и результат.
Проверьте readiness, вход, известные доски/карточки и несколько вложений и
аватаров; убедитесь, что в production не было записей и уведомлений. При ошибке
исправьте процесс копирования и повторите проверку. Защитите и удалите
изолированную копию согласно правилам хранения данных.

<a id="upgrade-rollback"></a>

## Откат обновления

До обновления сохраните согласованную пару копий, прежний тег образа, Compose
и конфигурацию. При сбое остановите все записи. Prisma применяет миграции при
старте только вперёд; старый образ может быть несовместим с обновлённой базой.
Восстановите **базу и загрузки до обновления вместе** по инструкции выше со
старым образом и Compose, проверьте readiness, доски и файлы, затем откройте
доступ. Записи после создания копии потеряются: сообщите точку восстановления и
при необходимости отдельно сохраните данные сбойного развёртывания для анализа.

## Обновление

Миграции выполняются автоматически при запуске контейнера приложения, поэтому
у обновления нет ручного шага миграции.

1. Прочитайте заметки к релизу и создайте резервные копии базы, загрузок и
   `.env`. Задайте нужную версию в `JANOSIK_TAG` в `.env`, например `v0.2.0`.
   Установщик фиксирует начальную версию, поэтому одной загрузки образа для
   обновления недостаточно. Скачайте и проверьте Compose из того же релиза,
   заменив `v0.2.0` в адресе на выбранную версию:

   ```bash
   curl -fsSL -o docker-compose.yml.new https://raw.githubusercontent.com/VitalyTolstik/janosik/v0.2.0/docker-compose.yml
   # Проверьте docker-compose.yml.new и замените им docker-compose.yml.
   ```

   Откат: измените значение или удалите строку.

2. Загрузите новый образ.

   ```bash
   docker compose pull
   ```

   Откат: нет. Этот шаг только загружает.

3. Пересоздайте стек.

   ```bash
   docker compose up -d
   ```

   Точка входа выполняет `npx prisma migrate deploy` перед запуском API.
   Первый запуск после обновления может идти дольше по двум причинам.
   Миграция, добавляющая индекс, строит его до старта API; например, индексы
   журнала команд по времени на большом журнале строятся дольше. А если том
   загрузок всё ещё принадлежит root (его создал старый образ, работавший от
   root), точка входа один раз передаёт его пользователю `node` через
   `chown -R`, что на большом томе занимает время.

   Индексы хранения (мягкое удаление, токены, общие доски, приглашения,
   напоминания) строятся так же. На bare-metal (`npm`) с большой базой
   постройте их без блокировки записи до обновления — тогда миграция их
   увидит и выполнится мгновенно:

   ```bash
   npm run db:indexes --workspace backend
   ```

   Откат: следуйте разделу [Откат обновления](#upgrade-rollback),
   восстановив пару базы и загрузок и предыдущие образ и Compose.

## Мониторинг

### Проверки работоспособности

`GET /api/v1/health` — проба **живости** (liveness): всегда отвечает `200` и не
трогает ни базу, ни Redis, поэтому на неё можно вешать перезапуск процесса.

`GET /api/v1/health/ready` — проба **готовности** (readiness): проверяет базу (и
Redis, если он настроен) и отвечает `503`, когда зависимость недоступна.
Результат кэшируется на пару секунд, поэтому опрос проб не усиливает нагрузку на
пул соединений. Обе пробы освобождены от глобального ограничения частоты.

```bash
curl -fsS http://localhost:3000/api/v1/health/ready
```

Ответ содержит три поля:

| Поле | Значения |
| --- | --- |
| `status` | `ok` или `error` |
| `db` | `up` или `down` |
| `redis` | `up`, `down` или `disabled` |

Здоровый экземпляр отвечает `200` с `{"status":"ok","db":"up","redis":"up"}`.
`redis` равен `disabled`, когда `REDIS_URL` не задан. Если проверка базы данных
неуспешна, сервер возвращает `503` с
`{"status":"error","db":"down","redis":"..."}`.
Настроенный, но недоступный Redis также отвечает `503` с
`{"status":"error","db":"up","redis":"down"}`. [Справочник API](/ru/docs/api/)
документирует ту же форму.

### Страница наблюдаемости в панели мастера

В панели мастера есть страница наблюдаемости по `/admin/observability`. Она
загружает один снимок только для чтения:

| Поле | Значение |
| --- | --- |
| `version` | версия пакета backend |
| `nodeEnv` | `NODE_ENV` |
| `uptimeSec` | время работы процесса в секундах |
| `deploy.startedAt` | время запуска процесса |
| `deploy.commit` | коммит сборки или `null` |
| `database.sizePretty` | размер базы данных |
| `database.tables` | двенадцать самых больших таблиц с числом строк и размерами |
| `jobs.transcode` | транскодирования: в ожидании, завершено, с ошибкой |
| `jobs.demo` | состояние демо-доски и её id |
| `jobs.realtime` | активные каналы досок и подключённые клиенты |
| `jobs.queues` | счётчики по каждой очереди: в ожидании, обработано, с ошибкой, с указанием бэкенда (`redis` или `memory`) |
| `health` | проверки базы данных, реального времени и режима обслуживания |

Если подсистема недоступна, вместо её данных показывается соответствующее состояние.

### Журналы

```bash
docker compose logs -f app        # follow
docker compose logs --tail=200 app
```

## Масштабирование

Один небольшой хост обслуживает обычную команду. По мере роста важны две настройки,
у обеих безопасные значения по умолчанию:

- **Живые потоки.** Каждая открытая доска (и публичная общая ссылка) держит одно
  SSE-соединение (~0.1–0.17 МБ). Сверх лимита инстанс отказывает новым потокам
  `503` + `Retry-After` вместо исчерпания памяти и раз в минуту пишет в журнал
  число живых соединений. Настраивается `SSE_MAX_CONNECTIONS` (на инстанс, по
  умолчанию `5000`), `SSE_MAX_PER_USER` (`32`) и `SSE_MAX_PER_BOARD` (`0` = без
  ограничения). `0` означает «без ограничения».
- **Куча.** `NODE_OPTIONS=--max-old-space-size=…` (по умолчанию `1024`)
  ограничивает old space V8, чтобы всплеск вызывал GC, а не OOM-киллер контейнера.

**Несколько нод.** При настроенном Redis рассылка по доске уже кросс-нодовая, а
воркеры очередей распределяются по репликам, поэтому можно запускать несколько
реплик API за балансировщиком: уберите `ports:` у сервиса `app` и пусть
балансировщик подключается к репликам по сети контейнеров, задайте `TRUST_PROXY=1`.
Держите `DB_CONNECTION_LIMIT` × реплики ниже `POSTGRES_MAX_CONNECTIONS`.
Список участников онлайн хранится на каждом узле отдельно, поэтому может
различаться между узлами. Для небольшой команды обычно достаточно одного узла.

## Устранение неполадок

**Контейнер приложения перезапускается в цикле, а в журналах упоминается
`Refusing to start`.** `PUBLIC_ORIGIN` — это URL со схемой `http://`, тогда как
`COOKIE_SECURE` включён или не задан. Либо отдавайте приложение по HTTPS, либо
только для пробного запуска в локальной сети задайте `COOKIE_SECURE=false` и
перезапустите. Сервер выводит полное сообщение:
`Refusing to start: NODE_ENV=production but PUBLIC_ORIGIN is not HTTPS (...)`.

**Вход работает, но примерно через 15 минут вас выбрасывает на экран входа.**
Refresh-cookie отбрасывается. Почти всегда приложение доступно по HTTP, тогда
как `COOKIE_SECURE=true`, либо прокси не передаёт `X-Forwarded-Proto`.
Исправьте настройку TLS или прокси, а не снижайте `COOKIE_SECURE`.

**Правки в реальном времени не появляются в другом браузере.** Прокси
буферизует поток SSE. Убедитесь, что он пересылает на `127.0.0.1:3000` (API
отправляет `X-Accel-Buffering: no`), а для nginx добавьте
`proxy_buffering off`.

**Ограничения частоты или журнал аудита показывают IP прокси.** Задайте
`TRUST_PROXY=1` и убедитесь, что прокси передаёт `X-Forwarded-For`.

**Письма никогда не приходят.** Без `SMTP_HOST` приложение по замыслу работает
в режиме логирования. Проверьте `docker compose logs app` или настройте
**Email service** в панели мастера.

**`docker compose up` завершается с ошибкой `set JWT_SECRET`.** `.env`
отсутствует или пуст. Скопируйте `.env.example` в `.env` и заполните его.

**Контейнер приложения сразу завершается, а в журналах написано
`POSTGRES_PASSWORD is still the example value 'change-me'`.** Задайте в `.env`
настоящий пароль (например, `openssl rand -hex 24`). На существующей
установке у базы уже старый пароль, поэтому сначала смените его в
PostgreSQL, затем обновите `.env` и выполните `docker compose up -d`:

```bash
docker compose exec postgres psql -U janosik -c "ALTER USER janosik WITH PASSWORD '<новый пароль>'"
```

Замените `janosik` на ваш `POSTGRES_USER`, если он другой.

**Вложения или импорт досок падают с `413` за nginx.** По умолчанию nginx
отклоняет тела больше 1 МБ. Добавьте `client_max_body_size 30m;` в блок
server (см. [Установка на своём сервере](../self-hosting/#поставьте-tls-впереди)) и
перезагрузите nginx.

**После пересборки фронтенда из исходников консоль браузера сообщает о
заблокированном встроенном скрипте.** API разрешает встроенные скрипты по
хешам, вычисленным при запуске. Перезапускайте API после каждой пересборки
фронтенда. Образ контейнера делает это при каждом деплое.

**Вход отвечает «Too many failed sign-in attempts».** Адрес попал в задержку
входа после пяти или более неверных паролей. Подождите указанное время (не
больше 15 минут); блокировка снимается при следующем успешном входе.

## Чек-лист безопасности

- [ ] Приложение отдаётся по HTTPS, с `COOKIE_SECURE=true`.
- [ ] Надёжные, уникальные `JWT_SECRET` и `POSTGRES_PASSWORD` (никогда не
      `change-me` из примера, с которым контейнер не запускается).
- [ ] `ALLOW_REGISTRATION=false`, когда ваша учётная запись создана.
- [ ] Впереди обратный прокси, `TRUST_PROXY=1`.
- [ ] Открыты только `80` и `443`; база данных и Redis остаются внутренними.
- [ ] Регулярные резервные копии `pg_dump` и загрузок, плюс периодическая
  проверка восстановления.
- [ ] `docker compose pull && docker compose up -d` применяется для исправлений
  безопасности.

См. [Безопасность](/ru/docs/security/) об элементах защиты, реализованных на сервере.
Сообщайте об уязвимостях приватно, никогда в публичном issue.

Каждый runbook это нумерованный список. Каждый шаг это одно действие, и его
можно скопировать и вставить. Шаги, меняющие состояние, называют свой откат.
Шаги с пометкой **Risky** могут уничтожить данные; сначала сделайте резервную
копию.

## Резервное копирование

Копируйте и базу данных, и том загрузок. Ни один шаг не меняет состояние.

1. Сохраните дамп базы данных в файл с датой в текущем каталоге.

   ```bash
   docker compose exec postgres pg_dump -U janosik janosik > backup-$(date +%F).sql
   ```

   Откат: нет. Этот шаг только читает.

2. Заархивируйте том загрузок (вложения и аватары).

   ```bash
   docker run --rm \
     -v janosik_janosik-uploads:/data \
     -v "$PWD:/out" \
     alpine tar czf /out/uploads-$(date +%F).tar.gz -C /data .
   ```

   Имя тома имеет префикс проекта Compose, обычно это имя каталога. Проверьте
   реальное имя командой `docker volume ls`. Откат: нет. Этот шаг только
   читает.

3. Скопируйте оба файла с хоста.

## Восстановление

**Risky.** Восстановление перезаписывает живые данные. Сделайте свежую
резервную копию в шаге 1, чтобы можно было отменить весь runbook.

1. Сделайте свежую резервную копию текущей базы данных, прежде чем что-либо
   менять.

   ```bash
   docker compose exec postgres pg_dump -U janosik janosik > pre-restore-$(date +%F).sql
   ```

   Откат: нет. Этот шаг только читает.

2. Остановите приложение, чтобы оно не писало во время восстановления.

   ```bash
   docker compose stop app
   ```

   Откат: `docker compose start app`.

3. **Risky.** Восстановите базу данных. Это перезаписывает текущие данные.

   ```bash
   docker compose exec -T postgres psql -U janosik janosik < backup-2026-10-26.sql
   ```

   Откат: загрузите дамп из шага 1.

4. **Risky.** Восстановите том загрузок. Команда сначала удаляет текущее
   содержимое.

   ```bash
   docker run --rm -v janosik_janosik-uploads:/data -v "$PWD:/out" alpine \
     sh -c "rm -rf /data/* && tar xzf /out/uploads-2026-10-26.tar.gz -C /data"
   ```

   Откат: восстановите архив загрузок, снятый до этого runbook-а.

5. Запустите приложение снова.

   ```bash
   docker compose start app
   ```

   Откат: не нужен. Стек вернулся в обычное состояние.

## Обновление

Миграции выполняются автоматически при запуске контейнера приложения, поэтому
у обновления нет ручного шага миграции.

1. Зафиксируйте целевую версию (необязательно). Задайте `JANOSIK_TAG=v0.1.0` в
   `.env`.

   Откат: измените значение или удалите строку.

2. Загрузите новый образ.

   ```bash
   docker compose pull
   ```

   Откат: нет. Этот шаг только загружает.

3. Пересоздайте стек.

   ```bash
   docker compose up -d
   ```

   Точка входа выполняет `npx prisma migrate deploy` перед запуском API.

   Откат: верните `JANOSIK_TAG` к предыдущему тегу и выполните
   `docker compose up -d`. Миграции применяются только вперёд, поэтому если
   миграцию нельзя откатить, восстановите резервную копию базы данных,
   снятую до обновления (см. [Восстановление](#восстановление)).

## Мониторинг

### Эндпоинт здоровья

`GET /api/v1/health` это проба готовности. Он освобождён от глобального
ограничения частоты, поэтому оркестратор может опрашивать его свободно.

```bash
curl -fsS http://localhost:3000/api/v1/health
```

Ответ содержит три поля:

| Поле | Значения |
| --- | --- |
| `status` | `ok` или `error` |
| `db` | `up` или `down` |
| `redis` | `up`, `down` или `disabled` |

Здоровый экземпляр отвечает `200` с `{"status":"ok","db":"up","redis":"up"}`.
`redis` равен `disabled`, когда `REDIS_URL` не задан. Неудачный пинг базы
данных отвечает `503` с `{"status":"error","db":"down","redis":"..."}`.
Настроенный, но недоступный Redis также отвечает `503` с
`{"status":"error","db":"up","redis":"down"}`. [Справочник API](api/)
документирует ту же форму.

### Страница наблюдаемости в панели мастера

В панели мастера есть страница наблюдаемости по `/admin/observability`. Она
загружает один снимок только для чтения:

| Поле | Значение |
| --- | --- |
| `version` | версия пакета backend |
| `nodeEnv` | `NODE_ENV` |
| `uptimeSec` | время работы процесса в секундах |
| `deploy.startedAt` | время запуска процесса |
| `deploy.commit` | коммит сборки или `null` |
| `database.sizePretty` | размер базы данных |
| `database.tables` | двенадцать самых больших таблиц с числом строк и размерами |
| `jobs.transcode` | транскодирования: в ожидании, завершено, с ошибкой |
| `jobs.demo` | состояние демо-доски и её id |
| `jobs.realtime` | активные каналы досок и подключённые клиенты |
| `jobs.queues` | счётчики по каждой очереди: в ожидании, обработано, с ошибкой, с указанием бэкенда (`redis` или `memory`) |
| `health` | проверки базы данных, реального времени и режима обслуживания |

Каждое поле корректно деградирует, когда подсистема недоступна.

### Журналы

```bash
docker compose logs -f app        # follow
docker compose logs --tail=200 app
```

## Устранение неполадок

**Контейнер приложения перезапускается в цикле, а в журналах упоминается
`Refusing to start`.** `PUBLIC_ORIGIN` это URL со схемой `http://`, тогда как
`COOKIE_SECURE` включён или не задан. Либо отдавайте приложение по HTTPS, либо
только для пробного запуска в локальной сети задайте `COOKIE_SECURE=false` и
перезапустите. Сервер выводит полное сообщение:
`Refusing to start: NODE_ENV=production but PUBLIC_ORIGIN is not HTTPS (...)`.

**Вход работает, но примерно через 15 минут вас выбрасывает на экран входа.**
Refresh-cookie отбрасывается. Почти всегда приложение доступно по HTTP, тогда
как `COOKIE_SECURE=true`, либо прокси не передаёт `X-Forwarded-Proto`.
Исправьте настройку TLS или прокси, а не снижайте `COOKIE_SECURE`.

**Правки в реальном времени не появляются в другом браузере.** Прокси
буферизует поток SSE. Убедитесь, что он пересылает на `127.0.0.1:3000` (API
отправляет `X-Accel-Buffering: no`), а для nginx добавьте
`proxy_buffering off`.

**Ограничения частоты или журнал аудита показывают IP прокси.** Задайте
`TRUST_PROXY=1` и убедитесь, что прокси передаёт `X-Forwarded-For`.

**Письма никогда не приходят.** Без `SMTP_HOST` приложение по замыслу работает
в режиме логирования. Проверьте `docker compose logs app` или настройте
**Email service** в панели мастера.

**`docker compose up` завершается с ошибкой `set JWT_SECRET`.** `.env`
отсутствует или пуст. Скопируйте `.env.example` в `.env` и заполните его.

## Чек-лист безопасности

- [ ] Приложение отдаётся по HTTPS, с `COOKIE_SECURE=true`.
- [ ] Надёжные, уникальные `JWT_SECRET` и `POSTGRES_PASSWORD`.
- [ ] `ALLOW_REGISTRATION=false`, когда ваша учётная запись создана.
- [ ] Впереди обратный прокси, `TRUST_PROXY=1`.
- [ ] Открыты только `80` и `443`; база данных и Redis остаются внутренними.
- [ ] Регулярные резервные копии `pg_dump` и загрузок, плюс периодическая
  проверка восстановления.
- [ ] `docker compose pull && docker compose up -d` применяется для исправлений
  безопасности.

См. [Безопасность](security/) об элементах защиты, реализованных на сервере.
Сообщайте об уязвимостях приватно, никогда в публичном issue.

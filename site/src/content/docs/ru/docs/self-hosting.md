Образ для self-hosting обслуживает весь продукт на одном origin: API по
`/api/v1`, приложение (React SPA) по `/app/` и маркетинговый сайт по `/`.
Отдельный веб-сервер не нужен, а SSE и cookie работают на одном origin.

## Что запускает стек

`docker compose up -d` по умолчанию запускает три контейнера:

- **`app`** — сайт, приложение, API, панель мастера и фоновые задачи.
  Слушает порт `3000`. Образ — `ghcr.io/vitalytolstik/janosik`; версия
  задаётся через `JANOSIK_TAG`, по умолчанию это `latest`.
- **`postgres`** — база данных `postgres:16-alpine` для досок, пользователей,
  команд и журнала аудита.
- **`redis`** — сервис `redis:7-alpine` для фоновых задач, включая почту,
  транскодирование, обслуживание и экспорт.

Четвёртый, необязательный сервис **`mcp`** (образ
`ghcr.io/vitalytolstik/janosik-mcp`) запускает общий MCP Streamable HTTP шлюз
для многих агентов с профилем `--profile mcp`. Он слушает порт `8080`, по
умолчанию привязан к `127.0.0.1` и хранит сессии в памяти. См.
[Подключение MCP](#подключение-mcp).

`postgres` и `redis` остаются внутренними. Порт приложения публикуется по
умолчанию; необязательный шлюз публикует только `127.0.0.1:8080`. При запуске
контейнер `app` применяет миграции базы данных, затем запускает API.

Это вся установка для одного хоста. Чтобы запустить 2–4 реплики API за
встроенным прокси nginx/Caddy, см. раздел *Горизонтальное масштабирование*
ниже; быстрый запуск с одним контейнером не меняется.

Контейнер стартует от root только для того, чтобы передать том загрузок
непривилегированному пользователю `node` (тома, созданные старыми образами,
принадлежат root), а затем запускает миграции, API и ffmpeg от `node`. До
этого он проверяет две настройки: отказывается запускаться, пока
`POSTGRES_PASSWORD` равен значению `change-me` из примера, и выводит напоминание при
каждом запуске, пока `ALLOW_REGISTRATION=true`.

Образ задаёт `STATIC_DIR=/app/public`, `SITE_DIR=/app/site` и
`UI_BASE=/app/`. С этими значениями по умолчанию маркетинговый сайт находится
по `/`, а приложение по `/app/`, поэтому интерфейс доски доступен по
`PUBLIC_ORIGIN/app/`, а панель мастера по `PUBLIC_ORIGIN/app/admin`.

## Платформы и установка

Janosik открывается в браузере и требует работающего сервера. Используйте Docker
на Linux, macOS (Intel или Apple Silicon) либо Windows с Docker Desktop и WSL2.
Docker автоматически скачает подходящий Linux-образ `amd64` или `arm64`.
Архивы в GitHub Releases содержат исходный код; отдельных установщиков `.exe`
для Windows и `.dmg` для macOS пока нет.

Версия v0.2.0 проверена в WSL и в Linux CI на обеих архитектурах. Отдельной
проверки на физическом Mac пока не было. Установщик запускает приложение только
на этом компьютере; для доступа с других устройств см. инструкции для локальной
сети и HTTPS ниже.

## Требования

- Хост с Docker Engine 24 или новее и плагином Docker Compose v2.
- Свободный порт `3210` для установщика по умолчанию; примеры ручной настройки
  локальной сети используют порт `3000`. Для публичного сервера нужны порты
  `80` и `443` и обратный прокси.
- Доменное имя для HTTPS (необязательно для пробного запуска, требуется для
  реального использования).

Проверьте хост:

```bash
docker --version
docker compose version
```

Установка Docker на вашу машину описана ниже в разделе
[Установка Docker по операционным системам](#установка-docker-по-операционным-системам).

## Пробный запуск в локальной сети или на localhost

Подходит, чтобы попробовать. Не для публикации в интернете.

Для пробного запуска на Linux, macOS или Windows с WSL2 установите Docker,
Compose, curl и OpenSSL, затем выполните:

```bash
curl -fsSLO https://raw.githubusercontent.com/VitalyTolstik/janosik/main/install.sh && bash install.sh
```

Откройте `http://localhost:3210/app/`. Установщик создаст `janosik/.env` и
`janosik/docker-compose.yml`, сгенерирует уникальные секреты и откроет
приложение только на localhost. Он использует последний стабильный релиз GitHub
и соответствующий образ; оба должны быть опубликованы. Чтобы изменить папку или
порт, задайте `JANOSIK_INSTALL_DIR` или `JANOSIK_INSTALL_PORT` при запуске
`bash install.sh`. Существующие файлы установщик не перезаписывает. Если запуск
завершился с ошибкой, устраните её и выполните `docker compose up -d` в папке
установки.

Для локальной сети или ручной настройки:

```bash
mkdir janosik && cd janosik
curl -O https://raw.githubusercontent.com/VitalyTolstik/janosik/main/docker-compose.yml
curl -o .env https://raw.githubusercontent.com/VitalyTolstik/janosik/main/.env.example
```

Отредактируйте `.env`:

- `JWT_SECRET`: сгенерируйте командой `openssl rand -hex 32`.
- `POSTGRES_PASSWORD`: задайте надёжный пароль. С значением `change-me` из примера
  контейнер не запустится.
- `PUBLIC_ORIGIN=http://<host-ip>:3000` (или `http://localhost:3000`).
- Для пробного запуска по HTTP задайте `COOKIE_SECURE=false` (безопасное
  значение по умолчанию — `true`; по HTTP приложение откажется стартовать,
  чтобы не терять cookie молча).

```bash
docker compose up -d
```

Откройте `http://<host-ip>:3000/app/`. Так как это обычный HTTP, приложение
выводит громкое предупреждение о `COOKIE_SECURE=false`. Здесь это ожидаемо.

## Production с доменом и HTTPS

Отличие от пробного запуска в том, что вы перестаёте публиковать приложение
напрямую и позволяете прокси с завершением TLS пересылать запросы на
`localhost:3000`.

### Настройте `.env`

```
JWT_SECRET=<openssl rand -hex 32>
POSTGRES_USER=janosik
POSTGRES_PASSWORD=<strong password>
POSTGRES_DB=janosik
PUBLIC_ORIGIN=https://kanban.example.com
COOKIE_SECURE=true
TRUST_PROXY=1
APP_BIND_ADDRESS=127.0.0.1
ALLOW_REGISTRATION=true
```

`PUBLIC_ORIGIN` должен совпадать с URL, который реально открывают пользователи.
Значение задаёт canonical-адреса, адреса предпросмотра и sitemap встроенного
сайта, а также используется для URL обратного вызова OAuth и проверки Secure-cookie.
При переходе с пробной установки сохраните её секреты и `COMPOSE_PROJECT_NAME`.
Установщик задаёт `PORT=3210`: измените порт на `3000` для примеров ниже или
направьте прокси на `127.0.0.1:3210`.

### Запустите стек

```bash
docker compose up -d
```

Теперь приложение доступно на `localhost:3000`, только с самого хоста.

### Поставьте TLS впереди

**Caddy** автоматически получает сертификат Let's Encrypt:

```text
# /etc/caddy/Caddyfile
kanban.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

```bash
sudo systemctl reload caddy
```

**nginx** завершает TLS и проксирует всё на приложение. API отправляет
`X-Accel-Buffering: no`, но для realtime всё же нужны две настройки прокси:
отключить буферизацию и задать `proxy_read_timeout` больше 60-секундного
keep-alive PAT (`3600s` безопасно). Другой настройки не требуется. Поднимите
`client_max_body_size`: по умолчанию nginx
отклоняет тела больше 1 МБ, и вложения (до 25 МБ), импорт досок (25 МБ), тела
команд/планов (10 МБ) и большие команды (2 МБ) упали бы с `413`.

```nginx
server {
    listen 443 ssl;
    server_name kanban.example.com;

    # ssl_certificate     /etc/letsencrypt/live/kanban.example.com/fullchain.pem;
    # ssl_certificate_key /etc/letsencrypt/live/kanban.example.com/privkey.pem;

    client_max_body_size 30m;         # attachments, imports, commands

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;          # realtime (SSE)
        proxy_read_timeout 3600s;     # долгие потоки; больше 60-секундного keep-alive PAT
    }
}
```

**Traefik** работает так же: пересылайте на `127.0.0.1:3000`, передавайте
`X-Forwarded-For` и `X-Forwarded-Proto` и задайте `TRUST_PROXY=1`, чтобы
ограничения частоты и журнал аудита видели реальный IP клиента, а не IP
прокси. Минимальная конфигурация через file provider:

```yaml
# traefik dynamic configuration (file provider)
http:
  routers:
    janosik:
      rule: "Host(`kanban.example.com`)"
      entryPoints: [websecure]
      service: janosik
      tls:
        certResolver: letsencrypt
  services:
    janosik:
      loadBalancer:
        servers:
          - url: "http://127.0.0.1:3000"
```

### Брандмауэр

Открытыми должны быть только порты прокси (`80`, `443`). Порт приложения
`3000`, а также порты базы данных и Redis остаются внутренними.

## Горизонтальное масштабирование (2–4 реплики API)

Стандартный стек запускает один контейнер `app`. `docker-compose.scale.yml` —
необязательный overlay: 2–4 реплики API за nginx (по умолчанию) или Caddy и
одноразовая задача миграций. Быстрый запуск с одним контейнером не меняется.
Overlay и файлы `deploy/scale/` входят в исходники релизного тега; для
установки, созданной installer'ом, скопируйте их рядом с `docker-compose.yml`.
Если старый `.env` явно задаёт `TRUST_PROXY=0`, измените его на `1` (или
удалите строку) перед запуском реплик: явный 0 переопределяет default overlay
и ломает лимиты/аудит по реальному IP клиента.

```bash
# Сначала остановите одиночный app; именованные тома сохраняются.
docker compose down
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --wait
```

Топология:

```text
клиенты → proxy :3000 → app-1 / app-2 / app-N
                              ├── PostgreSQL (пул на реплику)
                              └── Redis (очереди, SSE, лимиты)
                         общий том загрузок
```

Прокси — единственный опубликованный сервис. Реплики используют внутренний
alias `app`, интерфейс и сайт уже в каждом образе, а вложения лежат на общем
томе `janosik-uploads`. Sticky-сессии не нужны: access-токены не хранят
состояние, а SSE-клиент переподключается с `?since=<lastSeq>` и может попасть
на другую реплику, не теряя журнал команд. Overlay задаёт `TRUST_PROXY=1` для
одного хопа; если впереди ещё и внешний TLS-прокси, задайте `TRUST_PROXY=2`,
чтобы лимиты и аудит видели реальный IP клиента. Конфиг nginx сохраняет
`X-Forwarded-Proto` внешнего прокси; для Caddy либо завершайте TLS в Caddy,
либо добавьте в `servers { trusted_proxies static … }` только точную подсеть
внешнего прокси.

Чтобы запустить Caddy вместо nginx, достаточно сменить образ (монтируются оба
конфига):

```bash
JANOSIK_PROXY_IMAGE=caddy:2-alpine \
  docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --wait
```

Caddy по умолчанию работает по HTTP на `PORT`. Чтобы завершать TLS в Caddy,
замените `:8080` в `deploy/scale/Caddyfile` на домен, уберите `auto_https off`,
смените маппинг портов прокси на `80:80` и `443:443` и оставьте
`PUBLIC_ORIGIN=https://…`.

Переопределить число реплик (по умолчанию 3) на один запуск:

```bash
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d \
  --scale app=4 --wait
```

### Sizing

Это отправные точки; подтверждайте их прогонами TASK-200.14.

| Хост | Реплики | На реплику (CPU / память) | Куча V8 | `DB_CONNECTION_LIMIT` | `SSE_MAX_CONNECTIONS` |
| --- | --- | --- | --- | --- | --- |
| 4 vCPU / 8 ГБ | 3 | 1.0 / 1536 МБ | 768 МБ | 10 (всего 30) | 2000 (всего 6000) |
| 16 vCPU / 32 ГБ | 4 | 3.0 / 5 ГБ | 3.5 ГБ | 15 (всего 60) | 5000 (всего 20000) |

Прокси входит в бюджет хоста: `PROXY_CPUS=0.5` / `PROXY_MEMORY_LIMIT=512M` на
4 vCPU/8 ГБ и `1.0` / `1G` на 16 vCPU/32 ГБ, `PROXY_NOFILE=131072`.
`deploy/scale/nginx-main.conf` поднимает nginx до `worker_connections 65536` и
`worker_rlimit_nofile 131072`; стандартных 1024 соединений мало для
документированных 6k/20k потоков. `PROXY_NOFILE` — лимит nofile контейнера;
держите его не меньше nginx `worker_rlimit_nofile` (на хосте с меньшим hard
limit снижайте оба). В production — 2–4 реплики; одна только для отката. Compose не проверяет диапазон `API_REPLICAS` (прямой `up` с 5 запустит
пять; `rollout.sh` отклонит), приоритет — shell env → `.env` → default 3.
Это отправные точки: живой горизонтальный прогон S2/S3 для этого
изменения не выполнялся; гейт ёмкости остаётся за TASK-200.14.

Держите `реплики × DB_CONNECTION_LIMIT + ~10 < POSTGRES_MAX_CONNECTIONS` с
запасом на миграции и admin CLI. На большом хосте увеличьте
`POSTGRES_SHARED_BUFFERS`, `POSTGRES_WORK_MEM` и `POSTGRES_MAX_CONNECTIONS`; после
примерно восьми реплик добавьте PgBouncer, а не повышайте `max_connections`.

Значения задаются в `.env`; overlay их читает:

```dotenv
API_REPLICAS=3
API_CPUS=1.0
API_MEMORY_LIMIT=1536M
API_NOFILE=65536
NODE_OPTIONS=--max-old-space-size=768
DB_CONNECTION_LIMIT=10
SSE_MAX_CONNECTIONS=2000
PROXY_CPUS=0.5
PROXY_MEMORY_LIMIT=512M
PROXY_NOFILE=131072
JANOSIK_PROXY_IMAGE=nginx:1.27-alpine
```

`ulimits.nofile` поднят до 65 536 на реплику. Куча V8 должна быть меньше
лимита памяти контейнера (оставьте 300–500 МБ для Node, Prisma и нативных
буферов).

### Общий Redis и лимиты

Compose уже задаёт `REDIS_URL`. С ним общими для всех реплик становятся
счётчики глобального throttler, значение лимита из панели мастера,
SSE-рассылка по доскам, инвалидация кэшей и задачи BullMQ. Одиночная установка
без Redis по-прежнему работает с внутрипроцессными лимитами и локальной
рассылкой; для нескольких реплик Redis обязателен. Если настроенный Redis
недоступен, readiness отвечает `503`, ограничитель переходит на счётчики
каждой реплики, а межреплиционная SSE-рассылка останавливается до восстановления.

Redis делает кластерными **не все** ограничители. В кластере общие: счётчики
глобального throttler на принципала и живые правки `THROTTLE_LIMIT`. Общие через
Redis, пока он доступен, с локальным fallback: login backoff. На реплику
(эффективный потолок N×): `BOARD_READ_CAP`, пер-пользовательский лимит из
панели, явные и стандартные лимиты API-токенов, агентские бюджеты TASK-200.3
(сессия/доска) и очередь команд доски, лимиты публичных share-токенов и OG,
SSE-лимиты instance/user/board (анонимные share-потоки ограничены на instance и
доску), presence и TTL-кэши (инвалидация между репликами, fallback по TTL).
Держите значения консервативными и полагайтесь на общий `THROTTLE_LIMIT` на
принципала как на основной предохранитель.

### Прокси, раскатка и откат

Конфиги лежат в `deploy/scale/nginx-main.conf`, `deploy/scale/nginx.conf` и
`deploy/scale/Caddyfile`. Главный конфиг nginx поднимает
`worker_connections` до 65 536 и `worker_rlimit_nofile` до 131 072 (стандартных
1024 мало для документированных потоков); оба прокси используют retry и
пассивную проверку отказов. SSE-маршруты — 3600 с на read/send, 3600 с
downstream `send_timeout` (дефолтные 60 с обрывали бы PAT-поток во время
0–6 с jitter keep-alive) и без буферизации; обычные API-запросы — 90 с
(с запасом на 60-секундный ready long-poll), загрузки/скачивания — длинный
таймаут с `client_body_timeout 3600s` для медленных тел. nginx кэширует
контентно-хэшированные `/_astro/` и `/app/assets/` на 7 дней; Caddy проксирует
статику без дополнительного кэша. `/healthz` на обоих проверяет readiness API.
Проверка без запуска stack/app-контейнеров (только временные контейнеры
проверки синтаксиса): `npm run deploy:test`. Живая проверка SSE
между репликами на Linux-хосте:
`JANOSIK_TOKEN=… JANOSIK_BOARD_ID=… node deploy/scale/smoke-sse.mjs`;
unit-smoke входит в обычный backend-набор.

```bash
COMPOSE="docker compose -f docker-compose.yml -f docker-compose.scale.yml"

# Та же последовательность есть в deploy/scale/rollout.sh.
$COMPOSE pull
$COMPOSE run --rm migrate                 # только если релиз меняет схему
$COMPOSE up -d --no-deps app --wait       # число реплик из API_REPLICAS/.env
$COMPOSE up -d --no-deps proxy --wait     # если образ/лимиты прокси изменились
$COMPOSE exec -T proxy nginx -s reload    # для Caddy: caddy reload
curl -fsS http://localhost:3000/api/v1/health/ready
```

Обычный Compose пересоздаёт сервис API целиком, поэтому возможен короткий
интервал без готовой реплики. Прокси повторяет запрос на другой upstream, SSE
переподключается с `?since=`; это не zero-downtime раскатка. Пересоздание самого
прокси (при смене образа/лимитов) тоже даёт короткий публичный простой. Если
потеря запросов недопустима, используйте Swarm или Kubernetes.
`deploy/scale/rollout.sh` выполняет ту же последовательность и никогда не
передаёт устаревший `--scale`.

Откат к **одной реплике за тем же прокси**:

```bash
$COMPOSE up -d --scale app=1 --wait
$COMPOSE exec -T proxy nginx -s reload
```

Откат к **установке с одним контейнером** (тома сохраняются):

```bash
$COMPOSE down
docker compose up -d --wait
```

При плохом образе задайте `JANOSIK_TAG` с предыдущей версией и повторите
`pull` + `up -d --wait`. Миграции выполняются только вперёд; для отката схемы
восстановите подходящую резервную копию.

**Ограничение нескольких хостов.** Реплики используют локальный Docker-том
`janosik-uploads`. Для реплик на разных хостах нужна общая POSIX-файловая
система для загрузок и общие Redis/Postgres; объектное хранилище не
реализовано. Healthcheck Compose — не активная проверка балансировщика:
нездоровая реплика продолжает получать трафик, пока её не уберут или не
перезагрузят прокси.

## Первый запуск

1. **Создайте мастер-аккаунт.** CLI создаёт отдельную учётную запись для
   панели мастера. Первый мастер получает роль `OWNER`.

   ```bash
   docker compose exec app node /app/backend/scripts/admin-cli.cjs create --email me@example.com
   # Enter the password twice at the hidden prompt.
   docker compose exec app node /app/backend/scripts/admin-cli.cjs list
   ```

   Войдите по адресу `PUBLIC_ORIGIN/app/admin`. Чтобы сменить пароль мастера и
   отозвать его сессии, выполните:

   ```bash
   docker compose exec app node /app/backend/scripts/admin-cli.cjs passwd --email me@example.com
   ```

2. **Создайте учётную запись для досок.** При настройках Compose по умолчанию
   и без SMTP самостоятельная регистрация с паролем недоступна. В панели
   мастера выберите **Пользователи → Создать пользователя**, откройте его
   карточку и выберите **Подтвердить email** для адреса, к которому у вас
   есть доступ. Войдите по адресу `PUBLIC_ORIGIN/app/` с паролем пользователя.

   - Для самостоятельной регистрации настройте SMTP в **Настройки → Почта**
     (`/app/admin/settings?tab=email`) и оставьте регистрацию открытой.
     Нажмите **Создать аккаунт** на `PUBLIC_ORIGIN/app/` и подтвердите почту.
   - Локальный установщик включает `ALLOW_BOOTSTRAP_USER=true` и открывает
     регистрацию. Если база данных пуста, кнопка **Создать аккаунт** позволит
     создать и подтвердить одну учётную запись без SMTP. После этого задайте
     `ALLOW_BOOTSTRAP_USER=false` в `.env`.

3. **Закройте регистрацию для частной установки.** Задайте
   `ALLOW_REGISTRATION=false` в `.env` и выполните `docker compose up -d`.
   Значение, сохранённое в **Настройки → Общие → Флаги функций → Открытая
   регистрация**, имеет приоритет. Проверьте, что `/api/v1/auth/config`
   возвращает `allowRegistration: false`.

CLI принимает три команды: `create`, `passwd` и `list`. Длина пароля — от 8 до
100 символов. Пароль никогда не передаётся в командной строке. Интерактивный
запуск
запрашивает пароль дважды скрытым вводом; неинтерактивный читает переменную
окружения `ADMIN_PASSWORD`.

### Подключение MCP

Стек Compose уже предоставляет API для MCP. Создайте персональный ключ в
**Account → API keys**, затем настройте MCP-клиент на машине агента по
[инструкции MCP](/ru/docs/mcp/). Для локального запуска укажите
`JANOSIK_URL=http://localhost:3210` и `JANOSIK_APP_BASE=/app`. Для процесса MCP
нужны Node.js и доступ к этому адресу; на другой машине или в контейнере вместо
`localhost` используйте доступный HTTPS-адрес.

Для многих агентов запускайте общий шлюз вместо отдельного stdio-процесса на
каждого: `docker compose --profile mcp up -d`, затем настройте клиентов на
`https://your-gateway/mcp` со своим заголовком `Authorization: Bearer jnk_…`.
Шлюз сначала проверяет локальный допуск (глобальный лимит и лимит на ключ — по
умолчанию 50 — плюс бакеты initialize на IP/токен и negative cache), затем
проверяет ключ через API. Сессии хранятся **в памяти**: перезапуск их удаляет,
а несколько реплик требуют session-affine proxy (или клиенты должны
переподключаться). Успешные MCP POST — SSE-потоки, ошибки шлюза — JSON,
поэтому отключите буферизацию прокси и задайте read timeout больше самого
долгого вызова. По умолчанию — 500 сессий, лимит памяти 2 ГБ и 2 CPU. В
Compose задан `stop_grace_period: 20s`; для обычного Docker используйте
`--stop-timeout 20`, чтобы 10-секундный drain успел завершиться. Для большого
первого роя поднимите `THROTTLE_LIMIT` API и
`JANOSIK_MCP_HTTP_INIT_RATE_LIMIT`; см.
[инструкцию MCP](/ru/docs/mcp/#общий-http-шлюз-для-многих-агентов).

## Почта (необязательно)

Без SMTP почта не отправляется, а регистрация с паролем недоступна — кроме одноразового первого аккаунта при `ALLOW_BOOTSTRAP_USER`. Настройте почту до открытия регистрации. Аккаунты, ранее созданные с автоматическим подтверждением, требуют проверки оператором. Чтобы привязать OAuth к существующему аккаунту с паролем, войдите в него и откройте «Аккаунт → Безопасность»; адрес у провайдера должен совпадать.
В production-логе содержание сообщений и коды не записываются.

Чтобы отправлять реальную почту, откройте панель мастера, перейдите в
**Email service**, выберите шаблон (Gmail, Yandex, Mail.ru, Brevo, SendGrid
или свой SMTP), вставьте учётные данные и включите доставку. Для Gmail,
Yandex и Mail.ru нужен пароль приложения при включённой двухэтапной
аутентификации, а не пароль от входа.

## Справочник переменных окружения

Каждая переменная проверяется при запуске в `backend/src/config/env.ts`.
Стек compose заполняет нужные из них из `.env`.

| Переменная | Значение по умолчанию | Примечания |
| --- | --- | --- |
| `NODE_ENV` | `development` | Одно из `development`, `test`, `production`. Образ задаёт `production`. |
| `PORT` | `3000` | HTTP-порт, который слушает API. Контейнер всегда слушает `3000`; compose публикует его. |
| `DATABASE_URL` | нет (обязательна) | Строка подключения к PostgreSQL для Prisma. Compose строит её из `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB`. |
| `TEST_DATABASE_URL` | пусто | Используется вместо `DATABASE_URL`, когда `NODE_ENV=test`, чтобы e2e никогда не трогал базу разработки. |
| `JWT_SECRET` | нет (обязательна) | Подписывает access-токены. Не менее 32 символов. Генерируйте через `openssl rand -hex 32`. |
| `ACCESS_TOKEN_TTL` | `15m` | Время жизни access-токена, строка длительности vercel/ms. |
| `REFRESH_TOKEN_TTL_DAYS` | `30` | Время жизни refresh-токена в днях. |
| `THROTTLE_LIMIT` | `300` | Глобальное ограничение API, запросов в минуту на субъекта: пользователя, API-ключ или IP для анонимных вызовов. |
| `AGENT_SESSION_RATE_LIMIT` | `0` (авто) | Взвешенных единиц в минуту на агентскую сессию (batch списывает число команд). `0` = `max(600, THROTTLE_LIMIT)`; иначе не менее `100`. |
| `AGENT_TOKEN_RATE_LIMIT` | `0` (авто) | Взвешенных единиц в минуту на API-ключ агента. `0` = `max(600, ceil(THROTTLE_LIMIT / 4))`; явный `rateLimitPerMinute` токена ограничен этой долей. Закреплённые значения — не менее `100`. |
| `BOARD_RATE_LIMIT` | `0` (авто) | Предохранительный потолок на доску, взвешенных единиц в минуту для всех агентов доски. `0` = `max(12000, 2 × THROTTLE_LIMIT)`. Увеличьте для крупного роя; справедливость дают бюджеты токена и сессии. Закреплённые значения — не менее `100`. |
| `AGENT_COMMAND_QUEUE_MS` | `1500` | Сколько команда сверх потолка доски ждёт токенов/места в очереди, прежде чем получить `503` + `Retry-After`; `X-RateLimit-Queued-Ms` показывает полное ожидание (`0`, если предел 64 ожидающих запросов/batch и 32 МиБ сериализованного JSON отклонил сразу). Максимум `30000`. `0` — отвечать сразу. |
| `BOARD_READ_CAP` / `BOARD_READ_QUEUE_MAX` | `16` / `256` | Сколько полных сборок `GET /boards/:id` выполняется одновременно **на процесс API** / сколько ждут слота. Одинаковые конкурентные чтения сначала объединяются; конкурируют только разные board/role/projection/кодировки. При N репликах предел кластера — N × это значение. Cap может быть больше `DB_CONNECTION_LIMIT` (по умолчанию 10): лишние сборки ждут в pool Prisma до `BOARD_READ_WAIT_MS`, затем `503 board_read_busy`. Задайте cap ≤ pool, чтобы избежать ожидания pool. |
| `BOARD_READ_WAIT_MS` / `BOARD_READ_TIMEOUT_MS` | `10000` / `20000` | Максимальное ожидание semaphore/pool / **один общий deadline ответа** (stamp + wait + build + encode) до `503 board_read_busy`/`board_read_timeout`. Таймаут должен быть больше ожидания и не меньше `300` мс. Каждая стадия получает только остаток бюджета, поэтому conditional miss не складывает WAIT+TIMEOUT. `WAIT_MS=0` отключает очередь semaphore и pool wait, но stamp и транзакция используют общий deadline. Read-транзакция получает `timeout` = остаток минус encode-margin и `maxWait=min(WAIT_MS,budget)` при `WAIT_MS>0` (`WAIT_MS=0` => 0), с зарезервированным transaction slice, чтобы `maxWait+timeout` не превышал deadline; P2010/57014, P2024/P2028 становятся 503, а не 500. Уже отправленный запрос не отменяется, но истекает по этому budget. |
| `BOARD_READ_RETRY_AFTER_SECONDS` | `2` | `Retry-After`, который отдаётся при отказе полного чтения доски. |
| `BOARD_READ_COMPRESS_MIN_BYTES` | `1024` | Тела меньше этого размера не сжимаются в `GET /boards/:id`; большие проходят согласование gzip/Brotli и всегда отправляют `Vary: Accept-Encoding`. |
| `TRUST_PROXY` | `0` (не задан в `.env.example`) | Число доверенных хопов обратного прокси. Задайте `1` за одним прокси; scale-overlay по умолчанию даёт `1`, если значение не задано. `2` — если впереди ещё внешний TLS-прокси. |
| `UPLOAD_DIR` | пусто | Корень блобов для вложений и аватаров. Пусто означает `backend/data/uploads`; относительное значение привязывается к пакету backend, а не к рабочему каталогу процесса. |
| `STATIC_DIR` | пусто | Каталог собранного интерфейса. Пусто означает только API. Образ задаёт `/app/public`. Встроенные скрипты отсюда разрешены хешами CSP, вычисленными при запуске, поэтому после пересборки интерфейса перезапустите API. |
| `SITE_DIR` | пусто | Каталог собранного маркетингового сайта, отдаваемый по `/`. Пусто означает, что он не отдаётся. Образ задаёт `/app/site`. |
| `UI_BASE` | `/` | Подпуть, по которому отдаётся приложение, используется для редиректов OAuth. Образ задаёт `/app/`. |
| `ALLOW_PUBLIC_SHARES` | `true` | Главный переключатель публичных ссылок для чтения. `false` также запрещает создание новых ссылок (и скрывает диалог «Поделиться»), а не только их открытие; публичный контур отвечает `404`. |
| `ALLOW_REGISTRATION` | `true` | Разрешает регистрацию с паролем при наличии SMTP или одноразового bootstrap. Для закрытого инстанса задайте `false`. Пока значение `true`, контейнер выводит предупреждение при запуске. |
| `ALLOW_BOOTSTRAP_USER` | `false` | Одноразовый bootstrap без SMTP: разрешает ровно первый аккаунт и сразу подтверждает его. Неактивен, когда пользователь уже есть; после настройки задайте `false`. Локальный installer включает его. |
| `COOKIE_SECURE` | `true` (в compose) | Принудительно задаёт атрибут `Secure` у cookie. Держите `true` за HTTPS; для пробного HTTP-запуска задайте `false` (иначе приложение откажется стартовать). Пусто = авто: включено в production. Допустимые значения: пусто, `true`, `false`. |
| `PURGE_AFTER_DAYS` | `30` | Удаляет мягко удалённые строки старше стольких дней. Используется, когда в панели нет настройки хранения. |
| `UNVERIFIED_ACCOUNT_TTL_DAYS` | `14` | Освобождает уникальный e-mail заброшенной неподтверждённой регистрации через столько дней. Аккаунты, принявшие членство в доске или создавшие контент, пропускаются. |
| `MAX_BOARDS_PER_USER` | `0` | Лимит досок на аккаунт в серверном режиме. `0` = без лимита (продуктовый дефолт); положительное значение — предохранитель оператора. Локальный/офлайн режим сохраняет собственный лимит в 10 досок в localStorage. |
| `AUDIT_RETENTION_DAYS` | `365` | Удаляет строки журнала аудита мастер-панели старше стольких дней (для подотчётности окно длиннее). |
| `DB_CONNECTION_LIMIT` | `10` | Размер пула Prisma на процесс API. Произведение числа реплик и этого лимита должно быть меньше `POSTGRES_MAX_CONNECTIONS`. |
| `SLOW_QUERY_MS` | `200` | Запросы Prisma, выполняющиеся не менее указанного времени, логируются вместе с id запроса. `0` — выключено. |
| `NODE_OPTIONS` | `--max-old-space-size=1024` | Потолок кучи Node для процесса API. Ограничивает память, чтобы всплеск живых потоков вызывал GC, а не OOM-киллер контейнера. Увеличьте на сервере с большим объёмом памяти. |
| `SHARE_AGGREGATE_CACHE_MS` | `2000` | Окно кэша агрегатов живых досок. Каждый процесс хранит до 64 агрегатов и при заполнении вытесняет тот, который дольше всего не использовался. Расход памяти зависит от размера досок. Изменение `seq` сбрасывает запись. `0` отключает хранение. Каждый процесс одновременно пересобирает до 64 разных досок. Запрос на новую пересборку сверх лимита возвращает `503`. |
| `ADMIN_METRICS_CACHE_MS` | `5000` | Окно кэша `/api/v1/admin/metrics` в мастер-панели (сбрасывается при любом действии модерации). `0` — выключено. |

| `MEMBERSHIP_CACHE_TTL_MS` | `30000` | Кэш членства `(пользователь, доска)` для чтения и SSE keep-alive. Записи/SSE его обходят; смена роли/удаление сбрасывают его. `0` — выключено. Ограничен `MEMBERSHIP_CACHE_MAX_ENTRIES` (`10000`). |
| `FEATURE_FLAG_CACHE_MS` | `30000` | Кэш строки флага; изменение флага сбрасывает его на всех узлах. `0` — выключено. Ограничен `FEATURE_FLAG_CACHE_MAX_ENTRIES` (`64`). |
| `BOARD_AGGREGATE_CACHE_ENTRIES` / `BOARD_AGGREGATE_CACHE_BYTES` | `32` / `33554432` (32 МиБ) | Кэш полного агрегата доски на процесс для команд, планов, approvals и legacy `GET /boards/:id`. LRU по числу записей и приблизительному размеру UTF-8 JSON (+256 Б на запись), поэтому предел — около 32 МиБ на реплику; запись также платит один `JSON.stringify` + `structuredClone`, попадание возвращает клон (временно, на запрос). Кэш наполняется закоммиченной командой и промахом внутри REPEATABLE READ снимка (legacy-чтение доски и загрузчики планов/approvals); обычный промах чтения его не заполняет. Доска больше байтового бюджета не кэшируется. `0` в любом из параметров выключает кэш и возвращает путь без кэша. |
| `POSTGRES_SHARED_BUFFERS` | `256MB` | `shared_buffers` встроенного контейнера Postgres. |
| `POSTGRES_WORK_MEM` | `8MB` | `work_mem` встроенного контейнера Postgres. |
| `POSTGRES_MAX_CONNECTIONS` | `100` | `max_connections` встроенного контейнера Postgres. |
| `SHARE_RATE_LIMIT` | `240` | Запросы к публичной общей доске в минуту, на токен. |
| `SHARE_OG_RATE_LIMIT` | `60` | Запросы OG-превью публичной общей доски в минуту, на токен. |

## Установка Docker по операционным системам

Два способа запустить Janosik на своей машине:

| | Docker (рекомендуется) | Из исходников (разработка) |
| --- | --- | --- |
| Что это | Готовый контейнер: всё приложение плюс PostgreSQL и Redis | Серверы разработки интерфейса и API с PostgreSQL |
| Что нужно | Docker Desktop или Docker Engine | Node.js 22.17 или новее, npm |
| Для чего подходит | Реальное использование, self-hosting | Изменение кода |

### macOS

Установите и запустите Docker Desktop (Intel или Apple Silicon) либо Colima
с Docker и Compose. В терминале выполните команду из раздела
[пробной установки](#пробный-запуск-в-локальной-сети-или-на-localhost).
Опубликованный образ поддерживает `amd64` и `arm64`.

### Windows 11

1. Установите WSL2 и дистрибутив Linux (например, Ubuntu): выполните
   `wsl --install` в PowerShell от администратора. При необходимости
   перезагрузите компьютер.
2. Установите и запустите Docker Desktop. Включите WSL2 engine и интеграцию
   с WSL для выбранного дистрибутива.
3. Откройте терминал Ubuntu, убедитесь, что установлены `curl` и `openssl`,
   и выполните команду из раздела
   [пробной установки](#пробный-запуск-в-локальной-сети-или-на-localhost).
   Держите папку установки внутри файловой системы WSL (например, `~/janosik`).

Установщик — Bash-скрипт; не запускайте его напрямую в PowerShell.

### Linux

Установите и запустите Docker Engine с плагином Compose v2. Убедитесь, что ваш
пользователь может запускать Docker, и установите `curl` и OpenSSL. Затем
выполните команду из раздела
[пробной установки](#пробный-запуск-в-локальной-сети-или-на-localhost).
Официальные инструкции для дистрибутивов — на
[docs.docker.com/engine/install](https://docs.docker.com/engine/install/).

### Из исходников, все платформы

Установите Node.js 22.17 или новее (в `.nvmrc` указана основная версия **24**) и
выполните `npm install` в корне репозитория. Затем настройте API — dev-compose
читает `POSTGRES_*` из `backend/.env`, поэтому файл должен существовать до
`docker compose up`:

```bash
# 1. настройка API
cp backend/.env.example backend/.env
#   задайте JWT_SECRET (openssl rand -hex 32; в PowerShell см. раздел Windows)

# 2. dev PostgreSQL (контейнер janosik-postgres на порту 5433)
docker compose --env-file backend/.env -f backend/docker-compose.yml up -d

# 3. миграции, сборка и запуск API (порт 3000)
npm run prisma:deploy -w backend
npm run build:backend
npm run start -w backend

# 4. во втором терминале запустите UI (Vite проксирует /api на :3000)
npm run dev
```

С настройками из `backend/.env.example` (без SMTP и bootstrap)
самостоятельная регистрация с паролем недоступна. В корне репозитория
выполните `npm run admin:create -w backend -- --email me@example.com`, чтобы
создать первого мастера. Войдите по адресу `http://localhost:5173/admin`
(сервер разработки Vite), выберите **Пользователи → Создать пользователя**,
а затем в карточке пользователя нажмите **Подтвердить email** для адреса,
к которому у вас есть доступ. Войдите в аккаунт для досок по адресу
`http://localhost:5173/`.

**Маркетинговый сайт** — отдельный dev-сервер (`npm run dev:site`, порт 4321).
В dev приложение не отдаётся по `/app/` на сайте — этот путь принадлежит
образу для самостоятельного размещения, — поэтому для кнопок входа и регистрации
на сайте нужно указать адрес сервера разработки интерфейса:
`PUBLIC_APP_URL=http://localhost:5173 npm run dev:site`.

**Исходящая почта по умолчанию выключена** (режим записи в журнал, если не заданы `SMTP_*`):
регистрация с паролем требует настроенной почты. См.
[Почтовая служба](/ru/docs/admin/settings/) и [Инструкции по эксплуатации](/ru/docs/runbooks/).
Локальная песочница — Mailpit:

```bash
docker run -d --name janosik-mailpit --restart unless-stopped \
  -p 1025:1025 -p 8025:8025 axllent/mailpit
# SMTP localhost:1025, веб-ящик http://localhost:8025
```

Чтобы собрать образ из рабочей копии вместо загрузки готового, раскомментируйте
`build: .` в `docker-compose.yml`.

## Раздельный деплой (приложение и сайт на разных хостах)

Образ для самостоятельного размещения обслуживает сайт и приложение по **одному
базовому адресу** — сайт по `/`, приложение по `/app/`, —
поэтому настраивать нечего. Если **приложение** и **маркетинговый сайт/доки**
отдаются с *разных* хостов, настройте ссылки между сайтом и приложением:

| Направление | Переменная | Где задаётся | Значение |
| --- | --- | --- | --- |
| Сайт → Приложение (CTA «Sign in» / «Create account») | `PUBLIC_APP_URL` | сборка **сайта** | origin приложения, напр. `https://app.example.com/` |
| Приложение → Сайт («Help → Documentation») | `VITE_SITE_URL` | сборка **UI** | origin сайта, со слешем на конце, напр. `https://example.com/` |

Ошибка в любой из них приводит к **404**: CTA открывает страницу «не найдено»
сайта, либо Help → Documentation открывает страницу «не найдено» приложения. Та
же пара нужна в dev, где приложение и сайт всегда два сервера (приложение
`:5173`, сайт `:4321`):

```bash
# dev-сервер UI — меню «Помощь» ведёт на dev-сайт Astro:
VITE_SITE_URL=http://localhost:4321/ npm run dev

# dev-сервер сайта — CTA «Sign in» / «Create account» ведут на UI:
PUBLIC_APP_URL=http://localhost:5173 npm run dev:site
```

### Раздача статических файлов через nginx

Конфигурация `deploy/nginx.conf` подходит для установки, в которой nginx
сам отдаёт обе статические сборки. Укажите публичный адрес при сборке сайта:
nginx не может менять канонические URL, ссылки Open Graph и карту сайта во время
раздачи. Для сайта по пути `/janosik/` выполните
`SITE_BASE=/janosik/ SITE_URL=https://public-host PUBLIC_APP_URL=/app/ npm run build -w site`
и подключите сборку по пути `/janosik/`. Скопируйте `404.html` из сборки в корень
nginx, чтобы конфигурация из примера отдавала эту страницу при ошибках 404.
Оставьте `PUBLIC_APP_URL=/app/`, если приложение доступно на том же домене по
`/app/`, или укажите его полный публичный
URL. `SITE_BASE` добавляет префикс к сгенерированным ссылкам навигации, ресурсам
и SEO-адресам. Ссылки с начальным `/` в тексте документации по-прежнему ведут от
корня домена. Добавьте маршруты для этих ссылок или разместите сайт в корне
домена, чтобы все ссылки в тексте работали без дополнительных маршрутов.

После сборки backend и обоих фронтендов
сгенерируйте файл CSP из тех же каталогов, которые обслуживает nginx.
После каждой новой сборки создайте файл заново. Без этого файла проверка
`nginx -t` завершится ошибкой. Перезагрузите nginx после успешной проверки.

```bash
node scripts/generate-nginx-csp.mjs ui/dist site/dist > /etc/nginx/janosik-csp.conf.next &&
  mv /etc/nginx/janosik-csp.conf.next /etc/nginx/janosik-csp.conf &&
  nginx -t
```

Файл использует ту же политику и хеши встроенных скриптов, что и Node.
Публичные ссылки по-прежнему можно встраивать. Конфигурация добавляет HSTS
к статическим ответам и передаёт заголовки API от Node. Для собственных ответов
nginx, в том числе ошибок API 413 и 502, nginx добавляет HSTS и строгую CSP.
Откройте публичный домен по HTTPS, чтобы браузеры могли применить HSTS.

### Хранение журнала команд

Журнал команд доски хранится в месячных партициях PostgreSQL
(`Command_YYYYMM`). Обслуживание поддерживает предыдущий, текущий и следующие
три месяца, а целые месяцы старше окна хранения удаляются одной операцией (по
умолчанию 30 дней — `PURGE_AFTER_DAYS` или настройка в мастер-панели). Бюджет
очистки журнала — 1 млн строк на таблицу за часовой запуск (24 млн/сутки); если
планировщик остановлен, эффективное окно растёт. Поскольку партиции месячные,
живое окно фактически 30–60 дней; планируйте ~2× номинальных строк и места.
Активный рой агентов пишет
десятки команд в секунду; смотрите поле `commandLog` в
`GET /api/v1/admin/observability` (на текущей странице админки оно не
отрисовывается): размер партиций, мёртвые строки и время vacuum. `defaultRows`
считается точно и должно оставаться нулевым. Блок `registry` показывает
непартиционированную таблицу `CommandKey`; она очищается пакетными проходами
сиротских ключей, поэтому следите за её мёртвыми строками и autovacuum.
Миграция 6 строит индекс доски inline только для маленького реестра; большая
установка откладывает его на job `ensure-command-key-index`
(`CREATE INDEX CONCURRENTLY`, место под индекс/WAL, тихое окно). Для
обновления, которое вводит партиции, нужно примерно вдвое больше свободного
места, чем занимает журнал, и полное тихое окно — вся транзакция миграции
держит старые имена таблиц, пока копирует и строит индексы; остановите старые
реплики перед миграцией. Откат — восстановление резервной копии базы.

Резервное копирование, восстановление и обновление описаны в
[инструкциях по эксплуатации](/ru/docs/runbooks/). Сообщайте об уязвимостях приватно;
см. [Безопасность](/ru/docs/security/).

## Сообщение об уязвимости

Пожалуйста, не открывайте публичный issue по проблемам безопасности.
Сообщайте о них приватно через GitHub private vulnerability reporting
(Security, затем Advisories, затем «Report a vulnerability») в репозитории.

Укажите, насколько можете:

- описание проблемы и её влияние;
- шаги воспроизведения, например минимальный запрос и ответ или репозиторий
  для воспроизведения;
- версию или коммит, которые вы проверяли, и форму развёртывания (HTTPS, за
  прокси, один экземпляр).

Мейнтейнер стремится подтвердить получение в течение нескольких дней и
выпустить исправление или меру защиты для подтверждённых проблем как можно
скорее. Пожалуйста, дайте разумное время на выпуск исправления до публичного
раскрытия.

## Поддерживаемые версии

Janosik размещается самостоятельно и доступен в виде образов контейнеров и
исходного кода ветки `main`. Исправления безопасности получают только последний
релиз и `main`.

## Чек-лист защиты при размещении на своём сервере

Операционный чек-лист находится вместе с остальными сценариями:
[Чек-лист безопасности](/ru/docs/runbooks/#чек-лист-безопасности). Коротко:

- Отдавайте приложение по HTTPS и держите `COOKIE_SECURE=true`.
- Задайте `ALLOW_REGISTRATION=false`, когда ваша первая учётная запись
  создана.
- Используйте надёжный, уникальный `JWT_SECRET`; никогда не переиспользуйте
  значение из примера.
- Замените `POSTGRES_PASSWORD` из примера: контейнер отказывается
  запускаться, пока он равен `change-me`.
- Поставьте впереди обратный прокси с завершением TLS и задайте
  `TRUST_PROXY=1`.
- Держите базу данных и том загрузок в резервных копиях.

## Элементы защиты, реализованные на сервере

### Refresh-cookie

Refresh-токен никогда не появляется в теле ответа. Он передаётся в httpOnly cookie
с именем `refresh_token`, ограниченной путём `/api/v1/auth` с
`SameSite=Strict`. Атрибут `Secure` следует за `COOKIE_SECURE` (авто: включён
в production, выключен в остальных случаях). По обычному HTTP браузер молча
отбрасывает `Secure`-cookie, поэтому и существует описанная ниже защита при
запуске.

Контур учётной записи мастера использует свою cookie,
`admin_refresh_token`, ограниченную `/api/v1/admin/auth`, с отдельной
аудиторией JWT (`janosik-admin`) и отдельным claim `typ`. Пользовательский
токен никогда не аутентифицирует административный маршрут, а
административный токен никогда не аутентифицирует пользовательский маршрут.

### Хеширование паролей

Пароли хешируются с помощью argon2id, как для учётных записей пользователей,
так и для учётных записей мастеров, создаваемых через CLI. Ответы никогда не
содержат хеши паролей или токенов.

### Персональные API-ключи

Персональный API-ключ (`jnk_…`) действует от имени владельца в работе с
досками, но не может управлять учётными данными учётной записи. Просмотр,
создание и отзыв ключей, смена пароля и смена почты требуют сессии в
браузере; ключ на этих маршрутах получает `403` с `code: "pat_forbidden"`.
То же относится к приглашениям и записи профиля. Поэтому ключ, попавший в
журнал или раскрытый агентом из-за вредоносной инструкции в данных, не
позволяет создать новый ключ, принять приглашение, изменить профиль, лишить
владельца доступа или сменить адрес учётной записи.

У каждого ключа есть неизменяемый пресет области. Новые ключи создаются как
`worker`; токен никогда не повышает роль владельца на доске. Обычная запись
требует `worker`, переход в Done — `reviewer`, администрирование доски —
`admin` (и роль ADMIN на доске). Destructive-действия по умолчанию требуют
подтверждения человеком; `trustedCi` — явное исключение для доверенного
CI-конвейера, а политика доски `destructive: "deny"` блокирует их даже для
`trustedCi`. Полный жизненный цикл approval появится в 166.5: до этого
destructive-вызов агента получает `409 approval_required`, ничего не
применяется, а действие выполняет человек в браузере. Существующие ключи
получили `admin` + `trustedCi`, кроме read-only. Сменить область ключа нельзя:
создайте новый ключ и отзовите старый.

Смена пароля отзывает все API-ключи и завершает остальные сессии. Это помогает
защитить учётную запись при подозрении на утечку. Ключ, созданный через
API без срока действия, получает 90 дней; бессрочным его делает только явный
`null` (вариант `Бессрочно` в приложении). Хранится только sha256-хеш ключа.

### Владение учётной записью и подтверждение почты

Неподтверждённый адрес почты ничего не доказывает, поэтому сервер не отдаёт
ему ничего, что адресовано этому ящику:

- **Вход через OAuth в неподтверждённую учётную запись.** Когда кто-то
  входит через Google или Яндекс, а учётная запись с тем же адресом есть, но
  так и не подтвердила почту, сервер сначала стирает её учётные данные:
  удаляет пароль, отзывает все сессии и API-ключи и удаляет ожидающие коды
  подтверждения. Только после этого учётная запись привязывается и
  помечается подтверждённой. Тот, кто зарегистрировал адрес раньше, не владея
  ящиком, теряет весь доступ. Так закрыт путь захвата учётной записи заранее.
- **Приглашения.** Приглашения ждут подтверждения почты: неподтверждённая
  учётная запись не видит их и не может принять.
- **Защита от определения существующих аккаунтов.** Приглашение на адрес отвечает одинаково,
  есть ли у него учётная запись или нет, и задержка входа тоже считается по
  адресу независимо от существования учётной записи.

### Защита при запуске по HTTP

В production, если `PUBLIC_ORIGIN` не HTTPS, а refresh-cookie помечена
`Secure`, API отказывается запускаться, вместо того чтобы молча отбросить
cookie:

```
Refusing to start: NODE_ENV=production but PUBLIC_ORIGIN is not HTTPS (...)
```

Полное сообщение объясняет ловушку с выходом через 15 минут и предлагает
`COOKIE_SECURE=false` для явного отключения требования Secure-cookie. При таком значении в production,
сервер вместо этого выводит громкое предупреждение. Защита не действует вне
production, поэтому dev и e2e по обычному HTTP не затрагиваются.

### Ограничения частоты

Глобальное ограничение работает на `THROTTLE_LIMIT` запросов в минуту (по
умолчанию 300) на субъекта: пользователя для сессии после входа, ключ для
персонального API-ключа и IP клиента для анонимного трафика. Проба `/health`
освобождена. При заданном `REDIS_URL` счётчики общие для всех узлов.
Отдельные auth-маршруты добавляют поверх более строгие окна, а контур
публичных общих досок имеет свой бюджет на токен. Точные окна приведены в
[Справочнике API](/ru/docs/api/#ограничения-частоты-запросов). Отказ отвечает `429`.

Вход пользователя к тому же притормаживает по учётной записи. Начиная с
пятого неверного пароля для одного адреса, этот адрес блокируется на 30
секунд, и блокировка удваивается с каждой следующей неудачей, но не больше 15
минут. Заблокированный вход отвечает `429` с `code: "login_backoff"` и
`retryAfter` в секундах; успешный вход снимает блокировку. Это останавливает
подбор пароля, распределённый по множеству IP-адресов.

### Размер запроса

JSON-тело ограничено 256 КБ, поэтому неаутентифицированный запрос не может
заставить сервер буферизовать и разбирать мегабайты. Только импорт досок и
эндпоинты команд принимают до 5 МБ, а одна команда ограничена 2 МБ. У
загрузки файлов свои лимиты (25 МБ на вложение, 2 МБ на аватар).

### Заголовки безопасности и CSP

Каждый ответ проходит через helmet. Политика безопасности содержимого
настроена под оболочку приложения: `script-src` — это
`'self' 'wasm-unsafe-eval' https://plausible.io` плюс хеш `'sha256-…'` для
каждого встроенного скрипта отдаваемых фронтендов, `style-src` — это
`'self' 'unsafe-inline'`, `img-src` — это `'self' data: blob:`, `media-src` —
это `'self' blob:`, `connect-src` — это `'self' https://plausible.io`,
`worker-src` — это `'self' blob:`, а `font-src` — это `'self' data:`.
`upgrade-insecure-requests` убран, чтобы работал self-host по обычному HTTP.
Публичные общие доски ослабляют `frame-ancestors`, чтобы `?embed=1` можно
было встраивать, и остаются `noindex`. `wasm-unsafe-eval` позволяет поиску
документации скомпилировать WASM-индекс Pagefind, а `https://plausible.io` —
это необязательный скрипт аналитики без cookie (`PUBLIC_ANALYTICS_DOMAIN`).
Без них поиск зависает на «Поиск…», а событие аналитики молча блокируется.

В `script-src` нет `'unsafe-inline'`. При запуске сервер читает HTML-файлы в
`STATIC_DIR` и `SITE_DIR`, хеширует каждый найденный встроенный скрипт и
разрешает ровно их, поэтому внедрённый встроенный скрипт отклоняется. Хеши
вычисляются один раз на процесс: пересобрав фронтенд вне образа,
перезапустите API, иначе браузер заблокирует новые встроенные скрипты.
Образ контейнера и так делает это при каждом деплое.

### Блокировка учётной записи мастера

Вход мастера блокирует учётную запись после пяти неверных паролей на 15 минут.
Временная блокировка ограничивает число попыток подбора пароля. Каждая попытка входа и каждое
изменение пишут строку аудита, видимую на странице аудита в панели.

### Двухфакторная аутентификация и список разрешённых IP

Двухфакторная аутентификация доступна только при входе в мастер-аккаунт: тело входа
администратора принимает необязательный `totpCode`. Страница безопасности
панели мастера по `/admin/security` показывает, включён ли TOTP, заданный
список разрешённых IP и список оповещений о подозрительной активности.
Включение и отключение TOTP и изменение списка разрешённых IP записываются в
журнал аудита. У учётных записей пользователей второго фактора нет; 6-значные
коды для подтверждения почты и смены почты — это внешние подтверждения, а не
факторы входа.

Список разрешённых IP-адресов мастера проверяется на каждом административном запросе
и на каждом обновлении сессии, а не только при входе, поэтому токен или
refresh-cookie, унесённые из разрешённой сети, в другом месте перестают
работать с `403`. Сохранение списка, в который не входит ваш текущий адрес,
отклоняется с `400`, чтобы нельзя было запереть себя посреди сессии.

### Потоки realtime

SSE-поток доски перепроверяет вызывающего на каждом тике keep-alive раз в 25
секунд, а не только при открытии. Он закрывается, когда членство удалено или
доступ зрителя истёк, учётная запись заблокирована, доска удалена или
API-ключ, которым поток открыт, отозван или истёк. Поток публичной live-ссылки
закрывается так же, как только ссылка отозвана или истекла.

### Контейнер

Образ стартует от root ровно настолько, чтобы передать том загрузок
непривилегированному пользователю `node`, а затем запускает миграции, API и
ffmpeg от `node`. Он отказывается запускаться, пока `POSTGRES_PASSWORD` равен
значению `change-me` из примера, и выводит предупреждение при запуске, пока
`ALLOW_REGISTRATION` равен `true` (по умолчанию).

## Замечания об архитектуре

- Модель доски изменяется через журнал команд со строгой валидацией на
  сервере. Клиенту никогда не доверяют идентичность или обратные команды:
  валидатор пересобирает каждое действие по списку разрешённых полей,
  сохраняет служебные поля восстановления только у команд отмены, а сервер
  заменяет метку времени команды, отстоящие от его собственных больше чем на
  пять минут.
- Snapshot-ссылки отдают только те комментарии и вложения, которые
  существовали в момент снимка.
- Описания карточек и комментарии Markdown обрабатываются рендерером с защитой
  от опасного содержимого. Держите зависимости обновлёнными.
- Доступ основан на ролях для каждой доски (ADMIN, MEMBER, VIEWER), плюс
  отдельный контур учётной записи мастера для панели администратора платформы
  со своей аудиторией, cookie и таблицей refresh-токенов.

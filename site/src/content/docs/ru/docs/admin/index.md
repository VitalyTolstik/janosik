Панель администратора предназначена для управления платформой. Она доступна по
адресу `/admin` (в Docker-установке — `/app/admin`) и загружается отдельно от
основного интерфейса. Панель использует собственный API-клиент и токен. Её
маршруты не подключают пользовательские `AuthProvider` и `BoardProvider`,
поэтому административная и пользовательская сессии изолированы.

## Кто может пользоваться панелью

Для входа нужна отдельная учётная запись администратора платформы —
**мастер-аккаунт** (master account). Такие записи хранятся в таблице
`AdminUser`, отдельно от обычных пользователей в `User`. Вход выполняется через
`/api/v1/admin/auth/*` с отдельной аудиторией JWT (`janosik-admin`) и
собственной refresh-cookie. Роли администратора платформы не связаны с ролью
`ADMIN` на отдельной доске.

У мастер-аккаунтов две роли:

| Роль | Доступ к панели |
| --- | --- |
| `OWNER` | Полный доступ к данным плюс раздел мастеров и все настройки, доступные только владельцу. |
| `OPERATOR` | Полный доступ к данным, но не может управлять мастерами и менять настройки владельца. |

Права на изменение настроек владельца проверяются на сервере.
При попытке оператора изменить такую настройку сервер возвращает `403` с текстом `Owner rights
are required`. В боковой панели пункты `Masters`, `Email service` и `OAuth
login` скрыты от операторов. На страницах настроек оператор видит состояние
только для чтения: лимит трафика, демо-запуск, настройки эксплуатации, изменения
рассылок, список разрешённых IP-адресов и очистку по сроку хранения доступны
только владельцу.

## Три способа создать мастера

Публичного HTTP-эндпоинта, создающего мастера, нет. Мастер-аккаунт появляется
одним из трёх путей.

### 1. Серверный CLI (bootstrap)

CLI — единственный способ создать первого мастера на чистой установке.
Запускайте из корня репозитория с установленными зависимостями backend и
файлом `backend/.env`:

```sh
npm run admin:create -w backend -- --email me@example.com
npm run admin:create -w backend -- --email me@example.com --display-name "Ops" --owner
npm run admin:passwd -w backend -- --email me@example.com
npm run admin:list   -w backend
```

- `create` приводит email к нижнему регистру и отклоняет неверный адрес.
  Первый мастер в пустой базе автоматически становится `OWNER`. Каждый
  следующий становится `OPERATOR`, если не передан `--owner`.
  `--display-name` необязателен.
- Пароль никогда не берётся из командной строки. Он запрашивается скрытым
  вводом с подтверждением либо читается из переменной окружения
  `ADMIN_PASSWORD` для автоматизации. Длина от 8 до 100 символов.
- `passwd` сбрасывает пароль существующего мастера, отзывает все его
  refresh-сессии и снимает блокировку.
- `list` печатает всех мастеров (email, роль, имя, последний вход, флаги
  blocked или locked). Секреты не показываются.
- CLI создаёт запись в журнале аудита, поэтому создание или смена пароля видны в журнале
  аудита панели.

### 2. Панель (только владелец)

Владелец открывает `Masters` и нажимает `Add master`. Диалог принимает email,
необязательное имя (не более 50 символов) и флажок `Grant owner rights`,
который выбирает `OWNER` или `OPERATOR`. Сервер генерирует одноразовый пароль
и показывает его один раз.

### 3. Повышение существующего пользователя (только владелец)

Владелец открывает страницу пользователя и запускает `Promote to master`. Так
создаётся мастер `OPERATOR` с тем же email и новым временным паролем. Диалог
требует ввести email аккаунта для подтверждения. Если мастер с таким email уже
существует, запрос отвечает `409`.

## Как войти

Откройте `/admin`. Если вы ещё не вошли, откроется брендовый split-screen
входа мастера: панель бренда с версией сборки, форма 372 px, прогрессивная
двухфакторная проверка и show/hide пароля. Ссылки на регистрацию,
восстановление пароля и соцсети отсутствуют. Кнопки SSO нет, потому что в
бэкенде нет master OIDC-провайдера; экран сообщает об этом честно.

- Форма отправляет `POST /admin/auth/login` с email и паролем плюс
  необязательный шестизначный код двухфакторной аутентификации.
- Сессия использует отдельный access-токен и отдельный refresh-cookie с именем
  `admin_refresh_token`, привязанный к пути `/api/v1/admin/auth` с
  `SameSite=Strict`. Пользовательские маршруты этот cookie не получают, а
  админский cookie не доходит до пользовательских маршрутов.
- Маршрут входа ограничен 10 попытками в минуту на IP.
- После 5 неудачных входов аккаунт блокируется на 15 минут. Заблокированный
  аккаунт отвечает `429`, и форма показывает `Account is temporarily locked`.
  Успешный вход сбрасывает счётчик и блокировку.
- Для неизвестного адреса сервер выполняет ту же проверку хеша, что и при
  неверном пароле. Это снижает возможность определить существование аккаунта по
  времени ответа.
- Отключённый аккаунт отклоняется после проверки пароля с `403`.
- Когда включена двухфакторная аутентификация, одного пароля недостаточно.
  Сервер отвечает `401` с `code: "totp_required"`, и форма показывает поле
  кода двухфакторной аутентификации. Код — шесть цифр из приложения
  аутентификатора.
- IP-список, если он задан для мастера, проверяется после пароля, поэтому
  атакующий не узнает список без верных учётных данных. Он проверяется
  снова на каждом административном запросе и каждом обновлении сессии: токен
  или refresh-cookie с адреса вне списка получают `403`.
- Refresh-токены ротируются при каждом использовании. Повторное использование
  отозванного токена отзывает все сессии этого мастера.

Успешный вход ведёт на дашборд. На экране входа также показана подсказка `Master
accounts are created on the server via the admin CLI.`

## Оболочка

Интерфейс состоит из сайдбара 232 px с восемью хабами, верхней панели 44 px с
хлебными крошками и плотной основной области. Каждая возможность, которая
раньше была отдельной ссылкой, стала вкладкой хаба; старые URL перенаправляются
туда. Полная карта — в [Редизайн админки](./redesign/).

### Хабы боковой панели

| Группа | Хабы |
| --- | --- |
| Работа | Обзор, Пользователи, Доски, Модерация |
| Контроль | Аудит и активность, Коммуникации |
| Настройка | Доступ и безопасность, Настройки |

Верхняя панель показывает хлебные крошки, вошедшего пользователя (со значком
`Master` у владельцев), кнопку командной палитры, переключатели плотности и
темы, шпаргалку и `Sign out`. Внизу сайдбара — переключатель языка и
`Back to boards`.

### Адаптивность

Сайдбар 232 px на десктопе, 64 px icon rail от 640 до 959 px и sheet 280 px за
scrim на 639 px и уже. На 639 px и уже таблицы превращаются в карточки с
подписями, поэтому контент занимает всю ширину телефона.

### Сочетания клавиш и настройки

- `Ctrl` или `Cmd` + `K` открывает командную палитру из любого места панели.
- `Ctrl` или `Cmd` + `B` сворачивает и разворачивает боковую панель. В свёрнутом
  виде — это узкая панель значков, а выбор запоминается в `localStorage` под ключом
  `janosik.admin.sidebar`.
- `g`, затем `d/u/b/m/a/c/s/,` переходит в хаб; `?` открывает шпаргалку.
- Переключатель плотности переключает строки 36 px и 30 px и запоминается под
  ключом `janosik.admin.density`.
- Переключатель темы переключает светлую и тёмную темы.
- Переключатель языка переключает панель между английским и русским.

### Командная палитра

Палитра объединяет навигацию, действия, недавние страницы и поиск по
сущностям. Она ищет пользователей, доски, карточки, комментарии, вложения и
метки через `GET /admin/search?q=`; результаты сгруппированы и доступны с
клавиатуры (`↑`/`↓`, Enter). При ошибке запроса показывается повтор, а не
пустой результат.

## Управление агентами не входит в админ-панель

Панель — это консоль поддержки, модерации и расследования, а не второй
board-клиент и не control plane агентов. **`/admin` не показывает и не
управляет запусками (runs), согласованиями (approvals) и политикой агентов;
отдельного кросс-борд раздела агентов в ней нет.** В панели нет кнопок
«одобрить/отклонить», паузы и возобновления, отката run, режима разрушающих
действий или TTL согласования. Это осознанная граница, а не недостающая
страница.

Управление агентами находится в пользовательском приложении, где действуют
роли доски:

- **`/agents`** — глобальный кросс-борд inbox из трёх разделов:
  **Attention** (ожидающие согласования на досках, где вы ADMIN, и устаревшие
  сессии), **Sessions** (список сессий с группировкой по доскам и детали) и
  **Runs** (фильтры, детали run и условный откат, который может применить
  только ADMIN доски; для MEMBER и VIEWER — только чтение). Выбранная доска,
  поиск и deep links на сессию/run/согласование сохраняются в URL.
- **Agent Control** на доске (кнопка с ботом в шапке доски) — операционная
  поверхность доски: **Inbox** для согласований, **Live** для паузы,
  возобновления и завершения доски и сессий, **Runs** для просмотра и отката
  run. Одобрение/отклонение и live-управление доступны только ADMIN доски;
  MEMBER и VIEWER видят Live и Runs только для чтения и не видят Inbox.
- **Настройки доски → Agents & automation** задают политику: режим
  разрушающих действий, триггеры согласования, лимиты команд и карточек на run
  и TTL согласования. Читать и менять их может только ADMIN доски.
- Пауза ключа, **Stop all** и отзыв ключа находятся в **Аккаунт → API keys**,
  а не в диалоге доски и не в `/admin`.

Мастер-аккаунт — не аккаунт доски: вход в `/admin` не даёт членства в доске и
не открывает эти элементы управления. Если они нужны тому же человеку, он
входит в пользовательское приложение под своим обычным аккаунтом с ролью на
доске. Панель по-прежнему показывает карточки, комментарии, команды и строки
аудита/активности, созданные агентами, вместе с атрибуцией по токену, сессии и
run; это доказательства для поддержки, а не управление агентом. Демо-рой в
настройках запускает одноразовых агентов на тестовой доске; это демонстрационная
фикстура платформы, а не просмотр или управление реальными runs, согласованиями
и политикой.

Кросс-борд надзор из мастер-панели **не входит в TASK-176**. Если он
понадобится позже, это отдельная задача с master API, явной моделью прав и
аудитом доступа мастеров. Раздел только в UI поверх существующих
board-scoped эндпоинтов обходил бы роли доски и недопустим.

См. [руководство по запуску агентов](/ru/docs/agent-launch/),
[управление агентами на доске](/ru/docs/user-guide/boards/#согласования-запуски-и-политика-агентов)
и [Аккаунт → API keys](/ru/docs/user-guide/account/#пауза-и-остановка-агентов).

Бэкенд Janosik — это сервис на NestJS. Эта страница описывает соглашения, общие
для всех маршрутов, и перечисляет группы эндпоинтов верхнего уровня. Изменения
содержимого доски проходят через [API команд](./commands/); остальные операции,
включая комментарии и вложения, доступны через REST и описаны в [справочнике
REST API](./rest/).

## Базовый путь и транспорт

Каждый маршрут обслуживается под глобальным префиксом `/api/v1`. Маршрут,
названный в этом справочнике как `POST /auth/login`, доступен по
`POST /api/v1/auth/login`.

Запросы и ответы используют JSON. Размер тела запроса по умолчанию ограничен
256 КБ. Импорт досок (`POST /boards/import`) принимает тела до
`MAX_IMPORT_BYTES` (25 МБ), а команды доски
(`POST /boards/:id/commands`, `/commands/batch`, `/plans`, `/plans/apply`) и
административные маршруты команд — до `MAX_COMMAND_BODY_BYTES` (10 МБ). Это
позволяет передавать большие пакеты импорта и снимки `RESTORE_*` для проверки
валидатором, не выдавая командам бюджет импорта. Размер отдельного действия
дополнительно ограничен `MAX_COMMAND_BYTES` (2 МБ) в сервисе команд. Экспорт
доски больше 25 МБ (`MAX_BOARD_EXPORT_BYTES`) возвращает тот же `413` с
подсказкой про `pg_dump` и никогда не обрезается. При превышении лимита сервер
возвращает `413` с `code: "payload_too_large"`.

Загрузка файлов использует `multipart/form-data` с единственной частью `file`.

## Аутентификация

Пользовательские маршруты принимают один из двух видов токенов в заголовке
`Authorization`:

```
Authorization: Bearer <access-token>
Authorization: Bearer jnk_<43 base64url chars>
```

Первый — это короткоживущий JWT access-токен из эндпоинтов аутентификации.
Второй — это персональный API-токен (PAT): значение, чей префикс `jnk_`
указывает обработчику аутентификации проверить его по таблице `ApiToken`, а не через
JWT-стратегию. Оба вида токенов подходят для маршрутов доски.

### Маршруты только для сессии

Персональный API-токен действует от имени владельца в работе с досками, но не
может управлять учётными данными аккаунта. При обращении с PAT эти маршруты возвращают `403`:

- `GET /users/me/tokens`, `POST /users/me/tokens`, `DELETE /users/me/tokens/:id`
- `POST /users/me/tokens/:id/pause`, `POST /users/me/tokens/:id/resume`
- `POST /agents/pause-all`, `POST /agents/resume-all`
- `POST /boards/:id/agents/pause`, `POST /boards/:id/agents/resume`
- `POST /boards/:id/agent-sessions/:id/pause`, `POST /boards/:id/agent-sessions/:id/resume`
- `POST /auth/password`
- `POST /auth/email/change/request`, `POST /auth/email/change/confirm`

```json
{
  "message": "Personal API tokens cannot manage account credentials — sign in with a browser session",
  "code": "pat_forbidden"
}
```

Вызывайте их с access-токеном из входа в браузере. Маршруты досок,
участников, ссылок, приглашений, комментариев, вложений и команд по-прежнему
принимают PAT. Поэтому утёкший ключ не может выпустить новые ключи, сменить
пароль или перенести аккаунт на другой почтовый ящик.

Refresh-токен никогда не появляется в теле ответа. Он передаётся в httpOnly cookie
с именем `refresh_token`, ограниченной путём `/api/v1/auth` и с
`SameSite=Strict`. Только `POST /auth/refresh` и другие маршруты `/auth`,
которым нужна сессия вызывающего, читают её.

Контур мастер-аккаунта использует отдельную cookie (`admin_refresh_token`,
путь `/api/v1/admin/auth`), отдельную JWT-аудиторию (`janosik-admin`) и
отдельный claim `typ`. Пользовательский токен никогда не аутентифицирует
админский маршрут, а админский токен никогда не аутентифицирует
пользовательский маршрут.

## Формат ошибок

Каждая ошибка REST использует одно машиночитаемое тело (TASK-166.4):

```json
{
  "code": "version_conflict",
  "message": "The board changed since you read it",
  "retryable": false,
  "requestId": "3d0f2c7e-…",
  "currentVersion": 42,
  "conflict": "version",
  "statusCode": 409
}
```

- `code` — стабильный идентификатор в snake_case; ветвитесь по нему, а не по
  `message`.
- `message` — английский запасной текст. UI и MCP локализуют по `code`.
- `retryable` присутствует всегда. `true` означает, что тот же запрос можно
  повторить без изменений после `retryAfter` (секунды) или короткой паузы:
  занятая доска, ограничение частоты, ещё выполняющийся идемпотентный запрос.
  Ошибки валидации и прав доступа никогда не retryable.
- `requestId` совпадает с заголовком ответа `X-Request-Id`; приложите его к
  отчёту об ошибке.
- `currentVersion` всегда присутствует числом или `null`. В конфликте команды
  это последовательность доски (`max(Command.seq)`), а не `Board.version`.
- `field` указывает на отклонённое поле, `details` несёт дополнительный
  контекст, `limit`/`current` описывают смысловой лимит. `conflict`
  (`version`, `wip`, `id`, `workflow`) и `workflow` сохранены для
  совместимости.

`ValidationPipe` работает с `whitelist: true` и `transform: true`. Неизвестное
поле тела отбрасывается; проваленная проверка class-validator — это
`400 validation_failed`, а отдельные сообщения лежат в `details.messages`.

Устаревшее поле Nest `error` намеренно не возвращается; его заменяет `code`.
`statusCode` сохранён для совместимости.

| HTTP | `code` | Значение |
| --- | --- | --- |
| `400` | `validation_failed` | форма/поля тела; `field`, когда известно |
| `401` | `unauthorized` | нет учётных данных, истекли или неверны |
| `403` | `forbidden` | не участник или нет роли на доске |
| `403` | `scope_denied` | пресет токена не разрешает действие |
| `403` | `destructive_denied` | политика доски запрещает destructive-действия |
| `403` | `agent_paused` | агенты приостановлены на доске/в сессии/токене |
| `403` | `pat_forbidden` | персональный API-токен вызвал [маршрут только для сессии](#маршруты-только-для-сессии) |
| `404` | `not_found` | неизвестный или мягко удалённый ресурс |
| `409` | `version_conflict` | устарел `ifMatch`/`ifMatchVersions`; см. `currentVersion` |
| `409` | `workflow_conflict` | процесс запрещает переход; см. `workflow` |
| `409` | `limit_exceeded` | лимит WIP, коллекции, досок или share-ссылок |
| `409` | `approval_required` | destructive-действию нужно подтверждение человека (166.5) |
| `409` | `idempotency_conflict` | тот же `Idempotency-Key` использован с другим телом |
| `409` | `idempotency_in_progress` | первый запрос с этим ключом ещё выполняется; повторите |
| `413` | `payload_too_large` | тело/файл больше лимита маршрута; см. `limit` |
| `429` | `rate_limited` | подождите `retryAfter` секунд и повторите |
| `429` | `login_backoff` | слишком много неудачных входов; подождите `retryAfter` секунд |
| `503` | `board_write_timeout` | таймаут блокировки записи доски; повтор безопасен |
| `503` | `service_unavailable` | обслуживание или временный сбой; повторите позже |

Неожиданный сбой сервера — `500 internal_error` с общим текстом и без
stack trace. Полная таблица кодов — в `docs/TASK-166-launch-agent-control.md`
§8.2.

| Статус | `code`                | Значение                                                                                                               |
| ------ | --------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `403`  | `pat_forbidden`       | персональный API-токен вызвал [маршрут только для сессии](#маршруты-только-для-сессии)                                 |
| `403`  | `agent_paused`        | запись заблокирована паузой сессии/токена/доски; см. [Пауза и kill](./rest/#пауза-и-kill)                              |
| `429`  | `login_backoff`       | адрес в [задержке входа](#задержка-входа); `retryAfter` — это ожидание в секундах                                        |
| `503`  | `board_write_timeout` | запись в доску превысила время ожидания под нагрузкой; запрос можно безопасно повторить (команду с тем же `commandId`) |

## Идемпотентность

REST-операции записи `POST /boards`, `POST /boards/import`,
`POST /cards/:id/comments`, `POST /boards/:id/shares`,
`POST /cards/:id/attachments` и команда `DUPLICATE_CARD` принимают заголовок
`Idempotency-Key` (8–128 символов из `A-Z a-z 0-9 _ -`). Первый успешный
ответ сохраняется на 24 часа:

```http
POST /api/v1/boards
Idempotency-Key: create-roadmap-2026-11-10
Content-Type: application/json

{ "title": "Roadmap" }
```

Повтор с тем же ключом и тем же телом возвращает сохранённые статус и тело и
не создаёт вторую доску. Другое тело с этим ключом —
`409 idempotency_conflict`; параллельный повтор, пока первый запрос ещё
выполняется, — `409 idempotency_in_progress` (`retryable: true`). Записи через
журнал команд используют для этого `CommandRequest.commandId`; повтор
`commandId` с другим телом также даёт `409 idempotency_conflict`. Неудачный
запрос освобождает ключ, поэтому честный повтор может выполниться снова.

## Ограничения частоты запросов

Глобально работают два ограничителя:

- Фиксированное окно `THROTTLE_LIMIT` запросов в минуту (по умолчанию 300) на
  субъекта. Владелец платформы может изменить его во время работы из панели мастера.
  `/health` освобождён.
- Необязательный бюджет на аутентифицированного пользователя, задаваемый из
  панели мастера. Контуры `/admin`, `/auth` и `/health` освобождены от него.

Субъект, на счёт которого идёт запрос, это пользователь для валидного
access-токена (все вкладки и устройства одного аккаунта делят один бюджет),
ключ для персонального API-токена, недавно прошедшего аутентификацию (у
каждого ключа свой бюджет), и IP клиента для всего остального: анонимных
вызовов, неизвестных ключей, истёкших токенов. Когда задан `REDIS_URL`,
счётчики живут в Redis и общие для всех узлов; без него каждый процесс
считает сам.

Отдельные маршруты аутентификации добавляют более узкие окна `@Throttle`,
считаемые так же: на IP для анонимных маршрутов, на пользователя для
маршрутов после входа.

| Маршрут                              | Лимит                       |
| ------------------------------------ | --------------------------- |
| `POST /auth/register`                | 5 в минуту на IP            |
| `POST /auth/login`                   | 5 в минуту на IP            |
| `POST /auth/password`                | 5 в минуту на пользователя  |
| `POST /auth/email/change/request`    | 3 в час на пользователя     |
| `POST /auth/email/change/confirm`    | 5 в минуту на пользователя  |
| `POST /auth/verify-email`            | 10 в минуту на пользователя |
| `POST /auth/verify-email/resend`     | 3 в час на пользователя     |
| `GET /auth/oauth/:provider/start`    | 20 в минуту на IP           |
| `GET /auth/oauth/:provider/callback` | 20 в минуту на IP           |

У публичного API ссылок отдельный лимит запросов на токен (см.
[REST API](./rest/)). При превышении лимита сервер возвращает `429`.

### Задержка входа

Кроме ограничения по IP, `POST /auth/login` временно блокирует повторные попытки
входа для одного аккаунта. Неудачи
считаются по нормализованному email независимо от того, есть ли такой
аккаунт, поэтому блокировка ничего не говорит об адресе. Пятая неудача
блокирует адрес на 30 секунд, каждая следующая удваивает блокировку, но не
больше 15 минут. Пока блокировка действует, любой вход на этот адрес отвечает
`429`, даже с верным паролем:

```json
{
  "message": "Too many failed sign-in attempts — try again in 30 s",
  "code": "login_backoff",
  "retryAfter": 30
}
```

Успешный вход сбрасывает счётчик; кроме того, он обнуляется через час после
последней неудачи. При заданном `REDIS_URL` счётчик общий для всех узлов.

## Режим обслуживания

Когда владелец включает режим обслуживания, `MaintenanceGuard` отвечает на каждый
публичный и пользовательский запрос `503` с заданным сообщением. Пути
`/admin`, `/auth` и `/health` остаются доступными, чтобы владелец мог войти и отключить обслуживание.

## Эндпоинты аутентификации

| Метод  | Путь                         | Аутентификация | Возвращает                               |
| ------ | ---------------------------- | -------------- | ---------------------------------------- |
| `POST` | `/auth/register`             | нет            | `AuthResponseDto`                        |
| `POST` | `/auth/login`                | нет            | `AuthResponseDto`                        |
| `POST` | `/auth/refresh`              | refresh cookie | `AuthResponseDto`                        |
| `POST` | `/auth/logout`               | refresh cookie | `{ status: "ok" }`                       |
| `GET`  | `/auth/config`               | нет            | `AuthConfigResponse`                     |
| `GET`  | `/auth/me`                   | пользователь   | `AuthUserDto`                            |
| `POST` | `/auth/password`             | сессия         | `{ status: "ok" }`                       |
| `POST` | `/auth/email/change/request` | сессия         | `{ expiresAt: number, queued: boolean }` |
| `POST` | `/auth/email/change/confirm` | сессия         | `AuthResponseDto`                        |
| `POST` | `/auth/verify-email`         | пользователь   | `{ user: AuthUserDto }`                  |
| `POST` | `/auth/verify-email/resend`  | пользователь   | `{ expiresAt: number, queued: boolean }` |

`пользователь` принимает access-токен или персональный API-токен; `сессия`
принимает только access-токен из входа в браузере (см.
[Маршруты только для сессии](#маршруты-только-для-сессии)).

`register`, `login`, `refresh` и `email/change/confirm` устанавливают
refresh-cookie и возвращают `{ accessToken, user }`. `register` также
отправляет 6-значный код подтверждения на адрес.

### Регистрация

Тело `POST /auth/register`:

| Поле          | Тип    | Обязательно | Ограничения                                                |
| ------------- | ------ | ----------- | ---------------------------------------------------------- |
| `email`       | string | да          | валидный email; обрезается и приводится к нижнему регистру |
| `password`    | string | да          | от 8 до 100 символов                                       |
| `displayName` | string | нет         | не более 50 символов                                       |

Возвращает `AuthResponseDto` и устанавливает refresh-cookie. Если адрес уже занят, сервер возвращает `409`.

### Вход

Тело `POST /auth/login`:

| Поле       | Тип    | Обязательно | Ограничения                                                |
| ---------- | ------ | ----------- | ---------------------------------------------------------- |
| `email`    | string | да          | валидный email; обрезается и приводится к нижнему регистру |
| `password` | string | да          | не более 100 символов                                      |

Минимальная длина при входе не проверяется: при коротком пароле сервер
возвращает `401`, как и при любых других неверных учётных данных. Возвращает
`AuthResponseDto`.
Повторные неудачи для одного адреса включают
[задержку входа](#задержка-входа).

### Refresh и выход

`POST /auth/refresh` читает cookie `refresh_token` и возвращает свежий
`AuthResponseDto`. `POST /auth/logout` отзывает сессию и очищает cookie,
возвращая `{ status: "ok" }`.

### Конфигурация

`GET /auth/config` не требует аутентификации и возвращает два публичных
булевых значения, которые экран входа читает до появления сессии:

```json
{ "allowRegistration": true, "allowPublicShares": true }
```

### Me

`GET /auth/me` возвращает `AuthUserDto` аутентифицированного пользователя и
поле `impersonatedBy`: id мастера, когда access-токен — это сессия поддержки
(имперсонация), иначе `null`, в том числе для API-токенов. С персональным
API-токеном ответ также содержит `token` (`ApiTokenIdentityDto`, без секрета
и хеша); у сессии браузера `token: null`. TASK-166 резервирует поле `session`
для активной сессии агента (сейчас `null`).

### Смена пароля

Тело `POST /auth/password`:

| Поле              | Тип    | Обязательно | Ограничения           |
| ----------------- | ------ | ----------- | --------------------- |
| `currentPassword` | string | да          | не более 100 символов |
| `newPassword`     | string | да          | от 8 до 100 символов  |

Только для сессии: персональный API-токен получает `403` с
`code: "pat_forbidden"`. Возвращает `{ status: "ok" }`. Refresh-cookie
определяет сессию вызывающего, и она остаётся активной; все остальные сессии
отзываются, как и все персональные API-токены аккаунта.

### Смена email

Оба маршрута смены email только для сессии.
`POST /auth/email/change/request` запрашивает текущий пароль и подтверждение нового адреса. Тело:

| Поле              | Тип    | Обязательно | Ограничения                                                |
| ----------------- | ------ | ----------- | ---------------------------------------------------------- |
| `newEmail`        | string | да          | валидный email; обрезается и приводится к нижнему регистру |
| `currentPassword` | string | да          | минимум 1 символ                                           |

Возвращает `{ expiresAt, queued }` и отправляет 6-значный код на новый адрес.

Тело `POST /auth/email/change/confirm`:

| Поле   | Тип    | Обязательно | Ограничения  |
| ------ | ------ | ----------- | ------------ |
| `code` | string | да          | ровно 6 цифр |

При успехе адрес заменяется, отзываются все refresh-сессии (включая старую
cookie вызывающего), и возвращается свежий `AuthResponseDto` с новой
refresh-cookie.

### Подтверждение email

Тело `POST /auth/verify-email`:

| Поле   | Тип    | Обязательно | Ограничения  |
| ------ | ------ | ----------- | ------------ |
| `code` | string | да          | ровно 6 цифр |

Возвращает `{ user }` с установленным `emailVerifiedAt`.
`POST /auth/verify-email/resend` отправляет новый код и возвращает
`{ expiresAt, queued }`.

### Двухфакторная аутентификация

У пользовательских аккаунтов нет второго фактора. 6-значный код
(подтверждение email, смена email) это внешнее подтверждение, а не фактор
входа. Двухфакторная аутентификация есть только при входе мастер-аккаунта:
в теле запроса входа администратора можно передать `totpCode`. См. контур
мастер-аккаунта.

## OAuth-вход

| Метод | Путь                             | Аутентификация | Возвращает                          |
| ----- | -------------------------------- | -------------- | ----------------------------------- |
| `GET` | `/auth/oauth/providers`          | нет            | `{ providers: OAuthProviderDto[] }` |
| `GET` | `/auth/oauth/:provider/start`    | нет            | `302` на провайдера                 |
| `GET` | `/auth/oauth/:provider/callback` | нет            | `302` в UI                          |

Оба маршрута выполняют перенаправление браузера, а не XHR-запрос. `providers`
перечисляет только включённые провайдеры; каждая запись имеет вид `{ id, label
}`, где `id` принимает значение `google` или `yandex`.

`start` генерирует state, ставит httpOnly state-cookie `SameSite=Lax` с
путём `/api/v1/auth/oauth` и перенаправляет на провайдера. `callback`
проверяет state, ставит refresh-cookie и перенаправляет в корень UI. Любая
ошибка перенаправляет на `?authError=oauth_failed` в корне UI.

Email от провайдера обрезается, приводится к нижнему регистру и сверяется с
существующими аккаунтами без учёта регистра. Если адрес новый, сервер создаёт
OAuth-аккаунт без пароля. Существующий аккаунт привязывается, и его адрес
становится
подтверждённым. Если этот аккаунт так и не подтвердил email, перед привязкой
провайдера сервер удаляет пароль и ожидающие коды подтверждения и смены email, а
также отзывает все refresh-сессии и персональные API-токены.
Так закрыт путь захвата аккаунта заранее, когда кто-то регистрирует чужой
адрес с паролем до того, как владелец впервые войдёт через провайдера.
После этого аккаунт работает только через OAuth: `POST /auth/password` задаёт
первый пароль, не проверяя `currentPassword`.

## Пользователи и аккаунт

Все маршруты требуют пользовательской аутентификации (JWT или PAT), кроме трёх
маршрутов токенов, которые [только для сессии](#маршруты-только-для-сессии):
API-ключ не может ни перечислить, ни создать, ни отозвать ключи.

Персональный API-токен можно ограничить при создании: `boardId`
— одной доской, `readOnly: true` запрещает любую запись (`403 pat_read_only`),
а `rateLimitPerMinute` задаёт собственный лимит запросов (при превышении —
`429`).

| Метод    | Путь                    | Возвращает                |
| -------- | ----------------------- | ------------------------- |
| `PATCH`  | `/users/me`             | `AuthUserDto`             |
| `PATCH`  | `/users/me/avatar`      | `AuthUserDto`             |
| `GET`    | `/users/:userId/avatar` | байты изображения         |
| `GET`    | `/users/me/tokens`      | `UserTokenDto[]`          |
| `POST`   | `/users/me/tokens`      | `CreateUserTokenResponse` |
| `DELETE` | `/users/me/tokens/:id`  | `{ status: "ok" }`        |

Тело `PATCH /users/me`:

| Поле          | Тип             | Обязательно | Ограничения                                                           |
| ------------- | --------------- | ----------- | --------------------------------------------------------------------- |
| `displayName` | string или null | нет         | не более 50 символов; `null` очищает                                  |
| `avatarColor` | string или null | нет         | одно из `USER_AVATAR_COLORS`; `null` возвращает значение по умолчанию |
| `notifyDigest` | boolean        | нет         | `false` отключает запланированные сводки и напоминания                |
| `notifyAttention` | boolean     | нет         | `false` отключает немедленные письма-уведомления; in-app inbox продолжает работать |

Записываются только переданные ключи.

`PATCH /users/me/avatar` — это `multipart/form-data` с единственной частью
`file`. Изображение не более 2 МБ (`LIMITS.avatarSize`). Возвращает
обновлённого пользователя.

`GET /users/:userId/avatar` отдаёт изображение аватара любому
аутентифицированному пользователю. Имена блобов уникальны для каждой
загрузки, поэтому ответ можно кэшировать на длительный срок. Если у пользователя
нет аватара, сервер возвращает `404`.

Тело `POST /users/me/tokens`:

| Поле                 | Тип             | Обязательно | Ограничения                                                                                 |
| -------------------- | --------------- | ----------- | ------------------------------------------------------------------------------------------- |
| `name`               | string          | да          | не более 50 символов                                                                        |
| `expiresAt`          | string или null | нет         | ISO-8601; должен быть в будущем; пропуск означает 90 дней; `null` означает отсутствие срока |
| `boardId`            | string или null | нет         | привязать к одной доске, где владелец участник; `null`/пропуск означает все доски            |
| `readOnly`           | boolean         | нет         | при `true` любая запись отвечает `403 pat_read_only`; пропуск означает чтение и запись      |
| `rateLimitPerMinute` | integer или null | нет        | от 1 до 100000; `null`/пропуск означает отсутствие лимита на токен                          |
| `scopePreset`        | string          | нет         | `observer`, `worker`, `reviewer` или `admin`; пропуск означает `worker`; API применяет его, недопустимое значение отклоняется |
| `trustedCi`          | boolean         | нет         | разрешает destructive-действия без подтверждения, если политика доски не `destructive: "deny"`; пропуск означает `false`       |

Возвращает `{ token, apiToken }`. Полное значение `token` показывается один раз;
далее возвращаются только метаданные `apiToken`.
`GET /users/me/tokens` перечисляет метаданные (без полного значения токена).
`DELETE /users/me/tokens/:id` отзывает один токен и возвращает
`{ status: "ok" }`. Смена пароля отзывает все токены аккаунта. DTO токена
также содержит `scopePreset`, `trustedCi`, `individualPausedAt`/
`stopAllPausedAt` (и их `*By`), вычисляемый `paused` и
`effectiveTokenScope` (`observer` при `readOnly: true`). `GET /auth/me` с PAT
добавляет ту же несекретную идентичность в поле `token`.

## Уведомления внимания

Подтверждения, комментарии агента `blocker`/`handoff`, истёкшие захваты
карточек и исчерпание лимита досок создают одну дедуплицированную запись
in-app inbox. То же событие уходит письмом его человеческой аудитории —
активным ADMIN доски для подтверждений и заблокированных агентов,
заявителю и принявшему решение для решения/истечения, держателю захвата и
ADMIN для истёкшего захвата, самому аккаунту для предупреждения о лимите —
если аккаунт не выключил `notifyAttention`. API-токены никогда не получают
письма, а события досок, где пользователь больше не участник, скрываются.

| Метод | Путь | Возвращает |
| ----- | ---- | ---------- |
| `GET` | `/users/me/notifications?boardId=&unreadOnly=&cursor=&limit=` | `AttentionNotificationPage` |
| `POST` | `/users/me/notifications/:id/read` | `AttentionNotificationDto` |
| `POST` | `/users/me/notifications/read-all` | `{ updated }`; тело `{ boardId? }` |
| `GET` | `/users/me/notification-settings` | `NotificationSettingsDto` |
| `PATCH` | `/users/me/notification-settings` | `NotificationSettingsDto`; тело `{ notifyDigest?, notifyAttention? }` |

Все маршруты доступны только сессии браузера; персональный API-токен получает
`403 pat_forbidden`. Список идёт от новых к старым с непрозрачным курсором
`at:id` и `unreadCount`. `boardId` требует активного участия в доске. Типы
событий: `approval.requested`, `approval.decided`, `approval.expired`,
`agent.blocked`, `agent.needs_human`, `claim.expired`, `quota.exceeded`.
Запланированная сводка также один раз включает ещё не включённые в неё
категории внимания; немедленное письмо не задерживает запрос, который его
породил.

## Приглашения

Приглашение на доску — запись об участнике, ожидающая принятия (`acceptedAt: null`). Оно
не даёт доступа до принятия. Все маршруты требуют пользовательской аутентификации и
доступны только сессии браузера: персональный API-токен получает
`403 pat_forbidden` (TASK-166), поэтому агент не может перечислить или принять
приглашения владельца.

| Метод  | Путь                       | Возвращает             |
| ------ | -------------------------- | ---------------------- |
| `GET`  | `/invitations`             | `BoardInvitationDto[]` |
| `POST` | `/invitations/:id/accept`  | пустое тело, `200`     |
| `POST` | `/invitations/:id/decline` | пустое тело, `200`     |

`GET /invitations` перечисляет ожидающие, не истёкшие приглашения вызывающего,
сначала новые. `accept` ставит `acceptedAt`, после чего доска появляется в
`GET /boards`. `decline` удаляет строку. Истёкшее приглашение нельзя принять:
строка удаляется, а вызов отвечает `409`. Неизвестное или чужое приглашение
отвечает `404`.

Приглашения адресованы почтовому ящику, поэтому они ждут, пока аккаунт
докажет, что владеет им. Пока email не подтверждён, `GET /invitations`
возвращает пустой список, а `accept` отвечает `403`; после подтверждения
ожидающие приглашения появляются как обычно.

## Ленты активности

Доступны любому участнику, включая `VIEWER`.

| Метод | Путь                      | Возвращает         |
| ----- | ------------------------- | ------------------ |
| `GET` | `/boards/:id/activity`    | `ActivityFeedPage` |
| `GET` | `/cards/:cardId/activity` | `ActivityFeedPage` |

Оба принимают `?cursor=` (непрозрачный) и `?limit=`. Лимит по умолчанию 50,
максимум 100; лимит вне `1` до `100` отвечает `400`. Записи идут сначала
новые; `nextCursor` равен `null` в конце. Лента доски объединяет журнал
команд со строками `Activity`; лента карточки ограничена одной карточкой.

## Проверки работоспособности

`GET /health` проверяет, что процесс отвечает (liveness). Запрос не обращается
к базе данных и Redis и возвращает `200` с `{ "status": "ok" }`.

`GET /health/ready` проверяет готовность обслуживать запросы (readiness):
доступность базы данных и Redis, если он настроен. Ответ кэшируется на несколько
секунд. Обе проверки освобождены от глобального ограничения частоты.

```json
{ "status": "ok", "db": "up", "redis": "up" }
```

Если `REDIS_URL` не задан, `redis` имеет значение `disabled`. При недоступности
базы данных или настроенного Redis проверка готовности возвращает `503`
с `status: "error"` и состояниями зависимостей (`up` или `down`).

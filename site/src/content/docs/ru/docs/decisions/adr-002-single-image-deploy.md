## Контекст

Janosik поставляется как самохостимый продукт. История установки это
`docker compose up -d` на чистой машине, без отдельного веб-сервера, который
нужно настраивать. В репозитории лежат маркетинговый сайт на Astro (с доками
под `/docs`), React одностраничное приложение и NestJS API с его потоком SSE.

API ставит refresh-cookie с `SameSite=Strict`, а поток SSE это долгоживущее
соединение. И то и другое проще всего, когда сайт, приложение и API делят один
origin. Самохстеру не должно быть нужно настраивать CORS, домены cookie или
буферизацию прокси, чтобы получить рабочую установку.

## Решение

Один образ контейнера отдаёт весь продукт. Процесс NestJS отдаёт собранный
сайт Astro на `/`, SPA на `/app/` и API под `/api/v1`, используя переменные
окружения `SITE_DIR` и `STATIC_DIR`. `Dockerfile` собирает все три воркспейса
в один образ, а `docker-entrypoint.sh` прогоняет миграции Prisma на старте
перед запуском API.

`backend/src/common/serve-frontends.ts` реализует контракт маршрутизации:
хешированный вывод сборки кэшируется на год, `index.html` и `sw.js`
перепроверяются, неизвестные пути приложения падают на оболочку приложения, а
неизвестные пути сайта возвращают страницу 404 сайта. `deploy/nginx.conf`
описывает тот же контракт для развёртываний, которые ставят nginx вперёд.

## Последствия

### Положительные

- Один origin означает, что refresh-cookie и поток SSE работают без CORS и
  настройки прокси.
- Вся установка это `docker compose up -d`; обновление это
  `docker compose pull && docker compose up -d` с миграциями на старте.
- Контракт маршрутизации написан один раз и отражён в `serve-frontends.ts` и
  `nginx.conf`, поэтому развёртывание с прокси совпадает со встроенным.

### Отрицательные

- Образ несёт все три сборки, поэтому он больше, и любая пересборка фронтенда
  требует нового образа.
- Один процесс отдаёт и статику, и API, поэтому проблема со статикой может
  выглядеть как проблема API.
- Healthcheck проверяет и корень сайта, и API, поэтому контейнер, потерявший
  статику, помечается нездоровым, даже если API отвечает.

### Нейтральные

- nginx необязателен; `deploy/nginx.conf` нужен развёртываниям, которые
  добавляют прокси.
- Самохстер, который хочет внешний хостинг для сайта, может задать `SITE_URL`
  и `SITE_BASE`, а приложение остаётся на образе.
- Доки лежат под `/docs`, потому что этой веткой владеет Starlight, а
  маркетинговые страницы владеют корнем.

## Рассмотренные альтернативы

- **GitHub Pages для сайта.** Сильнейший аргумент за: бесплатный статический
  хостинг и свой домен без веса образа. Отклонён, потому что он отделяет
  origin от приложения, что ломает допущения о cookie и SSE и историю единой
  установки.
- **Отдельный контейнер nginx.** Сильнейший аргумент за: проверенный
  статический сервер, который масштабируется независимо от API. Отклонён для
  варианта по умолчанию, потому что добавляет движущуюся часть, которую
  самохстер обязан настраивать; `deploy/nginx.conf` остаётся доступным для тех,
  кому он нужен.
- **CDN для статики.** Сильнейший аргумент за: ниже задержка по миру и меньше
  нагрузки на процесс API. Отклонён для варианта по умолчанию, потому что
  добавляет внешнюю зависимость и работу по инвалидации кэша к продукту на
  одной ноде.

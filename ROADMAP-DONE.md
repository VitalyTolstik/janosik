### Fix — вложения в описании и обработка видео (2026-11-05)

Реализовано в ветке `fix/description-attachment-cleanup`; ожидает слияния.
Вставленные в описание файлы скрываются после удаления последней ссылки,
возвращаются при Undo и снова скрываются при Redo. Сохранённые для отмены и
снимков файлы можно удалить через отдельный раздел, освободив лимит; отдельные
вложения не удаляются. Для старых загрузок происхождение не определяется.
Видео преобразуются в H.264/AAC MP4; исходный MP4 сохраняется, если результат
не меньше, а другие форматы преобразуются для совместимости. При ошибке остаётся
исходный файл. Покрыто браузерными E2E (Undo/Redo, очистка, MOV и воспроизведение),
серверными E2E и unit-тестами; обновлены README и документация en/ru.

#### TASK-2 — `card-mdx-editor` · WYSIWYG-редактор описания (MDXEditor)

- **Статус:** ✅ реализовано (ветка `feature/TASK-2-mdx-description-editor`).
- **Зачем:** кнопки форматирования вместо ручного ввода Markdown; живой
  WYSIWYG вместо пары «textarea + превью».
- **Решение (обновлено пользователем):** официальный `@mdxeditor/editor`
  вместо самописного тулбара над textarea. react-markdown/remark-*
  полностью удалены — MDXEditor используется и для редактирования, и для
  read-only превью на карточке.
- **Что сделано:**
  - `DescriptionEditor` (edit, тулбар: undo/redo, тип блока, bold/italic,
    strikethrough, inline code, bullet/numbered/checklist, link) и
    лицо карточки текст описания не показывает (как в Trello): если
    описание есть — компактный бейдж с lucide-иконкой и тултипом
    `card.hasDescription`, если нет — ничего; полный текст живёт в диалоге
    карточки;
  - курируемый набор фич: заголовки, списки (включая `- [x]`), цитаты,
    ссылки, inline-код, `---`. Таблицы/код-блоки/картинки — плагины
    включены без кнопок, чтобы старые данные (сид/импорт) круглосуточно
    реэкспортировались без ошибок;
  - безопасность: `suppressHtmlProcessing` — сырой HTML из текста
    (импорт JSON/вставка) остаётся буквальным текстом, не исполняется;
    плюс собственная санитизация `sanitizeMarkdownForImport`: у image-плагина
    MDXEditor есть `innerHTML`-сток (`MdastImageVisitor` для HTML-`<img>`,
    подтверждено PoC — `<img src=x onerror=…>` исполняется даже с
    `suppressHtmlProcessing`), а прочий сырой HTML роняет импорт целиком.
    Санитайзер вырезает сырой HTML до подачи в редактор; инвариант —
    «в AST после санитизации нет ни одного `html`-узла» — проверяется
    дифференциально против настоящего remark-парсера: регрессионные
    обходы (backtick в info-строке fence, пары бэктиков, escaped-бэктики,
    продолжение html-блока) + 10 000 детерминированных fuzz-комбинаций;
    HTML в fenced-блоках сохраняется (там он для remark — инертный текст),
    в inline-коде — вырезается (fail-safe: точное зеркало парсинга
    бэктиков в micromark невоспроизводимо, а ошибочная «защита» экранирует
    живой тег); ссылки дополнительно защищены `@lexical/link`
    (протокол-allowlist, `javascript:` → `about:blank`);
  - иконки заменены на lucide через официальный проп `iconComponentFor`;
  - i18n: проп `translation` завязан на каталоги `editor.*` (en/ru);
  - темы: все цвета редактора — на дизайн-токенах (`index.css`, блок
    MDXEditor), тёмная/светлая работают автоматически, без классов
    `dark-theme`; тулбар/контент переписаны под токены (Tailwind preflight
    обнуляет типографику — она восстановлена явно);
  - попапы (link dialog, dropdown типа блока) порталится в `document.body`
    и поднимаются `z-index` над диалогом: центрирование диалога делает
    `transform`, который ломает координаты `position: fixed` внутри него —
    поэтому `overlayContainer` внутрь диалога передавать нельзя;
    тултипы кнопок оформлены (токены вместо нечитаемого дефолта);
  - модалка ссылки центрирована (`:has()` по классу попапа) с крестиком
    в правом верхнем углу (Cancel-контрол с lucide X через CSS-маску —
    в библиотеке он текстовый, без иконки); центрируется ТОЛЬКО форма
    редактирования, а превью-поповер при клике на ссылку остаётся
    привязанным к самой ссылке: для этого Radix-диалог центрируется
    через `inset-0 + margin auto`, а не `transform` — transform делает
    диалог containing block для `position: fixed` потомков, и якорь
    превью (viewport-координаты) молча улетал мимо ссылки; у
    центрированной формы библиотечный «хвостик»-стрелка скрыт (Radix
    ставит инлайн `display: block` — гасится `!important`); полей два —
    URL и текст ссылки (текст показывается, только когда некуда
    крепить), поле HTML-`title` выключено (`showLinkTitleField: false`);
    в превью-поповере ссылки кнопки (редактировать/копировать/убрать)
    приведены к размеру остального хрома редактора (иконки 15px вместо

    чекбоксы чек-листа выровнены в одну линейку с маркерами списков и

    с бордером-токеном, отмеченные — заливка `--primary` + белая галочка;
  - диалог карточки расширен до `sm:max-w-3xl`, грид-трек `minmax(0,1fr)`
    против переполнения на мобильных.

  ```ts
  const apply = useCallback((action: BoardAction) => {

  }, []);
  ```
  Редьюсер чист, поэтому значение в рефе всегда совпадает с тем, что
  закоммитит React; эффект синхронизации `stateRef` остался страховкой.
- **⚠️ На TASK-21.7d:** этот фикс — про **снапшоты**. Когда история
  переедет на пары `{do, undo}`, механизм исчезнет вместе со снапшотами,
  но **причина останется**: инверсия тоже считается от состояния «до», и

    возвращался бы на каждом дебаунс-сохранении;
  - исчезает сам, как только успешная запись проходит под порогом;

#### TASK-21.7 — `history-inverse` · Undo на инверсных командах (21.7a+b+c+d) ✅

- **Статус:** ✅ реализовано, ветка `feature/TASK-21.7-history-inverse`.
  §6.0.1 разбивала задачу на 4 PR («неревьюабельный ком»); пользователь
  попросил один PR — разбивка сохранена как порядок коммитов a→b→c→d.
- **Зачем.** `BoardHistory` хранила до 50 снапшотов `Board` и делала undo
  через `RESTORE_BOARD` целой доски: в памяти — десятки мегабайт, а в
  совместном режиме такой undo затирает чужие правки (Аня откатывает свою —
  исчезает правка Бориса). Undo должен быть **компенсацией** (селективный
  undo, как в Figma/Linear). Инверсию, однако, нельзя было даже вычислить:
  редьюсер сам звал `createId()` (9×) и `Date.now()` (16×), поэтому
  `ADD_CARD` не знал id созданной карточки, а ни один экшен не был
  воспроизводим.

**21.7a — детерминизм (корень).** Всё, что редьюсер записывает, приходит в
payload: `at` (одни «часы команды» на `updatedAt`/`createdAt`/`archivedAt`/
события ленты), id создаваемых сущностей с префиксом `new`
(`newCardId`, `newColumnId`, `newChecklistId`, `newItemId`, `newCardIds[]`)
и `activityIds[]` для событий активности. Префикс `new` выбран осознанно:
он отличает *создаваемый* id от *ссылки* (`cardId`), и тестовый хелпер
может безопасно делать такие поля необязательными. Третий аргумент
`boardReducer(state, action, { withActivity: false })` выключает ленту (для
сервера, §7.4.1) — карточка создаётся **без поля** `activity`, а не с
пустым массивом. DoD: `grep -c "createId()\|Date.now()"
src/store/board-reducer.ts` → **0**; правило записано в `AGENT.md`.

**21.7b — обратимость структурой.** `TOGGLE_CARD_LABEL` →
`SET_CARD_LABEL {on, index?}` (index — чтобы undo вернул метку на её место
в списке, а не в конец), `TOGGLE_CHECKLIST_ITEM` →
`SET_CHECKLIST_ITEM_DONE {done}`, `MOVE_CARD.fromIndex`, новый
`SET_COLUMN_CARD_ORDER {cardIds}` (инверсия `SORT_COLUMN`; принимает только
перестановку текущих id — иначе команда игнорируется),
`UNARCHIVE_CARD.index` (заодно закрыт баг §3.2 WARNING: восстановление из
архива больше не роняет карточку в конец колонки), `ARCHIVE_CARD.archivedAt`
(инверсия разархивации возвращает карточку в архив **с её датой**).
Сигнатуры удобных экшенов в UI не менялись: `toggleCardLabel(cardId,
labelId)` остался, но относительное намерение разрешается в абсолютное
значение в action creator'е — через `getActiveBoard()` из провайдера.

**21.7c — восстановление.** `RESTORE_CARD` (с колонкой и индексом; у
архивной карточки колонки нет), `RESTORE_COLUMN` (+ её карточки),
`RESTORE_LABEL` (+ `assignments: {cardId, index}[]` — метка возвращается
ровно туда, где висела), `RESTORE_CHECKLIST`, `RESTORE_CHECKLIST_ITEM` и
сверх списка §6.0.1 — `RESTORE_COLUMN_CARDS` (инверсия массового архива
колонки; карточки, добавленные после архива, остаются в конце, а карточки из
payload, которых нет в `cardIds`, из колонки убираются — поэтому команда
является точной инверсией самой себя). Явно отправленное восстановление
(консоль, импорт) уважает `LIMITS` и WIP; восстановление **как undo** —
никогда не отклоняется, см. ниже.

**21.7d — история на инверсиях.** `src/store/invert.ts`:
`invert(before, action)` считает инверсию в момент dispatch, пока состояние
«до» ещё известно; `never`-проверка полноты union'а — новый экшен без
инверсии **не компилируется**. `BoardHistory` хранит пары `{do, undo}` и
ни одного объекта `Board`. Undo отправляет `undo` с новым `at` (события
ленты — правдивые «сейчас»), redo пересылает исходный `do` **дословно**, но
с новым `commandId` (старый израсходован как ключ идемпотентности).
Коалесцинг сохранён: серия `UPDATE_CARD`/`TOUCH_CARD` по одной карточке
держит самое старое «до» и самое свежее «после». Задел под SSE:
`push(before, action, { foreign: true })` не пускает чужую команду в стек,
**не** чистит redo, разрывает коалесцинг и помечает пересечённые шаги
`dead` (undo их пропускает). И коалесцинг мёртвый шаг **не оживляет**:
правка той же карточки после чужой команды начинает свежий шаг, а не
продлевает убитый (иначе undo такого шага затёрло бы чужую правку).
История вынесена из `BoardContext` в
`src/store/use-undo-history.ts` (стеки по доскам, `canUndo`/`canRedo`,
хоткеи) — тот самый seam, который §7.5 требовал к TASK-29.

- **Точная обратимость — как достигнута.** Undo возвращает доску
  **побайтово**: `updatedAt` доски и карточки, позиции, лента активности.
  Механизм — четыре inverse-only поля, которые ставит только `invert()`
  (ни UI, ни сервер): `boardUpdatedAt`/`cardUpdatedAt` пишут старые штампы
  вместо `at`; `cardActivity` возвращает ленту карточки в то состояние, в
  котором инверсия её нашла (undo переименования не добавляет второе
  «renamed», а убирает первое — и это же чинит коалесцинг ленты и
  вытеснение по лимиту 50 событий); `inverse: true` — см. следующий пункт.
  Инвариант проверяется **в двух режимах** — с лентой (как работает
  приложение) и с `withActivity: false` (как будет работать сервер).
- **Undo нельзя отклонить.** Коллекционные гварды (`LIMITS`, WIP) стоят на
  пути *нового* контента; инверсия ничего нового не добавляет — она
  возвращает только что убранное, поэтому для команд с `inverse: true`
  гварды не применяются. Отказ undo — худший из возможных исходов
  (Ctrl+Z молча ничего не делает, а удалённая по ошибке карточка потеряна
  навсегда); колонка, на минуту вышедшая за лимит, — состояние, которое в
  приложении уже бывает (импорт, лимит опущен ниже текущего числа) и
  честно показывается красным счётчиком. Ограничения длины текста

## TASK-50 `video-transcode` — выполнено (2026-09-21)

Ветка `feature/TASK-50-video-transcode` от `main`. Запрос владельца: «ужиматор видео с минимальной потерей качества, как у топ-ресурсов».

### Как работает

- **Загрузка** видео (`video/*` из allowlist) пишется на диск сразу и отдается клиенту со статусом `pending` — вложение играет моментально, ничего не блокирует. Фоновая задача (`TranscodeService`, in-process FIFO, один кодек за раз) перегоняет файл в **H.264/AAC MP4**: CRF 25, preset medium, ширина ≤1920 (`scale='min(1920,iw)':-2`), yuv420p, `+faststart` — визуально прозрачное качество, на записях экрана минус 50–80% размера.
- **Подмена атомарна**: кодирование в `.tmp-*.mp4` рядом, `rename` на финальное имя, обновление строки (`storedName`, `mimeType: video/mp4`, `sizeBytes`), удаление оригинала. `content`-URL не меняется никогда — `<video>` в карточках и встроенные `::video` в описаниях продолжают играть без перезагрузки. `Content-Type` раздаётся из строки, так что после подмены отдаётся правильный mime.
- **Отказоустойчивость**: ffmpeg упал или таймаут (10 мин) → `failed`, tmp-файл удалён, **оригинал остаётся и играется как есть**. Гонка с удалением вложения во время кодека проверяется `updateMany.count` — проигравший удаляет свежий MP4. Рестарт сервера посреди кодека ничего не теряет: `onModuleInit` переставляет все `pending`-строки в очередь.
- **Бинарик** — `ffmpeg-static` (скачивается с пакетом, ни brew, ни системного ffmpeg не нужно); оверрайд `FFMPEG_PATH` для кастомных сборок.

### Состояния и UI

`Attachment.transcodeStatus`: `none` (не видео) / `pending` / `done` / `failed`. В списке вложений у кодируемого ряда — плашка «Encoding… / Сжимаем…» со спиннером; завершение прилетает SSE-фреймом `attachment_updated` (новый kind `activity`-канала), диалог перечитывает ряд — размер/статус обновляются на живом экране. В админке — колонка «Encode» со статус-чипом (done — зелёный, failed — красный, pending — серый).

### Попутный фикс хранилища (PR #92)

Расследование «пропавших файлов» вскрыло, что дефолт `UPLOAD_DIR` был **относительным** (`data/uploads` от cwd процесса): сервер, запущенный из другой папки, молча получал пустое хранилище, а все прежние блобы становились 404 при живых строках БД. Теперь дефолт якорится к папке backend (`__dirname`-based), `UPLOAD_DIR` описан в `.env.example`, а resolved-корень логируется на старте — расхождение видно сразу.

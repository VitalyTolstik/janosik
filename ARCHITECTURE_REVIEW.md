## 1. Резюме

**Janosik** — премиально оформленный клон Trello на стеке **React 18 + TypeScript (strict) + Tailwind CSS v4 + Vite**. Это однопользовательское, полностью клиентское приложение: все данные живут в `localStorage`, серверной части нет.

Сильные стороны:

- Чистая, хорошо структурированная кодовая база с сильной типизацией;
- Нормализованная модель данных, чистый reducer (легко тестируется и готов к undo/redo);
- Аккуратная дизайн-система на токенах, две темы, i18n с типобезопасными ключами;
- Продуманные микро-детали: префлайт темы (без «мигания»), миграция данных при ребрендинге, `prefers-reduced-motion`, кастомные скроллбары, анимации на GPU;
- Хорошее покрытие тестами чистой логики.

Главный стратегический вывод: **фронтенд-фундамент готов**, и его не нужно переписывать. Дальнейший рост лежит в трёх направлениях:

1. **Расширение модели данных** (описание карточки, сроки, чек-листы — то, что сейчас отсутствует);
2. **Многопользовательность и синхронизация** (бэкенд NestJS + Prisma + SQL, авторизация);
3. **Многодосочность** (модель уже готова к `Board[]`, не хватает UI и роутинга).

## 2. Что уже реализовано (инвентаризация)

### Данные и состояние

| Слой | Что есть |
| --- | --- |
| Модель | `Board` → упорядоченные `Column[]`, карточки в нормализованном `Record<string, Card>`, `labels`. Карточка: `title`, `labelIds[]`, `createdAt`, `updatedAt`. |
| Состояние | `useReducer` + чистый `boardReducer` (14 экшенов), `Board[]` (используется только индекс 0). |
| Персистентность | `localStorage` (`janosik-boards`), сохранение после каждого изменения, безопасная работа с ошибками. |
| Миграции | `migrateStorageKey` (ребрендинг Vortex→Janosik), `normalizeBoards` (v1 `labelId` → v2 `labelIds[]`). |
| Seed | Демо-доска «Product Launch» при первом запуске. |

### Функции доски

- CRUD колонок (добавление, переименование, удаление с каскадом карточек);
- CRUD карточек (создание через inline-композер, редактирование заголовка, удаление с подтверждением);
- Drag & drop: карточки (внутри/между колонками) и колонки (горизонтальная перестановка), включая клавиатурный сенсор, `DragOverlay`, подавление ложного клика после drop;
- Метки: 14 цветов, мульти-выбор, создание/переименование/перекраска/удаление (каскад со всех карточек);
- Фильтр: поиск по названию, метки (ANY + «без метки»), окно даты создания (сегодня/7/30 дней), точный день через календарь; горячие клавиши `/` и `Ctrl/Cmd+K`; счётчик совпадений; DnD отключается при активном фильтре;
- Перемещение карточки в другую колонку из диалога карточки.

### Дизайн-система

- Токены Tailwind v4 (`@theme inline` + CSS-переменные), тёмная тема по умолчанию, светлая через `.light`;
- Бренд: Space Grotesk (self-hosted), анимированный логотип «Перо Яношика», живая иконка-палитра/язык/тема с микровзаимодействиями;
- 4 пресета фона доски (solid / paper / dots / grid) с тематическими вариантами и компактными превью в пикере;
- UI-примитивы на Radix (dialog, dropdown, popover, tooltip, slot) + shadcn-стиль;
- i18n (en/ru) с типобезопасными ключами и плюрализацией.

### Тесты

68 тестов в 7 файлах: reducer, dnd-логика, фильтр, storage, миграции, i18n, интеграционный тест BoardSection.

## 3. Замечания по коду (что стоит улучшить)

Это не баги, а архитектурные/качественные наблюдения.

### 3.1. Персистентность — единственная точка потери данных

- **`localStorage` — единственное хранилище.** Лимит ~5 МБ, нет экспорта/импорта, нет резервного копирования, нет синхронизации между устройствами/вкладками. Любая очистка кэша браузера стирает всё.
- **Сохранение на каждое нажатие клавиши.** В `CardDialog` заголовок обновляется через `updateCard` на каждый `onChange`, а `BoardContext` пишет весь стейт в `localStorage` после каждого изменения. Это работает, но неэффективно (полная сериализация доски на каждый символ) и избыточно меняет `updatedAt`. Рекомендация: дебаунс сохранения (например, 300–500 мс) и/или отдельный `updatedAt` для «реального» редактирования.

### 3.2. Одна доска из `Board[]`

- Модель `BoardState = Board[]` уже заложена, но реально используется только `state[0]`. `commit()` всегда пишет в `state[0]` и сохраняет `state.slice(1)` — «мёртвая» обвязка до появления мультидосок.
- Нет UI для: переименования доски (заголовок `board.title` отображается, но не редактируется), создания/удаления/дублирования/архивирования досок, переключения между ними.

### 3.3. Модель карточки минимальна

- `Card` содержит только `title`. Нет поля описания/заметок, сроков, чек-листов, вложений, обложки, исполнителей, истории. Это главный функциональный разрыв с Trello/Linear.

### 3.4. Отсутствие undo/redo и «мягкого» удаления

- Reducer чистый — история действий добавляется тривиально. Сейчас все удаления перманентны («нельзя отменить» — это правда и рискованно).
- Нет корзины/архива: удалённое исчезает навсегда.

### 3.5. Роутинг

- Нет `react-router-dom` (и не нужен, пока одна доска). При переходе к мультидоскам понадобится URL-адресация `/board/:id`.

### 3.6. Мелкие замечания

- `CardDialog` — неконтролируемая `Textarea` с автофокусом и `onFocus select()`; поведение норм, но «живое» сохранение на каждый символ (см. 3.1).
- Нет `ErrorBoundary` — ошибка рендера уронит всё приложение.
- Нет toast-уведомлений (например, при переполнении квоты `localStorage` пользователь ничего не узнает — `saveJSON` молча возвращает `false`).
- Тесты покрывают логику, но нет E2E (Playwright/Cypress) и нет тестов drag-интеракций и диалогов.
- `MeasuringStrategy.Always` в DnD — корректно для малых досок, но на сотнях карточек может стать дорогим; при масштабе потребуется виртуализация списков.
- Семантически `noLabel` в фильтре объединён с `labelIds` через OR — это осознанный выбор, но стоит явно задокументировать/предложить переключатель «ANY / ALL» для меток.
- Seed-данные на английском не переводятся (осознанно — данные не локализуются), но новым русскоязычным пользователям было бы приятнее видеть русский демо-контент или пустую доску.

## 4. Предложения новых функций (по критичности)

Легенда:

- 🔴 **Критично** — без этого продукт неполноценен для реального использования;
- 🟠 **Высокий приоритет** — ожидаемые функции канбан-доски;
- 🟡 **Средний** — заметно улучшают UX;
- 🟢 **Низкий** — полировка;
- ⚪ **На будущее** — дифференциаторы/масштаб.

### 🔴 Критично

1. **Поле описания/заметки в карточке** *(запрошено)*
   Добавить `description: string` в `Card`, поле в `CardDialog` (многострочное, с автосохранением по дебаунсу). Это база для Markdown, чек-листов и истории. Минимально — plain text, далее — Markdown-рендеринг.

2. **Бэкенд + авторизация + хранение (NestJS + Prisma + SQL)** *(запрошено)*
   NestJS API (`/api/boards`, `/api/cards`, …), Prisma ORM, сначала SQLite/PostgreSQL, JWT-авторизация (или OAuth). Фронтенд **не мигрирует** — добавляется слой `fetch` к `/api`, текущий reducer остаётся, синхронизация через тот же dispatch. Это даёт: многопользовательность, синхронизацию между устройствами, защиту от потери данных.

3. **Экспорт/импорт данных (JSON) + авторезерв**
   Пока бэкенда нет — это дешёвый способ не терять данные. Экспорт всей доски в JSON, импорт с валидацией, автосохранение снапшотов.

4. **Undo/redo**
   История действий поверх чистого reducer (стек прошлых состояний или action-лог). Критично, потому что сейчас все удаления необратимы.

5. **Мультидоски**
   Список досок, создание/переименование/дублирование/удаление/архивирование, переключение. Модель уже готова (`Board[]`) — нужен роутер (`react-router-dom`) и UI.

### 🟠 Высокий приоритет

1. **Сроки (due dates) на карточках** — дата и время, подсветка просроченных (красным), «скоро» (жёлтым), сортировка по сроку, напоминание. Классическая функция Trello. `react-day-picker` уже в стеке.

2. **Чек-листы (подзадачи)** — список пунктов с прогрессом («2/5») прямо на карточке и в диалоге.

3. **Редактирование названия доски + настройки доски** — сейчас заголовок доски не редактируется.

4. **История/активность карточки** — лента «создана / изменена / перемещена», используя уже имеющиеся `createdAt`/`updatedAt` и расширив модель.

5. **Архивирование (мягкое удаление)** — карточки/колонки/доски в архив вместо перманентного удаления, с восстановлением.

6. **WIP-лимиты колонок** — лимит карточек на колонку, предупреждение при превышении (канбан-стандарт).

7. **Обложка/цвет карточки** — цветная полоса или обложка-градиент для визуального различия (есть только метки).

8. **Копирование/дублирование карточки и колонки** — быстрое копирование с сохранением меток.

### 🟡 Средний приоритет

 1. **Комментарии на карточках** — локально возможны сразу; при бэкенде — полноценные (нужен пользователь/автор).

 2. **Исполнители (assignees)** — локально список «людей», при бэкенде — реальные пользователи.

 3. **Расширенный поиск** — по всем карточкам/доскам, fuzzy, поиск в описании, поиск по меткам через строку.

 4. **Сортировка внутри колонки** — по дате создания, по сроку, по названию, ручная.

 5. **Переключатель меток ANY/ALL** в фильтре (сейчас только ANY).

 6. **Палитра горячих клавиш** — `?` со списком (`n` — новая карточка, `c` — новая колонка, `j/k` — навигация, `e` — редактировать).

 7. **Шаблоны досок и повторяющиеся карточки** — создание доски по шаблону, автоповтор задач.

 8. **Вложения (файлы)** — при бэкенде: загрузка файлов; локально: ссылки.

### 🟢 Низкий приоритет

 1. **Пользовательские фоны** — загрузка своего изображения/градиента (градиенты ранее убраны; вернуть как «кастомный» слой).

 2. **Иконки/эмодзи** на доске и колонках.

 3. **Прогресс-бар колонки** — процент завершённого (по метке Done или по WIP).

 4. **PWA/offline** — service worker, установка на рабочий стол, работа без сети (логично для чисто клиентского приложения).

 5. **Markdown в заголовках/описании**.

 6. **ErrorBoundary + тосты** — явная индикация ошибок (квота localStorage, сбой сети).

 7. **E2E-тесты** (Playwright) на главные сценарии: создать карточку, перетащить, удалить.

### ⚪ На будущее

 1. **Календарное представление** — карточки по срокам (календарь уже есть в стеке).
 2. **Автоматизации (аналог Butler)** — «при переносе в Done — проставить дату/метку».
 3. **Тайм-трекинг**, оценки времени.
 4. **Уведомления** (браузер/email/push) по срокам и упоминаниям.
 5. **Рабочие пространства (workspaces) и роли** — при бэкенде.
 6. **Timeline/Gantt** представление.

## 6. Рекомендуемый порядок работ

Порядок согласован: **сначала «заземления» и фронтенд, бэкенд — после того, как
модель данных устоится**. «Сначала бэк» — ловушка, вот почему:

- Главный мотив бэкенда-первого — риск потери данных (localStorage — единственное
  хранилище, § 3.1). Но он снимается дешевле: экспорт/импорт JSON + авто-бэкап
  (страховка на несколько итераций, без сервера).
- Бэкенд — самый рискованный и длинный кусок; пока он строится, продукт остаётся
  с критичными дырами (нет описания карточки — 🔴-разрыв с Trello/Linear).
- Схема бэкенда «выстрелит в молоко» без устоявшейся модели: сейчас `Card` —
  только `title`; сначала фронт-фичи расширяют payload (описание, сроки,
  чек-листы), затем Prisma-схема копирует устоявшуюся модель один раз.
- Фронт при бэкенде не мигрирует (уже решено: слой `fetch` поверх reducer) — нет
  причины тянуть бэкенд вперёд «чтобы не переделывать».
- Бэкенд реально блокирует лишь комментарии/исполнителей/вложения (нужны
  пользователи) — поэтому его место ровно перед этими фичами.

### Шаг 0 — «Заземления» (фронтенд, без новых фич)

1. **Слой персистентности** `BoardPersistence` + дебаунс сохранения (300–500 мс):
   чинит § 3.1 (запись на каждую клавишу); бэкенд позже = второй адаптер вместо
   localStorage, reducer и UI не трогаются.
2. **Undo/redo**: reducer чистый, 14 экшенов — история дешевле сейчас; action-лог
   станет базой будущего sync-протокола.
3. **Экспорт/импорт JSON + авто-бэкап**: страховка данных до бэкенда; формат
   экспорта = будущий формат seed для сервера.
4. **ErrorBoundary + тосты**: убирает «молчаливый» сбой квоты (§ 3.6); при
   сетевых ошибках бэкенда будут незаменимы.

### Шаг 1 — Фронт доделать по критичности

1. Описание карточки (+ дебаунс — уже заложен в Шаге 0.1).
2. Мультидоски + роутер (`react-router-dom`); заодно чинится «мёртвая» обвязка
   `commit()` из § 3.2.
3. Архив вместо перманентного удаления + редактирование названия доски.
4. Сроки (due dates), затем чек-листы — расширяют ту же модель без переделок.

*Развилка:* мультидоски можно делать и до сроков (предложено), и после — это
изолированный UI-слой, разница минимальна.

### Шаг 2 — Бэкенд (последний, но не «когда-нибудь»)

- NestJS + Prisma + SQL + JWT; схема копирует уже устоявшийся payload (описание,
  сроки, чек-листы уже в нём).
- Фронт получает **второй адаптер** `BoardPersistence` (`fetch` → `/api`); reducer
  и UI не трогаются. Синхронизация: сначала полный снапшот доски на debounced-save,
  позже — при необходимости — delta.
- Сразу после: комментарии / исполнители / вложения — только тогда им есть на чём стоять.

### Шаг 3 — Масштаб / дифференциация

Календарь, автоматизации, уведомления, PWA, E2E.

Такой порядок сохраняет текущий фронтенд нетронутым на первых шагах (никакой
миграции при добавлении бэкенда — только слой `fetch`), что соответствует уже
принятому решению «не переезжать на Next.js и не переписывать стек».

## 1. Executive verdict

Аудит в целом **точный**: ни один из 16 пунктов не является выдуманным или уже исправленным, ложных срабатываний нет. Но смешивать «отсутствующую ссылку», «осознанно узкий read-only экран» и «настоящий баг» нельзя.

| **FALSE POSITIVE / STALE** | **0** | Все проверенные утверждения подтвердились. |

**Прямой ответ на «надо ли фиксить или это так задумано»:** часть — задумано (read-only карточка, отсутствие master-контура агентов, отсутствие редактирования комментариев как продуктовой функции). Но потерянные ссылки, отсутствие структурных фильтров и лимиты, которые выглядят как полные списки, — **не задуманы**, а массовая операция между страницами — **настоящий баг**. Первой волной стоит закрыть bulk, затем «честность» счётчиков/выборок, затем дешёвые ссылки автор/актор/пригласивший. Полный редактор карточки и редактирование комментариев — отдельные продуктовые решения, не багфиксы.

## 3. Пункты 15–16: частичные данные и счётчики

### 15. Профиль пользователя — **REAL BUG**

**Что подтверждено:**

- `backend/src/admin/admin-entities.service.ts:1086` — `take: 500` для команд `ADD_CARD`/`DUPLICATE_CARD`;
- `:1117` — memberships `take: 100`;
- `:1134` — createdCards `take: 100`;
- `:1140` — assignedCards `take: 100`;
- `:1145-1175` — comments/attachments/sessions/tokens/recentCommands/recentActivity по `take: 25`;
- `:1212` — `cardsCreated: createdCards.length`, то есть счётчик равен длине ограниченной выборки, а не полному числу;
- `UserDetailPage.tsx:299-350` — бейджи вкладок используют `detail.<list>.length`;
- `site/src/content/docs/docs/admin/people.md:126` — «Cards created — cards derived from the command log as created by the user», `:136` — «nine tabs, each with a count». Документация не говорит «первые 25/100».

**Почему это баг, а не просто лимит:**

1. Счётчик «Cards created» может показывать `100` при 150 созданных — это не «приблизительно», а неверное число с подписью полного.
2. Вкладки comments/attachments/sessions/tokens включают soft-deleted/revoked/expired строки, а соответствующие `counters` — только живые/активные. То есть бейдж вкладки и соседний счётчик могут противоречить друг другу.
3. Хуже: deleted-комментарии и revoked-сессии занимают те же 25 слотов. У пользователя с 25 удалёнными комментариями вкладка покажет только их и скроет живые.

**Что делать:** не обязательно убирать лимиты. Достаточно:

- показывать `25 из 37` / `100+`, используя точные `counters`, где они есть;
- добавить пагинацию/«load more» на вкладки;
- для created cards либо считать точное число (дорого из-за отсутствия `Card.creatorId`), либо честно писать «последние 100» и не называть это полным счётчиком;
- фильтровать deleted/revoked по умолчанию или явно помечать, что они входят в выборку.

**Effort:** M. **Prio:** P1 (влияет на выводы поддержки; счётчик «Cards created» может быть прямо неверным). **Риск:** средний — нужно не сломать производительность и не разойтись с определениями счётчиков.

### 16. Карточка — **REAL BUG**

**Что подтверждено:**

- `admin-entities.service.ts:1319` — comments `take: 50`, без `deletedAt: null`;
- `:1334` — attachments `take: 50`, без `deletedAt: null`;
- `:1385/1391` — activity/commands `take: 30`;
- `:1417` — после merge `slice(0, 50)`;
- `CardDetailPage.tsx:378` (attachments), `:427` (comments), `:465` (timeline) — блоки без пагинации и без индикатора «показаны последние 50».

**Почему это баг:**

- Блок выглядит полным; при 60 комментариях пользователь не узнает, что 10 старых не показаны.
- Soft-deleted комментарии/файлы занимают слоты в этих 50. Если на карточке много удалённых комментариев, живые могут вообще не попасть в выборку.
- Глобальный поиск (п. 11) усугубляет: найденный старый комментарий ведёт на карточку, где его нет в первых 50.
- `AdminCardDetailDto.card.commentIds` содержит все видимые комментарии, а `attachmentCount` — точное число; их можно использовать для «50 из N» без нового тяжёлого запроса.

**Что делать:** пагинация/«load more» для comments/attachments, `N из M` для timeline, якорь/подсветка при переходе из поиска, отдельный тест на >50 с удалёнными строками.

**Effort:** M. **Prio:** P2. **Риск:** средний — контракт DTO и производительность.

## 5. Bulk-selection bug: deep dive

### Подтверждение

Да, баг реален и воспроизводится по коду. Ключевые точки:

- `ui/src/admin/EntityPage.tsx:208` — `const [selected, setSelected] = useState<Set<string>>(new Set())`.
- `:217` — `allSelected` считается только по `visibleIds`.
- `:240-253` — `runBulk`:
  ```ts
  const ids = visibleIds.filter((id) => selected.has(id));
  ```
  То есть в запрос уходят только ID текущей страницы.
- `:343-346` — панель показывает `selected.size`.
- `:506` — подтверждение показывает `selected.size`.
- `:495` — `Pagination` меняет `offset`, но никакой эффект не очищает `selected`.
- `ui/src/admin/use-admin-list.ts:64+` — `offset/limit/search/status/period` живут локально; смены страницы/фильтра не трогают `selected`.

### Repro

1. Открыть `/admin/boards` (или cards/comments/attachments — любой `bulk: true`).
2. Выбрать строку A на странице 1.
3. Перейти на страницу 2.
4. Выбрать строку B.
5. Панель показывает «2 selected»; нажать Delete; confirm показывает «Delete 2 items?».
6. Уходит `POST /admin/entities/boards/bulk` с `{"ids": ["B"], "action": "delete"}` — только ID текущей страницы.
7. B удаляется, A остаётся. При полном успехе `setSelected(new Set())` очищает и A; тост «Deleted»; пользователь уверен, что удалил оба.

### Expected vs actual

- **Expected:** либо удалены оба (A и B), либо счётчик/подтверждение честно говорят «1 на этой странице» и выбор сбрасывается при смене страницы.
- **Actual:** подтверждено 2, отправлен 1, второй тихо остаётся; выбор очищается.

### Варианты

- Смена `search/status/period/limit` также оставляет невидимые выбранные ID. Если список после фильтра пуст, bulk-панель исчезает, но `selected` жив; при возврате к списку строки снова отмечены.
- То же для restore: часть выбранных досок/карточек не восстановится, но тост будет успешным.
- При частичной ошибке (`result.failed`) в `selected` остаются только failed ID — это корректно, но только для отправленного набора.

### Тесты

- `e2e/tests/admin/boards.spec.ts:85-140` (B5) проверяет bulk delete/restore/clear **на одной странице**; смены страницы нет.
- Компонентные тесты (`EntityPage.skeleton.test.tsx`) проверяют только skeleton/колонки, не selection.
- То есть регрессия не покрыта.

### Smallest safe fix

Рекомендуемый контракт: **выбор живёт между страницами, действие применяется ко всем сохранённым ID; при смене фильтра/поиска выбор очищается.**

```ts
const ids = [...selected];
if (ids.length === 0) return;
if (ids.length > 500) {
  // backend AdminBulkDto: ArrayMaxSize(500)
  toast.error(...);
  return;
}
```

Почему так:

- счётчик, confirm и запрос начинают совпадать;
- не теряются выбранные на других страницах;
- 500 — реальный серверный лимит (`backend/src/admin/dto/admin-v3.dto.ts:94-103`), его нужно проверить на клиенте, иначе 6 страниц по 100 дадут 400.

Дополнительно:

- очищать `selected` при изменении `search/status/period/limit` (но не `offset`), чтобы не действовать на скрытые после фильтра строки;
- показывать в панели «N selected (M on this page)», если хочется прозрачности;
- E2E: 26+ строк, page size 25, выбрать на двух страницах, удалить, проверить оба ID и тело запроса. Либо компонентный тест с mock-страницами.

**Effort:** S. **Prio:** P1. **Риск:** низкий для `setSelected`; средний для контракта «действие по всем ID» — нужен guard на 500 и осознанное поведение при смене фильтра.

## 7. Top-5: что не стоит чинить сейчас

### 1. Полноценный agent-раздел в `/admin` (п. 13) — **won't fix now**

- Агентский контур уже отгружен в `/agents` и board-scoped `AgentControlDialog` (`ROADMAP.md:4273-4274`).
- Master- и user-сессия структурно разделены; у master нет API для agent runs.
- Это не «забытая ссылка», а другой продукт/периметр. Строить master API и cross-board approvals — L с высоким риском утечки.
- **Что сделать вместо этого:** обновить ADR/доки, где сказано «new admin UI» (`docs/TASK-166-launch-agent-control.md:70`), чтобы не создавать ложных ожиданий.

### 2. Редактирование комментариев (ops C) — **defer**

- В продукте нет update ни в admin, ни в user controller; user guide обещает только удаление.
- Это новая функция с вопросом авторства: мастер правит чужой текст? отображать ли «edited by»? хранить ли историю?
- Делать «кнопку» без контракта — худший вариант.

### 3. Полный редактор карточки из master-detail (ops B) — **defer / product decision**

- Master-панель по документации — «tools for daily moderation» и граф для расследования, а не второй board UI.
- Content editor уже даёт ограниченный write-path; расширение до assignee/due/labels/checklists — L и требует политики.
- Если делать, начать с description и move (S/M), а не с полного набора.

### 4. Отдельный браузер пунктов чек-листа (п. 8) — **defer**

- Пункт не является самостоятельным объектом для админа; он уже виден в карточке.
- Отдельный top-level tab увеличит IA без явной ценности.
- Если понадобится поиск по тексту пунктов — сделать фильтр/поиск, а не ещё один экран.

### 5. Отдельная master-detail страница ради audit-ссылки (часть п. 9) — **defer**

- `MastersPage` не имеет detail-страницы и поиска; строить её ради одной ссылки — overkill.
- Для `OPERATOR` ссылка вообще должна быть текстом (сейчас ведёт в 403).
- Для `OWNER` достаточно `?master=<id>` с подсветкой строки или поиска по email; полноценный detail — только если появится реальная потребность.

## 8. Вопросы к продукту

Только там, где намерение нельзя вывести из кода/доков:

1. **Граница master-редактирования.** Master уже создаёт/переименовывает/архивирует карточки в content editor. Должен ли он редактировать description, assignee, due, priority, labels, checklists и перемещать карточки из master-detail? Если да — какие поля в первой итерации?
2. **Атрибуция master-действий.** Должны ли участники доски видеть, что действие совершил master, или текущая модель «от имени владельца» — сознательное сокрытие? От этого зависит п. 10.
3. **Редактирование комментариев.** Это продуктовая функция? Если да — только автор или master тоже? Нужна ли история изменений и пометка «edited»?
4. **Агентский обзор для master.** `/agents` и board control — окончательная граница, или master должен видеть cross-board sessions/approvals/policy? ADR говорит про admin UI, реализация — в user app; нужно зафиксировать одно.
5. **Bulk-контракт.** Подтверждаем «выбор живёт между страницами, действие по всем выбранным, очистка при смене фильтра»? Или хотим «только текущая страница» с явным сбросом?

## 9. Предлагаемая формулировка для roadmap/PR

> **Мастер-панель: связи, честные выборки и bulk.** Панель уже покрывает расследование, но не все связи доведены до адресуемых переходов, а часть выборок выглядит полной, хотя ограничена. Первая волна: (1) привести bulk к одному контракту — выбранные ID между страницами, счётчик/подтверждение/запрос совпадают, guard на 500, E2E; (2) показать «N из M» и пагинацию в профиле пользователя и карточке, выровнять определения счётчиков, не давать deleted/revoked строкам вытеснять живые; (3) добавить прямые ссылки автор/актор/пригласивший (`lastActorId`, `invitedById`); (4) синхронизировать состояние списков с URL, открывать точный результат глобального поиска и возвращать контекст списка; (5) добавить адресуемые фильтры `boardId`/`columnId`/`labelId` и ссылки со счётчиков/колонок/меток. Полное редактирование карточки, редактирование комментариев и master-контур агентов — отдельные продуктовые решения, не в эту волну.

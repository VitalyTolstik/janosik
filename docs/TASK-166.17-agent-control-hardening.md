гонками и живой MCP-сценарий, unit и контрактные регрессии; обновлены

**Зависимости:** 166.1–166.16.

**Связь:** исправления здесь; сквозная проверка MCP/skill остаётся в

## Цель

Закрыть восемь выявленных дефектов существующих механизмов identity, pause,
limits, approvals, idempotency и rate limiting. Сохранить контракт ADR-166:
раздельные board-scoped сессии, least privilege, точное одноразовое approval,
атомарность команд, обратимую паузу и стабильные ответы ошибок. Не расширять
продукт новыми агентскими возможностями.

## Находки и критерии приёмки

### 1. P1 — MCP теряет сессию на маршрутах карточек и вложений

**Факт.** `mcp/src/client.ts` определяет доску только из
`/boards/:id/…`. `/cards/:id/comments`, `/comments/:id`,
`/cards/:id/attachments` и `/attachments/:id` отправляются без
`X-Agent-Session`. При paused session запрос с заголовком получает
`agent_paused`, без него комментарий создаётся с `agentSessionId = null`.
Это ломает и атрибуцию, и остановку действий конкретной сессии.

**Сделать.** Надёжно определять board/session context для всех MCP-операций с
комментариями и вложениями, включая delete, и передавать его без утечки между
досками. Продумать совместимость существующих вызовов и ситуацию, когда доску
нельзя достоверно определить: не приписывать запрос произвольной сессии.
Токеновая и board pause должны продолжать действовать независимо от наличия
сессии.

**Проверки.** Через реальный MCP-клиент: start → comment/upload с верной
атрибуцией → pause этой сессии → add/delete comment и upload/delete attachment
отклонены как `agent_paused` → resume → действия снова разрешены. Вторая
сессия/доска не затронута. Добавить негативный случай без надёжной привязки к
доске и тесты существующей совместимости.

### 2. P1 — копирование колонки обходит лимит создаваемых карточек

**Факт.** `ApprovalsService.assertPlanLimits` и счётчик preview в
`plans.service.ts` считают `DUPLICATE_COLUMN` одной карточкой. При
`maxCardsPerRun = 1` копия колонки с тремя карточками проходит, а preview
сообщает `cardCreates: 1`.

**Сделать.** Считать фактические создания для `ADD_CARD`,
`DUPLICATE_CARD` и `DUPLICATE_COLUMN`, включая несколько команд и изменения
состояния внутри плана; preview и реальное применение должны совпадать.
Применять лимит также к batch/plan/approval путям, с актуальной проверкой под
board lock. Лимит карточек на колонку не заменяет лимит run.

**Проверки.** Граница N/N+1 для копии колонки, смешанные create/duplicate,
несколько копий, пустая колонка и изменение колонки перед применением;
превышение → `limit_exceeded`, без частичной записи, run и расходования
approval. Проверить, что preview показывает правильный `cardCreates`.

### 3. P2 — чужой токен расходует бюджет сессии

**Факт.** `AgentRateLimitInterceptor.agentSessionIdOf` берёт ID из пути
heartbeat/end до проверки владельца в сервисе. Отклонённые чужие запросы
расходуют session budget и могут привести к `429` у владельца.

**Сделать.** Применять session bucket только к проверенной принадлежности
сессии текущему токену и доске; не ослабить token/board/global лимиты и не
создать информационный oracle по чужим сессиям.

**Проверки.** Два разных PAT: чужие heartbeat/end получают отказ и не меняют
бюджет владельца; собственные запросы всё ещё ограничиваются, соседние
сессии изолированы. Тест должен проверять статус и scope `429`.

### 4. P2 — failed lifecycle operation расходует approval

**Факт.** `claimOperation` ставит `consumed` до действия; вызывающие стороны
не используют `releaseOperation` при ошибке. Одобренный share с прошедшим
`expiresAt` возвращает `400`, ничего не создаёт, но approval уже
`consumed` и повтор получает `approval_consumed`.

**Сделать.** Согласовать состояние approval с фактическим результатом для
board/member/share/attachment lifecycle. При гарантированном rollback действия
approval не должно оставаться ложно потреблённым. Защитить однократность при
конкурентном применении, падении процесса, таймауте и неопределённом результате:
не переоткрывать approval, если действие уже могло закоммититься. Audit,
activity и уведомления должны отражать реальный исход.

**Проверки.** Ошибка валидации, конфликт и отказ паузы после авторизации не
создают ресурс и не показывают успешное потребление; успешное действие
потребляет approval один раз; конкурентные запросы не создают дубликаты;
сбой после commit и повтор не применяют действие повторно.

### 5. P2 — изменение лимита между проверкой и batch

**Факт.** `CommandsService.applyBatch` читает политику и проверяет лимиты до
`BoardWriteService.run`. Если после проверки ADMIN снижает
`maxCommandsPerRun` с 2 до 1, batch из двух команд всё равно применяется.

**Сделать.** Повторно проверить актуальные лимиты и соответствующие
ограничения плана под board lock до любых записей и потребления approval.
Сохранить атомарность, идемпотентный replay и семантику policy CAS.

**Проверки.** Детерминированная гонка: запрос прошёл предварительную проверку,
ADMIN сохранил более строгую политику, запрос продолжился → отказ без команд,
run и потребления approval. Покрыть и `maxCardsPerRun`, и replay.

### 6. P2 — идемпотентность share игнорирует expiry

**Факт.** Хеш `create_share` не включает `expiresAt`. Повтор с тем же
`Idempotency-Key`, но с другим сроком возвращает прежнюю ссылку: например,
запрос на ограниченный срок получает ранее созданную бессрочную ссылку.

**Сделать.** Различать существенные изменения срока и возвращать
`idempotency_conflict` на иной intent, сохраняя корректный replay
действительно идентичного запроса. Учесть, что MCP сейчас вычисляет
`expiresAt` из `expiresInHours` на стороне клиента: повтор исходного
намерения не должен ошибочно конфликтовать из-за сдвига часов. Не ослаблять
approval exactness.

**Проверки.** Без срока → со сроком, изменение/удаление срока и идентичный
replay; REST и MCP с относительным сроком; разные intent не создают второй
ресурс и не возвращают старый ответ как успешное новое действие.

### 7. P2 — read-only PAT не может выполнить preview отката

**Факт.** `MembershipGuard` запрещает `readOnly` PAT любой POST, хотя
`/runs/:runId/revert/preview` объявлен `observer` и не меняет данные.
Воспроизведён `403 pat_read_only`. Сценарии start/heartbeat/end сессии также
противоречат указанному в ADR observer/control-plane контракту.

**Сделать.** Явно определить узкий перечень разрешённых read-only операций и
control-plane маршрутов с учётом контрактов сессии. Разрешение preview не
должно открыть apply/revert, команды, approvals, редактирование доски или
другие записи. Уточнить EN/RU docs и OpenAPI, если меняется контракт.

**Проверки.** Read-only PAT получает preview без preimages; настоящий revert
и обычные записи запрещены; проверить start/heartbeat/end и паузу в
соответствии с ADR; observer preset и legacy `readOnly` покрыты отдельно.

### 8. P2 — старт сессии после отзыва ключа

**Факт.** `AgentSessionsService.start` после аутентификации создаёт сессию
без повторной проверки состояния ключа. При гонке revoke завершается первым,
затем создаётся `active`-сессия отозванного ключа. Сам ключ остаётся
недействительным, но консоль и lifecycle-состояние вводят в заблуждение.

**Сделать.** Сериализовать создание с отзывом/паузой и повторно проверять
ключ и доску в точке записи так, чтобы после завершённого revoke не осталась
новая активная сессия. Сохранить существующую семантику in-flight и порядок
блокировок.

**Проверки.** Детерминированная гонка start ↔ revoke и start ↔ pause; после
revoke нет активной сессии этого токена; при допустимом порядке завершения
все созданные сессии отменены; повтор и SSE/attribution остаются согласованы.

## Дополнительные исправления после ревью TASK-166

Запись агента сериализована с отзывом, паузой и изменением разрешений токена;
правила lifecycle повторно проверяются под блокировкой доски. Создание и импорт
досок, обновление снимка публикации и удаление чужого вложения учитывают паузу,
политику и состояние подтверждения в точке записи. При неизвестном результате
идемпотентный ключ сохраняется до истечения 24 часов, чтобы повтор не создал
дубликат. Консоль агентов сохраняет последние известные данные недоступных досок
и явно сообщает об ошибке частичной загрузки. Для этих случаев добавлены
постоянные регрессионные проверки.

The 10 streams reported 97 top findings; 10 duplicate merges reduced these to 87 unique entries. Twelve supplementary low-priority observations from stream notes were added, giving 99 entries.

**Top 5 risks**

1. **Rollback can destroy data the run never touched (C1).** A non-destructive no-op command (e.g. `ADD_COLUMN` with an existing ID) is recorded with a `DELETE_COLUMN` inverse. A later admin rollback deletes the pre-existing column and all its cards, bypassing the destructive-approval gate.
2. **The `OPERATOR` master role escapes its owner-only boundaries (H7, H8).** An operator can change any user's email, trigger a password reset to their own mailbox, and log in as that user; an operator can also run the destructive retention purge.
3. **Board content can be stolen or silently lost (H2, H3).** Any board member can reparent another card's checklist/item/link by reusing its ID in `ADD_*`; duplicating a card/column drops checklists server-side, and the duplicated IDs can later move the original's checklist to the copy.
4. **Fresh no-SMTP installs are blocked at first account creation (H1).** `install.sh` enables bootstrap mode, but `/auth/config` reports `allowRegistration:false` when SMTP is absent, so the UI hides the only registration control while the API still accepts the bootstrap account.
5. **Agent-control approvals dead-end (H10, H12).** A board Inbox that fetches the newest 100 rows of all statuses can hide an older pending approval that its header still counts, and MCP destructive tools generate a fresh `commandId` that cannot match the approved plan hash, so approved actions fail with `approval_mismatch`.

Also critical in impact though narrower in trigger: **demo cleanup destroys real data (H9)** — it deletes every `CardLink` on a user-supplied board and can hard-delete a normal board whose title starts with the demo prefix.

## 3. MEDIUM findings

### A. Auth, sessions, authorization and privacy

**M1 — OAuth login loses the deep link** (B1, B3). The OAuth success/failure callback always redirects to the app root, and `LoginPage` clears all query params on `authError`; a user who starts from `/app/board/<id>` lands on the first active board. Evidence: `ui/src/components/auth/LoginPage.tsx:89-93,321`; `backend/src/oauth/oauth.controller.ts:132-143`; `ui/src/store/BoardContext.tsx:806-816`. *Likely; no provider round trip.*

**M2 — Auth screens are clipped and unscrollable on short/landscape viewports** (B1). The outer shell uses `h-screen overflow-hidden` and the login `main` also uses `overflow-hidden`; password recovery, register + OAuth, and the verification gate place controls below a 320 px viewport with no scrolling. Measured on Chromium at 568×320: Reset button at y=318, `scrollHeight=463`, wheel leaves `scrollY=0`. Evidence: `ui/src/App.tsx:239,248`; `LoginPage.tsx:179`; `EmailVerificationGate.tsx:101`; `PasswordRecovery.tsx:102`. *Confirmed on Chromium; no physical mobile.*

Registration creates a unique `User.email` row with `emailVerifiedAt=null`; re-registration returns 409, password reset silently refuses unverified accounts, and there is no unauthenticated resend/change-email path. Evidence: `backend/prisma/schema.prisma:24`; `auth.service.ts:238-246,299-306`; `EmailVerificationGate.tsx:95-199`; no cleanup path found. *Likely; no live DB test.*

## 5. Cross-cutting themes

1. **Authorization is enforced at the wrong layer, or only in one client.** Operator vs owner is checked on some `/admin/ops` writes but not user email changes or retention purge (H7, H8). `share.update` approval is enforced on PATCH but not snapshot refresh (M9). Archived/deleted state is enforced on the main share but not nested comment/attachment routes (M10). Session-only/PAT rules are split between `JwtAuthGuard`, `SessionOnlyGuard` and `MembershipGuard`, producing `pat_forbidden` vs `pat_read_only` inconsistencies (M34, L21). The UI and API also disagree: `ALLOW_PUBLIC_SHARES` hides only the reader (M4), the bootstrap UI hides a server-supported path (H1), and admin/docs URLs assume the wrong base (M36).

2. **The server trusts client-supplied metadata as authority.** `inverse:true` is accepted as proof of an undo (M13); same-board IDs are accepted as proof of parentage (H2); no-op commands still carry destructive inverses (C1); duplicate clones reuse IDs (H3); `commandId` is both the idempotency key and part of the approval hash, but clients regenerate it (H12, M21). This class produces most of the data-integrity and limit-bypass findings.

3. **Ambiguous write outcomes are not reconciled.** The client rolls back on a lost response and then suppresses its own authoritative SSE echo (H14); revert/board-create/import/MCP writes generate new keys or no key on retry (M17, M20, M21); idempotency records can be stranded for 24 h (L24).

# Performance baseline — Janosik

Снято 2026-10-29 на одной машине. Это **точка отсчёта**: после перф-фиксов
сверяемся с ней (см. «Матрицу перепроверки» внизу).

## Стенд

- WSL2 Ubuntu-24.04, **16 vCPU, 23 GiB RAM**; одна машина.
- API `:3000` (NestJS, один процесс), Postgres 16 (Docker): **`max_connections=100`,
  `shared_buffers=16 MB`, `work_mem=4 MB`**; Redis 7 (Docker).
- Dev UI `:5173` (Vite), сайт `:4321` (Astro dev).
- Лимиты на время прогона подняты (`THROTTLE_LIMIT=1e6`, share-лимиты), затем
  `.env` восстановлен.
- **Важно:** генераторы нагрузки (k6, Node-SSE, Playwright) живут на том же хосте и
  делят CPU с приложением. Абсолютные числа консервативны; конкурентные выводы
  валидны. Для «настоящего» капасити нужен отдельный генератор + несколько нод.

## Как повторить

```bash
# 0) поднять лимиты и (опционально) Redis-режим; вернуть — revert-env.sh
bash ~/.janosik-dev/load/env-prep.sh dev      # или: redis

# 1) данные (идемпотентно): 2000 юзеров, доски 200/500/1000/2400, 100 досок
cd ~/.janosik-dev/load
USERS=2000 SHARED_CARDS_PER_COL=50 UI_TIERS=200,500,1000,2400 node provision.mjs
node mint-admin.mjs
node setpass.mjs

# 2) HTTP-нагрузка (k6 в ~/.local/bin)
bash series.sh read-aggregate.js 50 100 200 400
bash series.sh write-shared.js 10 25 50 100
bash series.sh mixed.js 100 200 400
bash series.sh admin-read.js 25 50 100
bash series.sh site.js 100 300 600
bash series.sh share.js 50 100 200
MODE=me bash runmon.sh auth.js 200

# 3) запись по 100 доскам
M=100 node add-boards.mjs && bash runmon.sh write-many.js 200

# 4) SSE/память (нужен временный /health/memory — см. ниже)
PER=0 STEPS=200,400,700,1000,1300,1600,2000,3000 node mem-ramp.mjs
C=2000 DUR=75 node steady.mjs

# 5) UI (Playwright, headless Chromium)
node ui-cards.mjs
N=10 node ui-agents-multi.mjs

# 6) вернуть окружение
bash ~/.janosik-dev/load/revert-env.sh
```

> `/health/memory` — временный диагностический маршрут, после измерений удалён.
> Чтобы снова мерить память: вернуть его в `backend/src/health/health.controller.ts`
> (за `MEMORY_DIAG=1`) и добавить `MEMORY_DIAG=1` в `backend/.env`, пересобрать
> `npm run build:backend`, перезапустить `janosik-api`. Скрипты `mem-ramp.mjs` и
> `steady.mjs` читают `/api/v1/health/memory`.
> `env-prep.sh` меняет `THROTTLE_LIMIT`/`REDIS_URL`, `revert-env.sh` возвращает
> исходный `.env` из `~/.janosik-dev/load/env.backup`.

## Проверка после TASK-144/145/146 (2026-10-29)

Перемер на том же стенде (dev-режим, без Redis). Командный путь и память SSE
не изменились; добавились ограничения ресурсов.

| Метрика | Baseline | После 144/145/146 |
| --- | ---: | ---: |
| SSE память, 1000 коннектов | 389 MB | 385 MB |
| SSE память, 2000 | 525 MB | 520 MB |
| SSE память, 3000 | 703 MB (жив) | 701 MB (жив) |
| Агрегат доски @400 VU | ~430–465 rps | 422 rps |
| Команды на 1 доску @100 writers | ~48 rps | 48.1 rps |
| Микс @400 VU | ~250 rps | 264 rps |

Вывод: **регрессии нет** — числа в пределах разброса (генераторы делят CPU с
API). Steady-state 1000 коннектов: `heapUsed` стабилен/убывает (154→130 MB за
60 c) — утечки нет (RSS в замере выше, потому что процесс не перезапускали
после mem-ramp: V8 не возвращает RSS ОС; смотреть `heapUsed`).

Изменения **по поведению** (не по скорости):

- presence больше не уходит в Redis (публикуется локально → на 2 нодах нет
  ложных `leave`); кадры несут `epoch`, keep-alive — `presenceEpoch`;
- SSE-лимиты: `SSE_MAX_PER_USER=32` (проверено: 40 потоков одним юзером →
  ~32 accepted, остальные `503`), `SSE_MAX_CONNECTIONS=5000`,
  `SSE_MAX_PER_BOARD=0` (рой на одной доске не обрезается);
- `ifMatchVersions` ≤ 100 и батч-версии (в k6-скриптах не используется — на
  сквозной throughput не влияет);
- upload-rate 60/мин на пользователя (`429`).

## UI после TASK-139: виртуализация (2026-10-30)

Тот же dev-стенд WSL2, Playwright headless Chromium 1600×900, синтетическая
доска 12×200. Окно монтирует только строки вокруг позиции скролла; ниже —
замеры до/после.

| Поверхность | До (baseline) | После |
| --- | ---: | ---: |
| Канбан, карточек в DOM | 67 676 узлов / 2400 карточек | **108** карточек, **4 017** узлов |
| Канбан, heap | 1 106 MB | **90 MB** |
| Канбан, первый рендер | 4.81 s | **~0.7 s** |
| Канбан, max long task | 3.90 s | **176 ms** |
| Таблица, строк в DOM | 2400 (49 165 узлов, 513 MB, 1.86 s long task) | **26** строк, 792 узла |
| Календарь, unscheduled-панель | до 2400 кнопок | **27** кнопок |
| Календарь, неделя (2400 в одном дне) | 2400 чипов | окно по скроллу сетки |
| Day-panel | до 2400 строк | **21** строка в окне панели |

Месячная сетка намеренно не виртуализируется: 42 ячейки и максимум 3 чипа на
ячейку + «+N» — это уже bounded. `SortableContext` получает полный список id,
поэтому перетаскивание внутри колонки и через колонки не меняет семантику;
j/k подскролливает колонку к карточке курсора, а открытый inline-композер
держит все карточки смонтированными, чтобы не потерять черновик.

**Оговорка.** Замер — dev-сборка на общем хосте с генераторами; абсолютные
числа консервативны, сравнение «до/после» — на одной машине и в одном режиме.

## UI после TASK-142: плотность карточек (2026-10-30)

Тот же dev-стенд WSL2, Playwright headless Chromium 1600×900, синтетическая
доска 12×200 (2400 карточек) с метками, описаниями, чек-листами, сроками и
исполнителями. Один вход, режим выбирается `localStorage` до перезагрузки.
Скрипты — `~/.janosik-dev/load/ui-density.mjs` и `ui-load.mjs`.

| Метрика (board-вид, 2400 карточек) | Полный | Компактный |
| --- | ---: | ---: |
| Карточек в DOM | 108 | **156** |
| DOM-узлов всего | 4 482 | **2 414** (−46%) |
| Узлов на карточку | 41.5 | **15.5** |
| Первый рендер (до первой карточки) | 1 060 ms | **740 ms** (−30%) |
| Max long task при загрузке | 499 ms | **295 ms** |
| Карточка, высота | 92 px | **48 px** |

Под нагрузкой (240 команд `UPDATE_CARD` живьём, ≈9/с, конкурентно×6, через тот
же командный API, что оборачивает MCP): **0 long task** на main-thread в обоих
режимах, обновления применяются в открытой доске без перезагрузки. Цена
компактного режима — больше карточек в окне (156 против 108), поэтому heap в
разных прогонах гуляет (≈95–123 MB), но DOM и время рендера стабильно ниже.

**Watch-вид (TASK-142, «без косметики»).** Та же доска в четвёртом виде:
**0 карточек в DOM и ~405 узлов всего** (крупный статус + рейка колонок/онлайн
+ живая лента из 50 строк) — против 2 414 у компакта и 4 482 у полного.
Ни карточек, ни DnD, ни анимаций/переходов (глушит `[data-watch]`); лента
опрашивается раз в 3 с и обновляется на кадр комментария / свой коммит.

## Загрузки: RSS при 20 × 24 MB одновременно (TASK-156)

Замер на `main` после TASK-155/156 (dev, API отдельным процессом, 20
параллельных multipart-загрузок по 24 MB в одну карточку; `VmRSS` из
`/proc/<pid>/status`, пик — максимум после каждой завершённой загрузки):

| Метрика | Значение |
| --- | ---: |
| RSS до загрузок | 221 MB |
| RSS пик | 231 MB |
| Прирост | **+10 MB** |
| Время 20 загрузок | 1.6 s |

Тела запросов больше не живут в RAM: multer пишет во временный `.tmp-*`,
после проверок файл атомарно переносится в blob-tree, а `finally` удаляет
scratch. Для сравнения: старый `memoryStorage` держал все 20 тел сразу
(~480 MB) и упирался в heap/лимит контейнера.

## Напоминание

Числа — это **одна нода и общий хост с генераторами**. Сравнивать прогоны между
собой корректно только на этой же машине и в том же режиме (`dev`/`redis`).

# Архитектурный аудит Janosik

**Состояние:** ветка `main` @ `2128cc2` + незакоммиченная работа TASK-47 (вложения, аватары).
**Объём:** ~71 000 строк TS/TSX в трёх воркспейсах (`ui`, `shared`, `backend`).
**Дата:** 2026-09-20. Независимое ревью.

Пометки: **[ПОДТВЕРЖДЕНО]** — воспроизведено запуском; **[ИЗ КОДА]** — следует из чтения.
Находки по последнему коммиту (card links) вынесены в
[LAST_COMMIT_AUDIT.md](LAST_COMMIT_AUDIT.md) и здесь только упоминаются.

## 0. Резюме

Проект в очень хорошей форме для «почти готов»: слой аутентификации сделан на уровне,
который редко встречается в pet-проектах (argon2id, ротация refresh, детект переиспользования,
кросс-табовая сериализация через Web Locks), SSE-стрим спроектирован без гонок, гварды
аккуратные, плотность документации в коде — выше среднего по индустрии.

Прогон на моей машине:

| Пакет | Результат |
| --- | --- |
| `shared` | 353/353 ✅ |
| `ui` | 661/661 ✅ |
| `backend` unit | 57/57 ✅ |
| `npm run lint` (все воркспейсы) | 0 ошибок, 32 предупреждения ✅ |
| `tsc --noEmit` (backend) | **19 ошибок** ❌ |

Главных системных проблем три, и все три — не «баги», а свойства архитектуры:

1. **Union действий размазан по пяти параллельным `switch`** без проверки полноты — новый тип
   команды требует руками попасть в 5–7 файлов, и промах не ловится компилятором. Уязвимость
   №1 из `LAST_COMMIT_AUDIT.md` — прямое следствие.
2. **Проверка владения id построена на рукописном списке ключей** — структурно обречена
   отставать от модели.
3. **Заявленный offline-first не выполняется в серверном режиме** — очередь команд живёт
   только в памяти.

### 1.1 🔴 Пять параллельных `switch` по одному union'у, без гарантии полноты

**[ПОДТВЕРЖДЕНО подсчётом]**

| Файл | `case`'ов |
| --- | --- |
| [shared/src/store/board-reducer.ts](shared/src/store/board-reducer.ts) | 44 |
| [shared/src/store/invert.ts](shared/src/store/invert.ts) | 47 |
| [backend/src/commands/command-writers.ts](backend/src/commands/command-writers.ts) | 50 |
| [backend/src/commands/commands.service.ts](backend/src/commands/commands.service.ts) (гварды лимитов) | 22 |
| [backend/src/commands/command-details.ts](backend/src/commands/command-details.ts) | 15 |

Плюс не-`switch` места, которые тоже обязаны знать про каждое действие:
`SUPPORTED_ACTIONS` (Set строк), `referencedEntityIds()` (`DIRECT_KEYS`/`ARRAY_KEYS`),
`validate.ts`, `migrate.ts`, `cardIdsTouchedBy()`, `textEntityKey()`.

Итого **добавление одной команды = ~7 точек редактирования**, из которых компилятор
защищает только те, где `switch` возвращает значение и есть `default: never`. `SUPPORTED_ACTIONS`
и `DIRECT_KEYS` — обычные списки строк, промах в них молчит. TASK-46 промахнулся ровно там.

**Что предлагаю:** заменить списки строк на `satisfies`-мапы, чтобы промах стал ошибкой
компиляции:

```ts
// shared/src/store/command-registry.ts
export const COMMAND_IDS = {
  ADD_CARD:       (a) => [a.newCardId, a.columnId],
  ADD_CARD_LINK:  (a) => [a.cardId, a.targetCardId, a.linkId],  // ← забыть нельзя
  …
} satisfies Record<BoardAction["type"], (a: never) => string[]>;
```

Тот же приём для `SUPPORTED_ACTIONS` и `textEntityKey`. Это не рефакторинг ради
красоты — это единственный способ не повторить находку №1.

### 1.3 🟢 Что устроено правильно

* **Общий редьюсер в `shared/`, исполняемый и клиентом, и сервером** — одна семантика
  команд на обе стороны. Это сильное решение, оно же даёт честное оптимистичное UI.
* **Command log с `commandId` как идемпотентным ключом** — ретрай безопасен by design.
* **Инверсия команд (`invert.ts`) вместо снапшотов** для undo — экономно и корректно,
  с продуманным правилом «инверсные команды проходят мимо гвардов».
* **`ifMatchVersions` только для текстовых правок**, остальное last-write-wins — ровно
  та степень строгости, которая нужна канбану.
* **SSE без гонки на подключении** ([events.controller.ts](backend/src/commands/events.controller.ts)):
  буферизация live-событий → догон дельты `?since=` → слив буфера с дедупом по `seq`.
  Это аккуратно и редко делается правильно.

## 2. Безопасность

### 2.1 ✅ Кросс-бордовая запись через `linkId` — исправлено

Подробно в [LAST_COMMIT_AUDIT.md §1](LAST_COMMIT_AUDIT.md). **[ПОДТВЕРЖДЕНО]**:
аутентифицированный пользователь одним `ADD_CARD_LINK` с чужим `linkId` уничтожал связь
на чужой доске.

**Закрыто:** `linkId` попал в `DIRECT_KEYS`, `assertIdsBelongToBoard` опрашивает
`cardLink`, оба writer'а переписаны со скоупом по `boardId`. Регрессия зафиксирована
в `command-ids.e2e-spec.ts`. Подпроблема §2.2 (слабый генератор id) остаётся открытой.

### 2.2 🟠 Проверка владения id — рукописный список ключей

**[ИЗ КОДА]** — [referenced-entity-ids.ts](backend/src/commands/referenced-entity-ids.ts)

Механизм правильный по идее (глобальные PK + board-scoped команды = обязательна проверка
владения), но реализован как два массива строк `DIRECT_KEYS` / `ARRAY_KEYS` плюс ручной
обход снапшотов `collectSnapshot`. Любое новое поле-идентификатор в любом действии
по умолчанию **не проверяется**. Это не «баг, который починили» — это конструкция, которая
будет ломаться повторно. См. фикс в §1.1.

Вторая половина проблемы — **сами идентификаторы**. Все они генерируются клиентом через
[`createId()`](ui/src/utils/id.ts):

```ts
return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
```

Метка времени + ~40 бит от `Math.random()`. Функция честно задокументирована как
«Not cryptographically secure (fine for localStorage data)» — и это было правдой, пока
данные лежали в localStorage. После TASK-29 эти же значения стали **глобальными первичными
ключами на сервере**, а `assertIdsBelongToBoard` — единственной границей между досками.
Граница, ключи которой перебираются по временному окну, — слабая граница.

**Фикс:** генерировать id через `crypto.randomUUID()` (доступен во всех целевых браузерах
в secure context, с фолбэком на `getRandomValues`). Старые данные при этом ломать не надо —
проверка владения id от формата не зависит.

### 2.3 🟠 `?client=` в SSE не привязан к пользователю

**[ИЗ КОДА]** — [events.controller.ts:57-58](backend/src/commands/events.controller.ts#L57-L58),
[presence.service.ts:73-85](backend/src/realtime/presence.service.ts#L73-L85)

Клиент сам присылает `clientId`, реестр присутствия ключуется `Map<boardId, Map<clientId, …>>`
без учёта пользователя. Участник доски, подобрав/подсмотрев чужой `clientId` (он живёт
в URL SSE-запроса и в localStorage вкладки), может:

* перезаписать чужую сессию своим `join` → чужой аватар пропадает из ростера;
* при разрыве своего стрима выполнить `leave(boardId, clientId)` → выбить чужую сессию.

Ущерб косметический (presence эфемерен), но это запись в состояние другого пользователя.

**Фикс:** ключевать сессию как `${user.id}:${clientId}`.

### 2.4 🟠 MIME вложений объявляет клиент, и он же уезжает обратно в `Content-Type`

**[ИЗ КОДА]** — [storage.service.ts:18](backend/src/attachments/storage.service.ts#L18),
[attachments.service.ts:57](backend/src/attachments/attachments.service.ts#L57),
[attachments.controller.ts:70-77](backend/src/attachments/attachments.controller.ts#L70-L77)

Три отдельные вещи:

1. `file.mimetype` у multer — это **заголовок из multipart-запроса**, то есть значение под
   контролем клиента. Аллоу-лист проверяет заявленный тип, не содержимое. Magic-byte
   проверки нет.
2. Тот же непроверенный `meta.mimeType` сервер отдаёт обратно в `Content-Type`.
3. Докблок утверждает: *«Executable-ish types (html, svg, x-sh) are excluded even inside
   the wildcard families»*. Это **неправда**: ветка `text\/[\w.+-]+` матчит `text/html`.
   (SVG действительно не проходит — группа `image/…` перечислена явно.)

Практическая эксплуатация сегодня блокируется двумя вещами: жёстким
`Content-Disposition: attachment` на роуте и `X-Content-Type-Options: nosniff`, который
ставит глобальный `helmet()`. То есть дыры нет — но защита держится ровно на двух
заголовках, а комментарий врёт про третий рубеж, которого нет. Стоит либо убрать
`text/*` из аллоу-листа, либо поправить комментарий.

### 2.5 🟡 `Content-Type` аватара выводится из расширения клиентского файла

**[ИЗ КОДА]** — [users.controller.ts:74-80](backend/src/users/users.controller.ts#L74-L80)

```ts
const ext = storedName.slice(storedName.lastIndexOf(".") + 1);
const mime = ext === "jpg" ? "image/jpeg" : `image/${ext === "jpeg" ? "jpeg" : ext}`;
```

`storedName` генерируется сервером, но расширение в нём взято из исходного имени файла
(`storedName()` пропускает любые `[a-z0-9]{1,10}`). Загрузив PNG с именем `x.bin`,
пользователь получит ответ `Content-Type: image/bin`. В БД уже лежит проверенная колонка
`mimeType` — надо отдавать её, а не собирать строку из расширения.

### 2.6 🟡 Rate limit: 100 req/min на IP, без `trust proxy`

**[ИЗ КОДА]** — [app.module.ts:23-25](backend/src/app.module.ts#L23-L25)

Два независимых вопроса:

* **Ключ.** `ThrottlerGuard` по умолчанию берёт `req.ip`. `app.set('trust proxy')` нигде не
  выставлен, а [deploy/nginx.conf](deploy/nginx.conf) прокси API ещё не описывает (помечено
  как TASK-38). Как только API окажется за nginx, **все пользователи схлопнутся в одно
  ведро** — 100 запросов в минуту на всю инсталляцию.
* **Величина.** Каждая команда — это один POST. Активная работа с доской (перетаскивания,
  чек-листы, правка текста после дебаунса) легко даёт >100 команд в минуту у одного
  человека. Лимит стоит делать per-user и раздельным для `/commands` и для остального.

### 2.7 🟢 Аутентификация — сильная сторона проекта

[auth.service.ts](backend/src/auth/auth.service.ts), [client.ts](ui/src/api/client.ts):
argon2id; access-токен только в памяти; refresh — непрозрачная строка, в БД лежит
только sha256; ротация на каждое использование; предъявление отозванного токена трактуется
как кража и гасит все сессии пользователя; атомарная ротация через `updateMany(revokedAt: null)`
закрывает гонку; `burnPasswordTime` выравнивает тайминг несуществующего e-mail;
изоляция аудиторий JWT (`janosik-admin` не откроет пользовательские роуты);
отключённый аккаунт отсекается и на логине, и на refresh, и в `JwtStrategy.validate`.

Отдельно отмечу кросс-табовую сериализацию refresh через Web Locks с комментарием,
описывающим реальный инцидент 2026-09-17 — это лучший вид документации.

Мелочь: access-токен отключённого аккаунта живёт до 15 минут — но `JwtStrategy` ходит
в БД на каждый запрос и проверяет `disabledAt`, так что фактически бан мгновенный.

### 3.2 🟠 `PresenceService.updateUser` игнорирует `avatarPath`

**[ИЗ КОДА]** — [presence.service.ts:100-127](backend/src/realtime/presence.service.ts#L100-L127)
vs [users.service.ts:91-95](backend/src/users/users.service.ts#L91-L95)

Сигнатура принимает `avatarPath` (`Pick<PresenceIdentity, "displayName" | "email" | "avatarColor" | "avatarPath">`),

Тихий no-op, который типы не поймали, потому что `Partial<>` разрешает игнорировать поле.

### 3.3 🟠 `use-avatar-object-url` — N параллельных запросов и утечка object URL

**[ИЗ КОДА]** — [use-avatar-object-url.ts](ui/src/hooks/use-avatar-object-url.ts)

Три дефекта в одном хуке:

1. **Нет дедупа in-flight запросов.** Кеш заполняется только в `.then()`. Доска, где
   30 карточек показывают аватар одного автора, смонтирует 30 `UserAvatar`, каждый не
   найдёт запись в кеше и выстрелит `api.fetchUserAvatar(userId)` → **30 одновременных
   HTTP-запросов за один и тот же файл**. Кешировать надо промис, а не результат.
2. **`URL.revokeObjectURL` не вызывается никогда.** При смене аватара
   `cache.set(userId, …)` затирает запись, старый blob остаётся жить до конца жизни вкладки.
   Комментарий «a handful of small images» занижает: лимит аватара —
   `LIMITS.avatarSize = 2 MB`, и утечка накапливается по каждой перезагрузке аватара.
3. **`setUrl(null)` прямо в теле эффекта** — это же предупреждение линтера
   (`react-hooks/set-state-in-effect`), и оно даёт мигание инициалами перед картинкой.

Плюс нет негативного кеша: 404 приводит к повторному запросу на каждый remount.

### 3.4 🟡 Вложения: гонка на лимите и осиротевшие блобы

**[ИЗ КОДА]** — [attachments.service.ts:69-101](backend/src/attachments/attachments.service.ts#L69-L101)

* `count()` живых вложений делается **вне** транзакции, а создание строки — внутри.
  Параллельные загрузки пробивают `attachmentsPerCard = 20`.
* `writeFile()` на диск происходит **до** транзакции. Падение транзакции оставляет файл
  навсегда — компенсирующего удаления нет. То же в `uploadAvatar`.

**Фикс:** писать блоб во временное имя, коммитить транзакцию, потом переименовывать;
либо оборачивать неудачу транзакции в `storage.remove()` в `catch`.

### 3.5 🟡 `storage.open(...).pipe(res)` без обработки ошибок потока

**[ИЗ КОДА]** — [attachments.controller.ts:76](backend/src/attachments/attachments.controller.ts#L76),

## 4. Производительность и масштабирование

### 4.1 🟠 `listSince(boardId, 0)` читает весь command log, без лимита и без retention

**[ИЗ КОДА]** — [commands.service.ts:282-300](backend/src/commands/commands.service.ts#L282-L300),
[schema.prisma:118-137](backend/prisma/schema.prisma#L118-L137)

`findMany` без `take`. Свежий клиент (или клиент, потерявший baseline) подключается с
`since=0` и получает **всю историю доски** — сначала целиком в память процесса, потом
одним залпом в SSE. Таблица `Command` при этом растёт бесконечно: ни pruning, ни
компакции, ни снапшотов нет, а `payload` + `details` хранят полный JSON каждого действия.

Активная доска на год работы — это сотни тысяч строк. Это самая серьёзная проблема
масштабирования в проекте.

**Фикс:** `take` + пагинация дельты; если клиент отстал дальше окна — отдавать сигнал
«перезагрузи агрегат» вместо реплея; отдельно — retention-политика на `Command`.

### 4.2 ✅ Квадратичный автокомплит связей — исправлено

См. [LAST_COMMIT_AUDIT.md §3](LAST_COMMIT_AUDIT.md). **[ПОДТВЕРЖДЕНО замерами]**:
было 65 ms/нажатие на 1 000 карточек и 621 ms на 3 000.

**Закрыто:** множество соседей строится одним проходом, функция линейна;
тест считает обращения к записи карточек и падает на старой реализации.

### 4.3 🟡 `FOR UPDATE` на строке доски сериализует все команды доски

**[ИЗ КОДА]** — [commands.service.ts:148-155](backend/src/commands/commands.service.ts#L148-L155)

Каждая команда берёт эксклюзивный лок на строку `Board`, внутри транзакции делает
загрузку полного агрегата, прогон редьюсера, `stableStringify` дважды и серию записей.
Пропускная способность доски = одна команда за раз, и длительность транзакции растёт
вместе с размером доски (агрегат грузится целиком на каждую команду).

Для десятка соавторов это нормально. Для «премиум-канбана на команду 50 человек» —
первое, что упрётся. Как минимум стоит замерить время транзакции на доске в 2 000 карточек.

### 4.4 🟡 3–4 запроса в БД на каждый HTTP-запрос

**[ИЗ КОДА]** — `JwtStrategy.validate` (1: `user`), `MembershipGuard` (2: `board` +
`boardMember`), `CardAccessGuard` (+1: резолв карточки/комментария/вложения). Без кеша.
Для self-hosted это приемлемо, но заметно при SSE-реконнектах и пачках команд.

### 4.5 🟢 Мелкие утечки, не срочно

* `RealtimeService.channels` — `Subject` на доску создаётся лениво и **никогда не удаляется**
  ([realtime.service.ts:16](backend/src/realtime/realtime.service.ts#L16)).

Обе растут по числу когда-либо открытых досок, не по трафику. Несрочно, но для
долгоживущего процесса — стоит чистить при опустошении.

## 5. Заявленный offline-first не выполняется в серверном режиме

**[ИЗ КОДА]** — [server-sync.ts](ui/src/store/server-sync.ts),
[BoardContext.tsx:1118-1140](ui/src/store/BoardContext.tsx#L1118-L1140)

README говорит:

> *«service worker caches the app shell and all hashed chunks; the board keeps working
> with the network fully cut»* (строка 72)

В серверном режиме это не так. `ServerSync` — **чисто in-memory очередь**: нет ни
persisted outbox, ни повтора при восстановлении сети. Команда, не дошедшая до сервера,
обрабатывается так:

```ts
realtimeRef.current?.settled(boardId);
showFailure(outcome.failure);          // тост «нет сети»
const rollback = rollbackStep(boardId, scoped);
if (rollback.kind === "reverted") apply(rollback.undo);   // ← правка откатывается
```

То есть при пропаже сети пользователь видит, как его изменения **откатываются одно за
другим**, каждое со своим тостом. Перезагрузка вкладки в оффлайне теряет всё
несохранённое: очередь была в памяти.

Отдельно: ветка `rollback.kind === "dead"` (поверх легли более новые команды) оставляет
оптимистичное состояние расходиться с сервером до следующего refetch по фокусу окна —
осознанный компромисс, но окно расхождения ничем не ограничено.

Это не баг реализации, а честный архитектурный выбор (command log + оптимистичный откат).
Но заявка в README и в `package.json` (`"keywords": ["offline-first", …]`) ему не
соответствует. **Либо** уточнить формулировку («offline работает в локальном режиме;
в серверном режиме требуется сеть»), **либо** сделать persisted outbox (IndexedDB +
дренаж по `online`). Инфраструктура для второго уже есть: `commandId` идемпотентен,
бэкапы в IndexedDB написаны, `keepalive` на fetch продуман.

## 7. Что сделано хорошо

Перечисляю не для вежливости — это то, что снижает риск эксплуатации и что стоит
сохранить при рефакторинге:

* **Аутентификация и сессии** (§2.7) — уровень выше среднего продакшена.
* **Общий редьюсер `shared/`** как единственный источник семантики команд для клиента
  и сервера; идемпотентность по `commandId`; инверсия вместо снапшотов.
* **SSE без гонки на подключении** — буфер → дельта → дедуп по `seq`.
* **Data-safety в UI**: провалившаяся запись в localStorage поднимает баннер, а не тост;
  quota-предупреждение отдельным уровнем; карантин нечитаемых данных; автобэкапы в IndexedDB.
  Мало кто доводит обработку `QuotaExceededError` до конца.
* **Качество комментариев.** Комментарии объясняют «почему», а не «что», и нередко
  фиксируют конкретный инцидент или альтернативу, которую отвергли. Это заметно ускорило
  само ревью. Ровно поэтому расхождения кода и комментария (§2.4, [LAST_COMMIT §6](LAST_COMMIT_AUDIT.md))
  я вынес отдельными находками: в этом проекте комментарию верят.
* **Объём тестов** — 1 071 зелёных теста в трёх пакетах, e2e поверх настоящего Postgres,
  coverage-гейты в CI для `shared` и `ui`.

Слабое место тестов — не покрытие, а форма: e2e на безопасность
([command-ids.e2e-spec.ts:148](backend/test/command-ids.e2e-spec.ts#L148)) перечисляет
типы действий руками, поэтому новый тип защищён только памятью автора. Это та же
проблема, что и §1.1, — и чинится тем же реестром.
